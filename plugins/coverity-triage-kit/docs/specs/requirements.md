# coverity-triage-kit 仕様書

この文書は、利用者から見た振る舞いを決める。しくみは [設計書](../design/design.md)、上位の決まりは [憲章](../constitution.md) にある。

- バージョン：0.1.0
- 4段階目の利用者から見た使い方は、元のプラグイン coverity-warning-triage（以下「元のプラグイン」）と同じにする（憲章 第26条2項）。元のプラグインの要件との対応は、9章にある。

## 1. 目的

Coverity Connect の警告（C / C++、標準・MISRA・CERT）を、人が1件ずつ調べる代わりに AI が下調べする。
警告ごとに、本物のバグかどうかの見立て、確信度、修正案と逸脱コメント案の両方を作る。人は一覧を見て、修正か逸脱かを決めるだけにする。

大がかりな一括の処理だけでなく、スキル1つ、作業エージェント1つのような小さな使い方もできるようにする。

## 2. 4つの段階

| 段階 | 部品 | 呼び方 |
| --- | --- | --- |
| 1 | スキル（`skills/` の下のフォルダ）、MCP サーバー（`mcp-servers/` の下のフォルダ） | スキルは `/<スキル>` か、AI が選ぶ。MCP サーバーは MCP のクライアントに登録する |
| 2 | 作業エージェント（`com.github.copilot/agents/` の作業エージェント）と、その表のスキル | `/agent` で選ぶ |
| 3 | 統括・作業・検証・統合のエージェント、スキル、MCP サーバー | `/agent` で統括エージェントを選ぶか、`/coverity-run` |
| 4 | 3段階目とエクステンション（Web管理画面） | チャットで「Coverity の警告をトリアージして」 |

- REQ-001：どの段階も、上の段階なしで使える。エクステンションが要るのは4段階目だけ（1〜3段階目は、エクステンションを無効にしても動く）。
- REQ-002：どの部品も、そのフォルダ（エージェントは定義のファイルと README）だけを取り出して使える。
  - スキルは、フォルダだけを作業フォルダの `.github/skills/<名前>/` か `~/.copilot/skills/<名前>/` にコピーして使える（Claude Code なら `.claude/skills/<名前>/`）。
  - MCP サーバーは、フォルダだけを置き、MCP のクライアントに登録して使える。
  - 2段階目は、作業エージェントの定義と、その表のスキル（と、使うなら MCP サーバー）だけで使える。
  - 3段階目は、エージェントの定義・スキル・MCP サーバーだけで使える（エクステンションは要らない）。
- REQ-003：下の段階の部品は、上の段階の部品の名前も、エクステンションも知らない。上の段階の部品は、下の段階の部品を、部品の表と設定のデータ（`defaults.json`）でだけ名前で参照する。
- REQ-004：部品どうしは、設計書の「部品の間の取り決め」に書いたファイルとコマンドと自然な文の頼みだけでやり取りする。取り決めの写しを2つ以上の部品が持つときは、どれも同じである。
- REQ-005：利用者の PC は Windows。すべての部品が Windows で動く。Linux でも動く。
- REQ-006：各部品の使い方は、その部品の README にだけ書く。上の段の文書（プラグインの README、段階ごとのガイド）には、下の段の部品の中身（スクリプトの名前、設定の項目の細部）を書かない。部品を足す・消す・置き換える手順は、開発者向けの `docs/replace.md` にだけ書く。
- REQ-007：元のプラグインと一緒に入れたときに困らないよう、MCP サーバー・エージェント・エクステンションのツール・記録の置き場所の名前は、元のプラグインと重ならない。ただし、スキルの名前（`/coverity-run` など）は、利用者から見た使い方を同じにするため、元のプラグインと同じにする。README に、元のプラグインとはどちらか一方だけを入れることを書く。

## 3. 1段階目：スキルと MCP サーバー

### 3.1 スキルの共通の決まり

- REQ-101：どのスキルも、そのフォルダだけで完結する。
  - フォルダの中の説明（SKILL.md、README.md、`references/`）だけで分かり、そのとおりに動く。
  - フォルダの中のファイルは、プラグインの名前、ほかのスキル・エージェント・MCP サーバー・Web管理画面の名前、フォルダの外を指すパスを書かない。
  - `README.md`（何をするか、必要なもの、置き方、呼び方、設定、結果の見方、うまくいかないとき、テストの動かし方）と、テスト（`tests/`）と、試験の課題（`evals/`）を持つ。
  - SKILL.md は、Anthropic の指針に沿う：name は64文字以内の小文字・数字・ハイフン、description は何をするかといつ使うかを三人称で1024文字以内、本文は500行未満、詳しいことは `references/` に分けて SKILL.md から1段でたどれるようにする。
- REQ-102：スキルのスクリプトは、`uv run --native-tls` で動く（Python と要るライブラリは uv が用意する）。結果は JSON を1つ標準出力に出し、失敗は `"ok": false` と理由（`error`）と終了コード 1 で返す。コマンドは PowerShell でも bash でも動く書き方にする。
- REQ-103：プロジェクトの設定は、調べたいリポジトリの `.coverity-triage/` に置く（元のプラグインと同じ形。設計書 4.1）。スキルは、自分が使う項目だけを読み、知らない項目は無視する。スキルの「確かめる」コマンドは、ファイルを作らず、設定を書き換えない。
- REQ-104：認証情報は、環境変数（既定 `COV_USER` / `COV_AUTH_KEY`）に置き、設定ファイルに書かない。チャットで聞かない。チャットに貼られたら使わず、作り直しを頼む。ログ・記録・画面では `****` に伏せる。
- REQ-105：失敗したら、起きたことと、何を直せばよいかを平易な文で伝える。その文に、ほかの部品の名前を出さない。
- REQ-106：スクリプトが `ok: false` を返したら、同じことを別のやり方（手で書き換えるなど）でしない。

### 3.2 MCP サーバー

- REQ-111：MCP サーバー（`coverity-connect`）だけを MCP のクライアントに登録して、チャットで Coverity Connect とやりとりできる。ほかの部品は要らない。
  - 接続の確かめ、条件（ストリーム、チェッカー、Impact、分類・対応・状態、件数）に合う警告の一覧、CID ごとの警告経路とチェッカーの説明、トリアージ（分類・対応・重大度・コメント）の書き戻しができる。
  - 一度に返りきらないときは、続きがあることが示され、続きを頼める。
  - 書き戻しの前に、件数と内容と確認の文字列が示される。示されただけでは、何も書き込まれない。確認の文字列が書き戻す内容と合わなければ、何も書き込まれない。同じ書き戻しをもう一度頼んでも、同じ項目は二重に書き込まれない。
  - ファイルで受け渡す使い方（条件のファイル、書き戻しの内容のファイルを渡し、結果をファイルに書く）もできる。時間のかかる処理は、途中で返り、同じ引数で呼び直すと続きをする。
  - 設定は、リポジトリの `.coverity-triage/config.yaml` の `coverity:` か、環境変数（`COVERITY_URL` など）で渡せる。リポジトリがなくても使える。
  - 偽の Coverity（`api: fake` と警告のファイル）でも動く（試しと試験のため）。
- REQ-112：ツールは Anthropic の指針に沿う：名前は `coverity_` で始まる、説明と引数の説明だけで使い方が分かる、結果は要る項目だけを返し `concise` と `detailed` を選べる、件数の多い結果はページに分ける、エラーは何を直せばよいかを書く、読むだけのツールと書き込むツールを注釈（annotations）で分ける。

### 3.3 各スキル

各スキルの細かい振る舞いは、そのスキルの README と SKILL.md に書く。ここには、利用者から見た仕事だけを書く。

| スキル | 仕事 | 頼み方の例 |
| --- | --- | --- |
| `checker-knowledge` | チェッカー（標準・MISRA・CERT）ごとの見方を答える | 「MISRA 10.4 の警告はどう見ればいい？」 |
| `triage-investigation` | 1件の警告が本物のバグかを調べ、判定・確信度・推奨と、根拠の場所（ファイルと行）を返す | 「CID 12345（NULL_RETURNS、src/foo.c の 120 行）の警告が本物か調べて」 |
| `code-fix` | 警告を直す。差分を示し、同意してから直す（作業用のコピーを渡されたときは、そこだけを直す） | 「この警告を直して」 |
| `deviation-comment` | 逸脱コメント（200文字以内）と、Classification・Action・Severity の案を返す | 「この警告の逸脱コメントを書いて」 |
| `triage-report` | 調べた結果を、決まった項目（`result.json` の形）で書き、形を確かめる | 「調べた結果を決まった形で書いて」 |
| `triage-review` | 別に調べた結果を確かめ、合格・要確認・差し戻しを返す。渡したものは変えない | 「この結果を確かめて」 |
| `triage-integration` | いくつかの警告の結果が同じ原因かを確かめ、まとめ方を返す | 「この3件、同じ原因ならまとめて」 |
| `coverity-setup` | `.coverity-triage/` の設定と認証情報を、対話で用意する | 「/coverity-setup」 |
| `coverity-run` | 条件に合う警告を一括でトリアージする手順と、実行フォルダの管理 | 「/coverity-run High だけ」 |
| `coverity-apply` | 承認を確かめて反映する（逸脱は Coverity へ、修正はブランチとプルリクエストか svn の作業コピーへ） | 「/coverity-apply」 |
| `coverity-gui` | 設定・監視・結果（承認の選択と逸脱コメントの手直し）のブラウザーの画面 | 「/coverity-gui」 |
| `coverity-help` | 困ったときに、資料と点検のコマンドで確かめて答える | 「/coverity-help このエラーは？」 |
| `coverity-selftest` | 道具・偽データでの流れ・社内の Coverity（読むだけ）・ビルドを確かめ、伏せ字の報告にまとめる | 「/coverity-selftest」 |

- REQ-121：調べる・直す・逸脱コメントを書く・確かめる・まとめるスキルを直接頼んだときは、結果はチャットに返り、頼まれない限り結果のファイルを作らず、Coverity にも書き込まない。
- REQ-122：警告の情報（CID、チェッカー、ファイルと行、警告経路）が足りないときは聞く。Coverity から警告を取る道具が使えるときは、それで取る。
- REQ-123：リポジトリに知識のファイル（`.coverity-triage/knowledge.md`）があれば、その知識を使う。
- REQ-124：直すときは、差分を示し、同意を得てから作業中のファイルを直す。作業用のコピーのフォルダを渡されたときは、そのフォルダだけを直す。
- REQ-125：確かめるときは、渡された結果と差分を書き換えない。

## 4. 2段階目：作業エージェント

- REQ-201：作業エージェントは、チャットの頼みだけで、1件の警告（または1グループ）のトリアージを最後まで行う。Web管理画面とほかのエージェントは使わない。
  - CID を渡されたら、警告の情報を取り（取れなければ聞く）、真偽を調べ、修正案と逸脱コメント案の両方を作り、決まった形で報告する。
  - 頼まれたときは、結果をファイル（`result.json` の形）に書く。
- REQ-202：作業エージェントの定義は、使う部品の名前と役割を「使う部品」の表（役割・部品・使うとき）にだけ書く。表の外には、部品の名前も、使う順の並びも、自分の名前も書かない。
- REQ-203：質問には ask_user を使う。ask_user が使えないとき（ほかのエージェントから呼ばれたとき）は、質問も合否の判断もせず、頼みの文に書かれたことだけをし、頼みの文が求める形で返す。
- REQ-204：直してよいのは、頼まれたフォルダ（作業用のコピー）のファイルと、頼まれた結果のファイルだけ。利用者の作業中のファイルは、同意なしに変えない。
- REQ-205：作業エージェントは、自分の結果の合否を決めない。

## 5. 3段階目：一括のトリアージ（オーケストレーション）

- REQ-301：統括エージェントを選んで「Coverity の警告をトリアージして（High だけ、など）」と頼むか、`/coverity-run` と入力すると、条件に合う警告を一括でトリアージし、実行フォルダに一覧と詳細と差分と承認の案ができる。Web管理画面は要らない。
- REQ-302：`/coverity-run` の条件の言い方は、元のプラグインと同じに受け付ける（「misra.yaml」「High だけ」「10 件だけ」「最初に解析して」「解析はしないで」）。途中の実行があれば、続きから再開するかを聞く。
- REQ-303：流れは次の順。各段は、設定で使わないときは飛ばす。
  初回解析 → 警告の取得 → 警告経路の取得 → グループ分け → 警告ごとの作業（作業エージェント、並行して最大 `parallel` 体）→ 同じ原因の統合（統合エージェント）→ 結果の確かめ（検証エージェント。差し戻しは作業エージェントが作り直す）→ ビルドでの検証 → 一覧と承認の案。
- REQ-304：次に何をするかは、一括実行のスキルのスクリプトが決める（統括エージェントは、その指示に従う）。統括エージェントは、ファイルを直さず、警告を自分で調べない。
- REQ-305：作り直しは、警告ごとに上限（`agents.max_rework`、既定 1、0〜2）まで。上限を超えた指摘は「要確認」として残す。人に見せる確信度は、作業エージェントと検証エージェントの低いほうになる。
- REQ-306：始めたら、終わるまで人に質問しない（始める前に、修正用のフォルダの読み書きの許可を1回だけもらう）。
- REQ-307：AI が失敗しても、ほかの警告の処理を続ける。処理できなかった警告は一覧に出し、再開したときにやり直す。
- REQ-308：終わったら、統括エージェントは、実行の記録を振り返って課題を書き残し、チャットで結果と課題を伝える。

## 6. 4段階目：Web管理画面

元のプラグインと同じ使い方である。

### 6.1 始める

- REQ-401：チャットで「Coverity の警告をトリアージして」と頼むと、Web管理画面の URL が示される。開始の前の設定は画面で行い、開始ボタンを押すと、チャットでもう一度頼まなくても始まる。
- REQ-402：Web管理画面は、Copilot CLI を動かしているマシンのブラウザーからだけ開ける。URL には、起動ごとに作る合言葉が入る。いつもの番号（ポート）が使われていれば、空いている番号で起動する。Copilot CLI を終えると、サーバーも終わる。
- REQ-403：開始の前に、次を決められる。
  - 役割（統括・作業・検証・統合）ごとに使うモデル。最初は、統括と検証に思考力の高いモデル、作業と統合に費用の低いモデルが選ばれている。
  - エージェントごとの思考の深さ（最初は「変えない」）
  - 繰り返しの上限（検証で差し戻された警告を作り直す回数の上限）
  - 条件ファイルの名前、Impact で絞るか（High / Medium / Low / Unspecified、または絞らない）、調べる件数の上限（1〜100）、最初に解析するか（設定どおり／する／しない）
  - Copilot CLI のモデルが Auto のときは、役割ごとのモデルが効かないことがあることと、実際に動いたモデルが示される。
- REQ-404：画面から始めたときは、前の実行が途中で止まっていても、聞かずに、画面の条件で新しく始める。途中の実行は残り、チャットの `/coverity-run` で再開できる。

### 6.2 実行中

- REQ-411：実行中は、ページを再読み込みしなくても、次が更新される。
  - 各エージェントの役割、状態、担当、実際に動いたモデル
  - 今が計画・実行・評価のどれか
  - エージェント間のデータの受け渡しを表した図
  - 作業ごとの様子（段・経過時間・「⚠ 停止?」・エラー）、重大なエラーと注意、最近の動き、初回解析の進み具合、全体の進み具合
  - 「⚠ 停止?」は、10分（初回解析は30分）動きがないときに出る。修正用のコピーを用意している作業には出ない。
- REQ-412：実行中にエージェントが求める確認（許可、AI クレジットの上限、質問）には、チャットで答える。画面には、チャットで確認を待っていることと、何の確認かが示される。
- REQ-413：止めるボタンを押すと、この実行のエージェントが止まり、10秒を目安に画面が終了の表示になる。チャットのほかの作業は止めない。止めきれないエージェントは、そのエージェントと止め方が示され、ツールを使えない。
- REQ-414：実行中に `/clear` をすると画面の更新が止まることと、しないことが、画面とチャットで示される。`/clear` の後にもう一度頼むと、前の実行が途中で切れたことが示される。

### 6.3 終わった後

- REQ-421：終わった後は、次を見られる。
  - 各エージェントの実行結果（長いものは畳んである）
  - 検証の結果（警告ごとに、確かめた項目ごとの合否と指摘）
  - 実行全体のまとめと、終わった理由（すべて合格した／上限の回数に達した／ユーザーが止めた／途中で終わった（理由つき））
  - 件数と承認の内訳、一覧（確信度の低い順）、処理できなかった作業
  - 詳細レポートと差分、承認の画面（結果と設定の画面の「結果」）へのリンク
- REQ-422：課題の一覧（失敗した実行、詰まったエージェント、データの流れ）と、coverity-triage-kit 自身を改善する Issue の案が並ぶ。案ごとの承認ボタンを押すと、その案だけが自身の GitHub リポジトリに Issue として起票される。起票できないときは、案は並び、起票できるようにする手順が示される。
- REQ-423：画面は、幅を変えても崩れず、ライトモードとダークモードで読め、状態を色だけでなく文字でも示す（WCAG 2.2 の色の差と文字の拡大）。表示は簡潔で、説明のない専門用語を使わない。

## 7. トリアージの中身（どの段階でも同じ）

- REQ-501：警告を1件ずつ（グループは1つずつ）調べる。警告経路を仮説として、呼び出し元や定義までたどって確かめ、判定（true_bug / false_positive / intentional / undetermined）・確信度（high / medium / low）・推奨（fix / deviation）を決める。「たぶん」「ふつうは」で決めない。
- REQ-502：警告の内容にかかわらず、修正案と逸脱コメント案の両方を作る。最新のリビジョンで直っているときは修正案を作らず、そのことを書く。どちらを採るかは人が決める。
- REQ-503：根拠は、実際に読んだコードの場所（リポジトリからのパスと行）で示す。
- REQ-504：逸脱コメントは日本語で200文字以内、1〜2文、「誤検知。」「意図的。」「本物の不具合。」で始め、理由 → コードの場所 の順に書く。条件つきの言い方、依頼の言い方を書かない。無条件に無害と言えない本物のバグは、修正を推奨する。
- REQ-505：修正は最小にし、外から見える仕様を変えず、新しい MISRA・CERT の違反を作らず、周りのコードの書き方に合わせる。
- REQ-506：同じチェッカーで、同じマクロ、同じファイルと関数、または同じファイルと行の警告は、1グループ（10件まで）にまとめて調べる。却下されたグループの CID は、次の実行からグループにしない。

## 8. 試験

- REQ-601：プラグインのフォルダで `python3 tests/run.py`（Windows では `py -3 tests/run.py`）を実行すると、モデルを使わない試験（部品ごとの試験、取り決めの一致、独立性、文書、画面）がすべて動き、合否が出る。
- REQ-602：段階ごとに、実際のモデルで課題を解かせて採点する試験（EVAL）がある：1段階目はスキルごと（skill-creator の形）と MCP サーバー（mcp-builder の形）、2段階目は作業エージェント、3段階目は一括のトリアージ、4段階目は Web管理画面の流れ。AI クレジットを使うので、CI では動かさない。
- REQ-603：独立性の試験は、部品を1つずつ（2段階目と3段階目は、その段階の部品の組を）別の場所に取り出して、その部品の試験が通ることと、その部品だけで仕事ができることを確かめる。
