# coverity-triage-kit 仕様書

この文書は、利用者から見た振る舞いを決める。しくみは [設計書](../design/design.md)、上位の決まりは [憲章](../constitution.md) にある。

- バージョン：0.2.0
- 4段階目の利用者から見た使い方は、元のプラグイン coverity-warning-triage（以下「元のプラグイン」）と同じにする（憲章 第26条2項）。元のプラグインの要件との対応と、違いは、9章にある。
- スキルの名前は、利用者が打つコマンドの名前なので、この仕様書に書く。スキル・エージェントの中身（スクリプトの名前、設定の項目の細部）は、各部品の README に書く。

## 1. 目的

Coverity Connect の警告（C / C++、標準・MISRA・CERT）を、人が1件ずつ調べる代わりに AI が下調べする。
警告ごとに、本物のバグかどうかの見立て、確信度、修正案と逸脱コメント案の両方を作る。人は一覧を見て、修正か逸脱かを決めるだけにする。

大がかりな一括の処理だけでなく、スキル1つ、作業エージェント1つのような小さな使い方もできるようにする。

GitHub Copilot CLI と Claude Code の両方で使える。1〜3段階目は両方で、4段階目（Web管理画面）は Copilot CLI だけで使う（REQ-009）。

## 2. 4つの段階

| 段階 | 部品 | 呼び方（Copilot CLI） | 呼び方（Claude Code） |
| --- | --- | --- | --- |
| 1 | スキル（`skills/` の下のフォルダ）、MCP サーバー（`mcp-servers/` の下のフォルダ） | スキルは `/<スキル>` か、AI が選ぶ。MCP サーバーは MCP のクライアントに登録する | 同じ（プラグインを入れると MCP サーバーも登録される） |
| 2 | 作業エージェントと、その「使う部品」の表のスキル（と MCP サーバー） | `/agent` で選ぶ | 作業エージェントの名前を挙げて頼むか、`claude --agent` で起動する |
| 3 | 統括・作業・検証・統合のエージェント、スキル、MCP サーバー | `/agent` で統括エージェントを選ぶか、`/coverity-run` | 統括エージェントを `claude --agent` で起動するか、`/coverity-run` |
| 4 | 3段階目と、エクステンション（Web管理画面）と、プラグイン全体のスキル（画面の入口、困ったとき、自己診断） | チャットで「Coverity の警告をトリアージして」 | 使えない |

- プラグインから入れたスキルは、`/coverity-triage-kit:<スキル>` で呼ぶ。ほかに同じ名前のスキルがなければ、`/<スキル>` でも呼べる（どちらが使えるかは Copilot CLI の版による。設計書 9.4 で測る。Claude Code では両方使える。設計書 9.5）。この仕様書では `/<スキル>` と書く。
- REQ-001：どの段階も、上の段階なしで使える。エクステンションが要るのは4段階目だけ（1〜3段階目は、エクステンションを無効にしても動く）。
- REQ-002：どの部品も、そのフォルダ（エージェントは定義のファイルと README）だけを取り出して使える。
  - スキルは、フォルダだけを作業フォルダの `.github/skills/<名前>/` か `~/.copilot/skills/<名前>/` にコピーして使える（Claude Code なら `.claude/skills/<名前>/`）。名前を変えてコピーしても使える。
  - MCP サーバーは、フォルダだけを置き、MCP のクライアントに登録して使える。
  - エージェントは、定義を作業フォルダの `.github/agents/` か `~/.copilot/agents/` にコピーして使える（Claude Code なら、Claude Code 用の定義を `.claude/agents/` か `~/.claude/agents/` に）。
  - 2段階目は、作業エージェントの定義と、その表のスキル（と、使うなら MCP サーバー）だけで使える。
  - 3段階目は、エージェントの定義・1段階目のスキル・MCP サーバーだけで使える（エクステンションは要らない）。
- REQ-003：下の段階の部品は、上の段階の部品の名前も、エクステンションも知らない。上の段階の部品は、下の段階の部品を、「使う部品」の表と設定のデータ（`defaults.json`）でだけ名前で参照する。
- REQ-004：部品どうしは、設計書の「部品の間の取り決め」に書いたファイルとコマンドと自然な文の頼みだけでやり取りする。取り決めの写しを2つ以上の部品が持つときは、どれも同じであり、同じ試験のデータで同じ答えを出す。
- REQ-005：利用者の PC は Windows。すべての部品が Windows で動く。Linux でも動く（Linux で Copilot CLI から MCP サーバーに認証情報を渡す方法は、設計書 3.2）。
- REQ-006：各部品の使い方は、その部品の README にだけ書く。上の段の文書（プラグインの README、4段階目のガイド）は、スキルの名前（コマンド）を書いてよいが、スクリプトの名前や設定の項目の細部を書かない。役割と部品の名前の対応表は、開発者向けの `docs/parts.md` にだけ書く。部品を置き換える手順の文書は用意しない（どの段階も単独で使えることは、REQ-001〜003 のとおり変わらない）。
- REQ-007：元のプラグインと一緒に入れたときに困らないよう、MCP サーバー・エージェント・エクステンションのツール・記録の置き場所の名前は、元のプラグインと重ならない。スキルの名前（`/coverity-run` など）は、利用者から見た使い方を同じにするため、元のプラグインと同じにする。
- REQ-008：利用者向けの文書は、1段階目から4段階目の順に進むチュートリアル（`docs/guide/1-skill.md`〜`4-screen.md`）を中心にする。各ステップは、操作しながら読める構成にし、やること・入力の例・表示の例・分かったこと・次のステップを書く。できることと利用者がやることを先に書き、制限や例外は各文書の末尾の「補足」にまとめる。プラグインの README は5分ほどで読める入口にし、できること（例つき）、チュートリアルへの導線、日常のコマンド、目的別の文書の一覧を書く。条件と設定の指定方法は `docs/guide/conditions.md` に、運用の情報（ツールを事前に許可する方法（`--allow-tool`、`--add-dir` の例）、実行中の注意、うまく動かないとき（3つの原因と対処）、Issue の起票の準備）は `docs/guide/operation.md` に書く。Claude Code で使えることは README の1か所にだけ書き、Claude Code での起動方法と事前の許可は、各エージェントの README の「Claude Code で使う」に書く。テストの実行方法は `tests/README.md` に書く。
- REQ-009：1〜3段階目は、Claude Code でも使える。4段階目（エクステンションと Web管理画面）は Copilot CLI だけで使う。
  - 同じプラグインのフォルダを、Claude Code のマーケットプレイス（リポジトリの一番上の `.claude-plugin/marketplace.json`）から `claude plugin install coverity-triage-kit@plugin-market-place` で入れられる。Copilot CLI と Claude Code は、それぞれ自分の形のファイルだけを読み、もう一方の形のファイルで振る舞いが変わらない。
  - Claude Code では、スキルを `/coverity-triage-kit:<スキル>`（ほかに同じ名前がなければ `/<スキル>`）で呼べ、MCP サーバーはプラグインが登録する。作業エージェントは名前を挙げて頼むか `claude --agent` で起動して使え、統括エージェントは `claude --agent` で起動するか `/coverity-run` で使える。振る舞い（REQ-201〜REQ-205、REQ-301〜REQ-310、7章）は Copilot CLI と同じ。
  - 認証情報は、Copilot CLI と同じ環境変数で渡す。入れていない変数は、ないものとして扱う。
  - Claude Code に画面の入口のスキルが読まれて使われても、画面は開かず、作業を始めない。Copilot CLI の3つの原因（REQ-402）は示さず、Web管理画面は Copilot CLI だけの機能であることと、Claude Code で一括のトリアージを始める2つのしかた（統括エージェントを `claude --agent` で起動する、`/coverity-run`）を、呼び方だけ伝える。
  - Claude Code で作業エージェントを名前を挙げて頼んだとき（会話の主役から呼ばれるエージェントとして動くとき）は、利用者に聞く道具がなく、同意を受け取れないので、修正の差分を案として返し、作業中のファイルを直さない。差分を見せて同意を得てから直す流れ（REQ-204）は、作業エージェントを `claude --agent` で起動したときに使う。
  - Claude Code では、反映（`/coverity-apply`）を、`--agent` を付けずに起動した会話で行う。統括エージェントを会話の主役にした会話には、ファイルを書く道具と、反映の確かめ・書き戻しのツールがないため。
  - プラグインの README に「Claude Code で使う」（入れ方、段階ごとの呼び方、4段階目は Copilot CLI だけであること、夜通し動かすときの前もって許可するしかた、認証情報の環境変数、プラグインのフォルダを作業フォルダにしないこと）を書く。各エージェントの README に、Claude Code での始め方と、`.claude/agents/`・`.claude/skills/` への取り出し方を書く。

## 3. 1段階目：スキルと MCP サーバー

### 3.1 スキルの共通の決まり

- REQ-101：どのスキルも、そのフォルダだけで完結する。
  - フォルダの中の説明（SKILL.md、README.md、`references/`）だけで分かり、そのとおりに動く。
  - フォルダの中のファイルは、プラグインの名前、ほかのスキル・エージェント・MCP サーバー・Web管理画面の名前、フォルダの外を指すパスを書かない。ほかの部品の力を借りたいときは、役割をふつうの言葉で書く。
  - `README.md`（何をするか、必要なもの、置き方、呼び方、設定、結果の見方、うまくいかないとき、テストの動かし方）と、テスト（`tests/`）と、試験の課題（`evals/`）を持つ。
  - SKILL.md は、Anthropic の指針に沿う：name は64文字以内の小文字・数字・ハイフン、description は何をするかといつ使うかを三人称で1024文字以内、本文は500行未満、詳しいことは `references/` に分けて SKILL.md から1段でたどれるようにする。
  - プラグイン全体のスキル（4段階目）は、この項の「ほかの部品の名前を書かない」の代わりに、名前を「使う部品」の表にだけ書く。
- REQ-102：スキルのスクリプトは、`uv run --native-tls` で動く（Python と要るライブラリは uv が用意する）。結果は JSON を1つ標準出力に出し、失敗は `"ok": false` と理由（`error`）と終了コード 1 で返す。コマンドは PowerShell でも bash でも動く書き方にする。日本語の Windows の PowerShell で読んでも文字化けしない。
- REQ-103：プロジェクトの設定は、調べたいリポジトリの `.coverity-triage/` に置く（元のプラグインと同じ形。設計書 4.1）。スキルは、自分が使う項目だけを読み、知らない項目は無視する。スキルの「確かめる」コマンドは、ファイルを作らず、設定を書き換えない。
- REQ-104：認証情報の扱い。
  - 認証情報は、環境変数（既定 `COV_USER` / `COV_AUTH_KEY`）に置き、設定ファイルに書かない。チャットで聞かない。認証キーは、ターミナルの伏せ字の欄で入れてもらう。チャットに貼られたら使わず、作り直しを頼む。ログ・記録・画面では `****` に伏せる。
  - 初回解析で Coverity に登録するときは、認証キーを環境変数 `COVERITY_PASSPHRASE` でだけ渡し、コマンドの引数とログに出さない。
  - GitHub のトークンは聞かない。プルリクエストは、使える道具で作り、なければ作るための URL を示す。
  - 画面で認証情報を保存できるのは Windows だけ。画面にキーの値を出さない。
- REQ-105：失敗したら、起きたことと、何を直せばよいかを平易な文で伝える。1段階目の部品は、その文に、ほかの部品の名前を出さない。
- REQ-106：スクリプトが `ok: false` を返したら、同じことを別のやり方（手で書き換えるなど）でしない。
- REQ-107：`config.yaml` を書き換えるとき（準備のスキル、結果と設定の画面）は、人が書いた注釈を元の場所に残す（元のプラグインの REQ-102 と同じ）。
  - 変えた値の行だけが変わる。注釈（行の頭の `#`、字下げした `#`、行の終わりの `# …`）は残る。値を変えた行の終わりの注釈も残る。消えるのは、消した項目やリストの値に付いていた注釈（その行の終わりと、すぐ上の注釈の行）だけ。リストを空にしたときは `キー: []` になり、キーの行の終わりの注釈は残る。リストの値の並びを変えると、値は注釈と一緒に動く。
  - ファイルにない項目は、既定の値から変えたときだけ足す。ファイルにある項目は、値を変えなければ、空の値でもそのまま残る。
  - 注釈を元の場所に残せない書き方（`|`・`>` で何行かにわたる値、`&`・`*` の使い回しなど）のときは、保存の前に「このファイルでは、注釈は動いたり消えたりします」と知らせ、やめることもできる。続けると、値は正しく保存される。

### 3.2 MCP サーバー

- REQ-111：MCP サーバー（`coverity-connect`）だけを MCP のクライアントに登録して、チャットで Coverity Connect とやりとりできる。ほかの部品は要らない。
  - 接続の確かめ、条件（ストリーム、チェッカー、Impact、分類・対応・状態、件数）に合う警告の一覧、CID ごとの警告経路とチェッカーの説明、トリアージ（分類・対応・重大度・コメント）の書き戻しができる。
  - 一度に返りきらないときは、続きがあることが示され、続きを頼める。
  - 書き戻しの前に、件数と内容と確認の文字列が示される。示されただけでは、何も書き込まれない。確認の文字列が書き戻す内容と合わなければ、何も書き込まれない。同じ書き戻しをもう一度頼んでも、同じ項目は二重に書き込まれない。
  - ファイルで受け渡す使い方（条件のファイル、書き戻しの内容のファイルを渡し、結果をファイルに書く）もできる。時間のかかる処理は、途中で返り、同じ引数で呼び直すと続きをする。
  - 設定は、リポジトリの `.coverity-triage/config.yaml` の `coverity:` か、環境変数（`COVERITY_URL` など）で渡せる。リポジトリがなくても使える。
  - 偽の Coverity（`api: fake` と警告のファイル）でも動く（試しと試験のため）。
- REQ-112：ツールは Anthropic の指針に沿う：名前は `coverity_` で始まる、説明と引数の説明だけで使い方が分かる、結果は要る項目だけを返し `concise` と `detailed` を選べる、件数の多い結果はページに分ける、エラーは何を直せばよいかを書く、読むだけのツールと書き込むツールを注釈（annotations）で分ける。
- REQ-113：MCP サーバーは、初めて起動するときに Copilot CLI が `server/discover` を先に送っても、同じ接続で `initialize` から始められる。

| `coverity-gui` | 設定・監視・結果（承認の選択と逸脱コメントの手直し）のブラウザーの画面 | 「/coverity-gui」 |

- REQ-121：調べる・直す・逸脱コメントを書く・確かめる・まとめるスキルを直接頼んだときは、結果はチャットに返り、頼まれない限り結果のファイルを作らず、Coverity にも書き込まない。
- REQ-122：警告の情報（CID、チェッカー、ファイルと行、警告経路）が足りないときは聞く。Coverity から警告を取る道具が使えるときは、それで取る。

- REQ-124：直すときは、差分を示し、同意を得てから作業中のファイルを直す。作業用のコピーのフォルダを渡されたときは、そのフォルダだけを直す。
- REQ-125：確かめるときは、渡された結果と差分を書き換えない。
- REQ-126：手順のスキルは、コマンドを使えないとき（ほかのエージェントからの作業）も、手順を最後まで行える。そのとき、決まった形の確かめは、頼んだ側が行う。

## 4. 2段階目：作業エージェント

- REQ-201：作業エージェントは、チャットの頼みだけで、1件の警告（または1グループ）のトリアージを最後まで行う。Web管理画面とほかのエージェントは使わない。
  - CID を渡されたら、警告の情報を取り（取れなければ聞く）、真偽を調べ、修正案と逸脱コメント案の両方を作り、決まった形で報告する。
  - 頼まれたときは、結果をファイル（`result.json` の形）に書く。
- REQ-202：作業エージェントの定義は、使う部品の名前と役割を「使う部品」の表（役割・部品・使うとき）にだけ書く。表の外には、部品の名前も、使う順の並びも、自分の名前も書かない。frontmatter の `tools` に書く MCP のツールは、表にある MCP サーバーのものだけにする。
- REQ-203：頼みの文が指示ファイル（作業用のコピーと結果のファイルを示したもの）を指すときは、ほかのエージェントからの頼みとして、質問も合否の判断もせず、頼みの文とそれが指すファイルに書かれたことだけをし、頼みの文が求める形で返す。それ以外は、利用者との会話として扱う。質問には利用者に聞く道具（Copilot CLI は ask_user、Claude Code は AskUserQuestion）を使い、使えないときは、聞くことを返事に書いてそのターンを終える。作業中のファイルを直す同意は、利用者からだけ受け取る。
- REQ-204：直してよいのは、頼まれたフォルダ（作業用のコピー）のファイルと、頼まれた結果のファイルだけ。利用者の作業中のファイルは、同意なしに変えない。
- REQ-205：作業エージェントは、自分の結果の合否を決めない。

## 5. 3段階目：一括のトリアージ（オーケストレーション）

- REQ-301：`/agent` で統括エージェントを選んで（Claude Code では、統括エージェントを `claude --agent` で起動して）「Coverity の警告をトリアージして（High だけ、など）」と頼むか、`/coverity-run` と入力すると、条件に合う警告を一括でトリアージし、実行フォルダに一覧と詳細と差分と承認の案ができる。Web管理画面は要らない。
- REQ-302：`/coverity-run` の条件の言い方は、元のプラグインと同じに受け付ける（「misra.yaml」「High だけ」「10 件だけ」「最初に解析して」「解析はしないで」）。途中の実行があれば、「前回の実行（日時・条件）が途中です。続きから再開しますか？」と聞く。再開のときは、初回解析の有無を変えられない。設定がなければ、準備のしかたを示して始めない。
- REQ-303：流れは次の順。各段は、設定で使わないときは飛ばす。
  初回解析 → 警告の取得 → 警告経路の取得 → グループ分け → 警告ごとの作業（作業エージェント、並行して最大 `parallel` 体）→ 同じ原因の統合（統合エージェント）→ 結果の確かめ（検証エージェント。差し戻しは作業エージェントが作り直す）→ ビルドでの検証 → 一覧と承認の案。
- REQ-304：次に何をするかは、一括実行のスキルのスクリプトが決める（統括エージェントは、その指示に従う）。統括エージェントは、ファイルを直さず、警告を自分で調べない。役に合うエージェントがないときは、汎用のエージェントに代わりをさせず、どのエージェントが要るかを伝える。
- REQ-305：作り直しは、警告ごとに上限（`agents.max_rework`、既定 1、0〜2）まで。上限を超えた指摘は「要確認」として残す。人に見せる確信度は、作業エージェント・検証エージェント・ビルドでの検証のいちばん低いものになる（下げるだけ）。
- REQ-306：始めたら、終わるまで人に質問しない。始める前に、実行フォルダの読み書きとコマンドの許可を、このセッションのあいだだけ与えるしかた（`/add-dir`、「このセッションでは許可」）を1回だけ示す。Claude Code で動いているときは、Claude Code の形（起動のときの `claude --add-dir … --allowedTools …`、または `/add-dir` と、`/permissions` での `uv` のコマンド・スキルを使うこと・スキルのフォルダを読むこと（読むだけ）・実行フォルダの中への書き込み・Coverity から読むツールの許可。`/permissions` の許可は設定に残るので、自分だけの設定に保存し、終わったら消すことも）を示し、README にも書く。夜通し動かすときは、起動のときの指定を勧める（`/add-dir` だけでは、ツールを許可しない）。どちらのツールでも、Coverity に書き戻すツールは前もって許可しない。
- REQ-307：AI が失敗しても、ほかの警告の処理を続ける。処理できなかった警告は一覧に出し、再開したときにやり直す。
- REQ-308：終わったら、統括エージェントは、実行の記録を振り返って課題を書き残し、チャットで結果と課題を伝える。
- REQ-309：結果と設定の画面のスキルがあるときは、始めたときに監視の画面を、終わったときに結果の画面を開く。終わったら、承認の選び方（修正・逸脱・却下・反映しない）と反映のしかたを案内する。
- REQ-310：会話の決まり：一度に1つずつ、短く平易に伝える。コマンドを動かす前に目的を言う。初回解析をするときは「最初に、開いているフォルダをビルド・解析して、Coverity サーバに登録します（数十分かかることがあります）」と伝える。5件ほどごとに進み具合を1行で伝える。利用者が日本語以外で書いたら、その言葉で答える。

### 6.1 始める

- REQ-411：実行中は、ページを再読み込みしなくても、次が更新される。

  - 今が計画・実行・評価のどれか（初回解析・取得・作業・統合・ビルドでの検証は実行、確かめは評価）
  - エージェント間のデータの受け渡しを表した図
  - 作業ごとの様子（作業・段・経過時間・作り直し・状態。「⚠ 停止?」は、10分（初回解析は30分）動きがないときに出る。修正用のコピーを用意している作業には出ない）、重大なエラーと注意、最近の動き（新しい順に5行）、初回解析の進み具合、全体の進み具合（処理した件数 / 全体）

- REQ-412：実行中にエージェントが求める確認（許可、AI クレジットの上限、質問）には、チャットで答える。画面には、チャットで確認を待っていることと、何の確認か（役割、種類、コマンドやパス）が示される。画面からは答えない。
- REQ-413：止めるボタンを押すと、この実行のエージェントと、初回解析やビルドの処理が止まり、10秒を目安に画面が終了の表示になる。チャットのほかの作業は止めない。止めきれないエージェントや処理は、そのものと止め方が示され、エージェントはツールを使えない。

- REQ-415：統括エージェントが、実行が終わっていないのに止まったら（止めるボタンを押したときを除く）、エクステンションは、同じ実行フォルダの続きから統括エージェントを2回まで始め直し、そのことを最近の動きに出す。

### 6.3 終わった後

- REQ-421：終わった後は、次を見られる。

- REQ-422：課題の一覧（失敗した実行、詰まったエージェント、データの流れ）と、coverity-triage-kit 自身を改善する Issue の案が並ぶ。最後まで動いた実行では、統括エージェントが振り返って足した課題も並ぶ。止めた実行と途中で終わった実行では、課題を洗い出すためにエージェントを動かさない。案ごとの承認ボタンを押すと、その案だけが自身の GitHub リポジトリに Issue として起票される。起票できないときは、案は並び、起票できるようにする手順（リポジトリ、`gh` を入れてログインする）が示される。

## 7. トリアージの中身（どの段階でも同じ）

- REQ-501：警告を1件ずつ（グループは1つずつ）調べる。警告経路を仮説として、呼び出し元や定義までたどって確かめ、判定（true_bug / false_positive / intentional / undetermined）・確信度（high / medium / low）・推奨（fix / deviation）を決める。「たぶん」「ふつうは」で決めない。評価基準 C-01〜C-04、C-21〜C-23、C-28 に従う。
- REQ-502：警告の内容にかかわらず、修正案と逸脱コメント案の両方を作る。最新のリビジョンで直っているときは修正案を作らず、そのことを書く。どちらを採るかは人が決める（C-05）。
- REQ-503：根拠は、実際に読んだコードの場所（リポジトリからのパスと行）で示す（C-12）。
- REQ-504：逸脱コメントは日本語で200文字以内、1〜2文、「誤検知。」「意図的。」「本物の不具合。」で始め、理由 → コードの場所 の順に書く。条件つきの言い方、調べた過程、依頼の言い方を書かない。無条件に無害と言えない本物のバグは、修正を推奨する（C-09〜C-11、C-28）。
- REQ-505：修正は最小にし、外から見える仕様を変えず、新しい MISRA・CERT の違反を作らず、周りのコードの書き方に合わせる（C-06〜C-08）。
- REQ-506：同じチェッカーで、同じマクロ、同じファイルと関数、または同じファイルと行の警告は、1グループ（10件まで）にまとめて調べる。却下されたグループの CID は、次の実行からグループにしない。統合でまとめるのは、原因が1つのものだけ（C-20）。
- REQ-507：結果の実行フォルダ（`<output_dir>/<YYYYmmdd-HHMMSS>/`）に、一覧 `summary.html`、詳細 `cid/<ID>.html`、差分 `patches/<ID>-fix.patch`（git 形式）、修正後のファイル `fixed/<ID>/fix/<パス>`、推奨入りの `approvals.json` ができる。修正後のファイルと差分は警告ごとに独立している。一覧と詳細の形は C-25・C-26、ファイルの置き場所は C-27 のとおり。どのレポートも、1つのファイルで、スクリプトを含まず、AI の書いた文をそのまま HTML にしない（エスケープする）。output_dir はリポジトリの外（既定 `../coverity-triage-out`）で、中なら始めない。
- REQ-508：人が承認して反映するまで、利用者の作業中のファイルも Coverity のトリアージも変えない（C-24）。反映（`/coverity-apply`）は、件数と ID を見せて同意を得てから行う。逸脱は、その警告のストリームが使うトリアージストアに書き戻す。修正は Coverity に書かない。修正のブランチは `coverity-fix/cid-<CID>`、グループは `coverity-fix/<実行の日時>-G<n>`、コミットの文は「Coverity CID <一覧>: 修正」と空行と要約。途中で失敗したら、もう一度反映すると残りだけを行い、二重に書かない。
- REQ-509：成功の基準：準備は20分以内、人の確認は1件5分以内、推奨がそのまま採用される割合は9割以上、100件を人が張り付かずに一晩で処理できる。

評価基準 C-01〜C-28 の文は、元のプラグインと同じで、結果の確かめのスキルの `assets/criteria.json` にある（設計書 4.6）。

## 8. 試験

- REQ-601：プラグインのフォルダで `python3 tests/run.py`（Windows では `py -3 tests/run.py`）を実行すると、モデルを使わない試験（部品ごとの試験、構造、取り決めの一致、独立性、模擬の Coverity との結合、文書、画面）がすべて動き、合否が出る。

- REQ-603：独立性の試験は、部品を1つずつ（2段階目と3段階目は、その段階の部品の組を）別の場所に取り出して、その部品の試験が通ることを確かめる（モデルを使わない）。その部品だけで仕事ができることは、EVAL で確かめる。

- 一覧 `summary.html` の「承認」の列は、一覧を作ったときの値を示す。今の値は、結果と設定の画面で見る。
- 結果と設定の画面は `/coverity-gui` で開く（元は ct.py gui）。困ったときのスキルからも開ける。
- 結果と設定の画面の「試しにビルドする」ボタンはない。ビルドの試しは `/coverity-setup` で行う（画面には、そのことを示す）。
- サブエージェントを Copilot の設定のフォルダに置く手順（元の `/coverity-setup` の一部）はない。エージェントはプラグインと一緒に入る。
- 別の形で作られた実行フォルダ（元のプラグインの実行）は、一覧に出るが、続きからはできず、反映もしない。
- `/coverity-setup` は、「画面で準備する」の道を出さない（準備は対話で行い、後から変えるのは結果と設定の画面）。Coverity と通信する部品の用意（元の prewarm）もしない。用意は、README の「準備」の2のコマンドで、先に1回済ませておく（済ませていなくても、初めて MCP サーバーが起動するときに用意されるが、時間がかかる）。
- Issue の起票先は、エクステンションの `defaults.json` の `issueRepo`（既定は xclang-brain/plugin-market-place）に決めてある（元は `plugin.json` の `repository` で、なければ起票できなかった）。画面の「課題と Issue の案」に、起票先のリポジトリを示す。
- Claude Code でも、1〜3段階目を使える（元のプラグインは Copilot CLI だけ）。4段階目（Web管理画面）は、元と同じく Copilot CLI だけ（REQ-009）。
- 作業エージェントは、頼みの文が指示ファイルを指すかどうかで、ほかのエージェントからの頼みかを決める（元のプラグインの作業エージェントは、指示ファイルなしでは動かなかった。0.1.0 は、利用者に聞く道具があるかどうかで決めていた。REQ-203）。
- 一括実行のスキル（`/coverity-run`）は、コマンドとして呼んだときに新しい実行を始める。スラッシュなしの「Coverity の警告をトリアージして」は、画面の入口が受け持つ（元と同じ。一括実行のスキルは画面の入口を知らず、コマンドとして呼ばれたときだけ始めるという自分の決まりで分かれる）。
