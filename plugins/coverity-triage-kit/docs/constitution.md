# coverity-triage-kit 憲章

- 版：1.1.0
- 欠番：第4条、第11条〜第18条

## 第1章 総則

### 第1条 目的

本憲章は、coverity-triage-kit（Coverity Connect の警告をトリアージし、警告ごとに修正案と逸脱コメント案の両方を作るプラグイン）が守る最上位ルールである。

### 第2条 構成

第2章は共通条項、第4章は coverity-triage-kit の条項である。どちらも coverity-triage-kit が守る。

### 第3条 用語

| 用語 | 定義 |
| --- | --- |
| 部品 | スキル、MCP サーバー、エージェント、エクステンションのそれぞれ |
| 段階 | 部品の組み合わせで決まる、使い方の大きさ。1段階目から4段階目まである（第26条） |
| 統括エージェント | 作業全体の指揮とタスク分担を行う |
| 作業エージェント | 割り当てられた作業を実行する |
| 検証エージェント | 作業成果物を検証する |
| 統合エージェント | 同じ原因の警告の成果物を1つにまとめる |
| Web管理画面 | ローカルWebサーバーが提供する、設定・監視・確認のためのブラウザ画面 |
| PDSサイクル | Plan（計画）– Do（実行）– Study（評価・学習）の反復 |

## 第2章 共通条項

### 第5条 準拠仕様

1. Agent Plugins 1.0.0 と、GitHub Copilot CLI と Claude Code の公式プラグイン仕様に従う。1つのフォルダを、両方のツールのプラグインにする。
2. 仕様が両立しない場合は Agent Plugins 1.0.0 を優先する。Copilot CLI と Claude Code の仕様が両立しないときは、それぞれのツールが読むファイルを分けて両方に従う（分け方は設計書に書き、試験で確かめる）。
3. 技術的な判断は、その時点の最新の公式の情報（公式の仕様、公式ドキュメント、更新履歴、最新の版での実測）にもとづいて行う。古い版や古いモデルの情報を使うときは、版と時点を書き、最新の情報で確かめ直す。
4. スキル・MCP サーバー・エージェントは、Anthropic の公式の指針（Skill authoring best practices、Writing effective tools for agents、Building effective agents）に沿って作る。スキルは skill-creator、MCP サーバーは mcp-builder の手順で作り、試す。

### 第6条 リポジトリの構成

1. リポジトリは、次の4種類の成果物を基本とする。

   | 成果物 | 内容 |
   | --- | --- |
   | 憲章 | プロジェクトが必ず守る最上位ルール |
   | 仕様書 | 実現する機能や振る舞いの要件 |
   | 設計書 | 仕様を実現するための構造・方式 |
   | 実装資産 | プログラムのソースコードとテストコードに加え、`SKILL.md` などのエージェント用定義ファイルを含む |

2. 優先順位は 憲章 ＞ 仕様書 ＞ 設計書 ＞ 実装資産 とし、下位は上位に矛盾しない。
3. 仕様書の要件は、設計書・実装資産・テストまで追跡できるようにする。

### 第7条 開発の進め方

ユーザーと対話しながら、憲章 → 仕様書 → 設計書 → 実装資産 の順に開発・保守する。

### 第8条 SWEBOK

[SWEBOK](https://www.computer.org/education/bodies-of-knowledge/software-engineering) の知識体系・考え方を踏まえて開発する。一律の手順とはせず、対象に適した実践方法を選ぶ。

### 第9条 分かりやすさ

1. 人間に伝える内容と人間が読む成果物は、分かりやすさを何より重視し、簡潔に、伝わる用語で書く。
2. 人間の指摘は、文言をそのまま残さず、目的に沿って直す。

### 第10条 KISS

1. 必要なものだけを、できるだけ単純に作る（KISS：Keep It Simple, Stupid）。
2. リポジトリを肥大化させない。

## 第4章 coverity-triage-kit の条項

### 第19条 マルチエージェント構成

1. 3段階目と4段階目は、統括エージェント1体、作業エージェント1体以上、検証エージェント1体で構成する。同じ原因の警告をまとめるときは、統合エージェントを加える。3段階目では、費用を抑えるため、検証エージェントと統合エージェントを設定で外せる。
2. 作業エージェントは自らの成果物を判定しない。検証エージェントは成果物を修正せず、指摘を統括エージェントに返す。
3. 作業エージェントは、統括エージェントと検証エージェントなしに、単体でも使える（2段階目）。単体で使うときは、第2項にかかわらず、作業エージェントが自分で進め方を決め、作業を終えてよい。

### 第20条 Web管理画面

1. ローカルWebサーバーを起動し、Web管理画面で各種設定を行えるようにする。
2. 既定ではローカルホストからの接続だけを受け付ける。

### 第21条 監視

Web管理画面で、各エージェントの状態・担当タスク・PDS のフェーズを監視でき、実行を停止できるようにする。

### 第22条 結果確認

Web管理画面で、各エージェントの実行結果と検証結果を確認できるようにする。

### 第23条 PDSサイクル

PDS サイクルで成果物と作業の進め方を改善する。

- Plan：統括エージェントが実施内容と評価基準を決める。一括のトリアージでは、一括実行のスクリプトが警告ごとの作業と評価基準（決まった評価基準の一覧）を決め、統括エージェントがそれに従って頼む。
- Do：作業エージェントが計画に沿って試行する。
- Study：検証エージェントが結果を分析し、統括エージェントが次の試行に反映する。

### 第24条 自己改善

1. 実行中にログを残し、実行後にログを振り返って課題を洗い出す。
2. 自身の改善につながる課題を見つけたら、自身の GitHub リポジトリに Issue を起票する。
3. 起票は毎回ユーザーの承認を得てから行う。

### 第25条 部品の独立性

1. 部品は、疎結合で、モジュール強度が高くなるように作る。1つの部品は1つの仕事を受け持つ。
2. どの部品も、その部品のフォルダ（エージェントは定義のファイル）だけを取り出して使える。ほかの部品のファイルを読み込まず、ほかの部品がなくても、その部品の仕事ができる。
3. 下の段階の部品は、上の段階の部品を知らない。上の段階の部品は、下の段階の部品を名前だけで参照し、中身に頼らない。名前を書くのは、部品の表と設定のデータだけにする。
4. 部品どうしは、決まった形のファイルとコマンドと自然な文の頼みだけでやり取りする。この取り決めは設計書に書き、試験で確かめる。
5. 1つの部品の中の決まりは、その部品にだけ書く。2つの部品が同じ取り決めを持つときは、設計書の取り決めとして書き、どちらの写しも試験で一致を確かめる。

### 第26条 4つの段階

1. coverity-triage-kit は、次の4つの段階で使える。どの段階も、上の段階なしで使える。

   | 段階 | 使う部品 | できること |
   | --- | --- | --- |
   | 1 | スキル1つ、または MCP サーバー1つ | 1つの仕事（警告の取得、1件の真偽の調査、修正、逸脱コメントなど） |
   | 2 | 作業エージェントと、その表のスキル | 1件の警告（CID）のトリアージを最後まで |
   | 3 | 統括・作業・検証・統合のエージェントと、スキルと MCP サーバー | 条件に合う警告の一括のトリアージ（Web管理画面なし） |
   | 4 | 3段階目に、エクステンション（Web管理画面）を加える | 画面で設定・監視・結果確認をする使い方 |
