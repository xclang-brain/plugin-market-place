## 判定の細かい基準

| 形 | 判定 | 理由 |
|---|---|---|
| 関数の中だけなら経路が成り立つが、呼び出し元をすべて確かめると、どれも条件を満たさない | `false_positive` | 経路は今のコードでは通らない。「宣言が値を禁じていない」「将来の呼び出し元」は理由にしない |
| 呼び出し元の1つが、条件を満たす値を渡す | `true_bug` | その呼び出し元を根拠に書く |
| Coverity が戻らない関数（独自の abort、無限ループでリセットを待つ関数）を知らず、その後ろを経路にしている | `false_positive` | その関数の中身（戻らないこと）を根拠に書く |
| マクロやビルドの設定で消える・現れるコード（DEADCODE など） | `intentional` | 設定の場所（ヘッダの行、ビルドの設定）を根拠に書く。どの構成でも通らないなら `false_positive` |
| 意図したフォールスルー（コメントや設計の文書がある） | `intentional` | そのコメントの行を根拠に書く |
| 公開の関数で、呼び出し元がリポジトリの外 | 引数の約束（ヘッダのコメント、仕様書）があれば、それで決める（確信度 中）。約束がなければ `undetermined`（確信度 低） | 外の呼び出し元は確かめられない |
| 実行時の値（外から来るデータ、ハードウェアの値、タイミング）だけで決まる | `undetermined` | コードからは決められない。どの値なら問題になるかを書く |
| MISRA・CERT の規則に本当に違反している | `true_bug`（規則の違反として） | 動作のバグでなくても、規則の違反は本物。直すか、正当な理由で逸脱するかは推奨で決める |

## 確信度の理由の書き方

どの基準に当たるかが、読んだ人に分かるように書く。

- 高の例：「警告経路の 3 段階をすべてコードで確かめ、呼び出し元 2 か所（src/a.c:40、src/b.c:77）も NULL を除いていた」
- 中の例：「呼び出し元 4 か所のうち 3 か所は確かめたが、1 か所はコールバックの登録先で、呼ぶ側がリポジトリにない」
- 低の例：「解析したリビジョンが分からず、作業中のファイルでは警告の行がずれていた」「ハードウェアから読む値の範囲がコードから分からない」

だめな例：「十分に確認した」「おそらく問題ない」（どの基準か分からない）。

## 推奨の細かい基準

1. プロジェクトの知識の「推奨の方針」があれば、それに従う（例「MISRA の Advisory の規則は逸脱にする」）。
2. なければ SKILL.md の決め方に従う。迷う形：
   - `false_positive` だが、直すのが1行の防御の確かめで、外から見える動きも変えない → 修正でもよい（コードの意図が分かりやすくなるなら、修正を勧めてよい）。
   - `false_positive` / `intentional` で、問題にならないと言うのに条件が要る（「今の設定のときは」「呼び出し元が増えなければ」）→ 修正。逸脱の案は、言える範囲の理由だけを短く書く。
   - `undetermined` で、直すと動きが変わる（タイミング、外との約束）→ 逸脱（確信度 低）。直しても動きが変わらない防御なら修正。
3. 推奨は判定と食い違わないようにする：`true_bug` で逸脱、`false_positive` / `intentional` で理由なしの修正、にしない。

## 言い切れるかの確かめ方

問題にならない理由を、判定区分で始まる1〜2文（200 字以内）にしてみる。

- 言い切れる例：「誤検知。get_buf() の戻り値は NULL になりうるが、呼び出し元 read_all()（src/io/reader.c:120）で NULL を除いてから渡しているため、NULL を参照することはない。」
- 言い切れない例：「誤検知。今の呼び出し元が NULL を渡さない場合に限り、問題にならない。」（条件がある → 推奨は修正）
- 書かないもの：調べた過程や調べきれなかったこと（調べた経過に書く）、推奨や依頼（「修正を推奨」「確認してください」）。

## 最新のコードとリビジョンのずれ

- 調べるコード（解析したリビジョン）と、直すコード（最新）は別のことがある。行番号がずれるので、関数名とコードの形で同じ場所を探す。
- 最新のコードで、★ の行の問題がもうない（NULL の確かめが入った、後始末が入った）なら、最新で直っている。直した場所（ファイルと行）を書く。
- ずれの確かめ（解析したリビジョンが分からず、作業中のファイルを読んだとき）：
  - 各イベントの説明（「fgets は NULL を返しうる」）が、その行のコードと合うか。
  - スクリプトの `drift_hints`（ファイルがない、行数が足りない、関数が見つからない）。
  - 合わなければ `detected` にして、何がずれているか（「警告の 42 行は今は空行。同じ処理は 47 行にある」）を `detail` に書き、確信度を低にする。
  - 合えば `none`。経路が取れていないなど、確かめきれなければ `unknown`。
- ずれていても、コードを直さない。調べたコードは読むだけ。

## グループのとき

- 同じチェッカーで、同じマクロ・同じ関数・同じ行の警告がまとめて渡されることがある。
- 代表の CID（最初のもの）を手順どおりに調べ、残りの CID が同じ理由（同じ条件、同じ呼び出し元の保証）で同じ判定になるかを、それぞれの行で確かめる。
- 理由が違う、確かめきれない CID は `group_excluded_cids` に入れ、外した理由を調べた経過に書く。全部を外すことはしない（外すなら代表だけを残す）。

## 見立てと調べた経過の書き方

- 見立て（`verdict.summary`）：40 字ほどの1行で、判断の決め手を書く。
  - よい例：「呼び出し元 3 か所すべてで NULL を除いている」「fread が足りないとき fp を閉じずに返す」
  - だめな例：「NULL_RETURNS の警告」「調べた結果、誤検知と判断」（決め手がない）
- 調べた経過（`verdict.rationale`）：経路のどの段階を、どのコードで、どう確かめたかを順に書く。
  - 例：「1. 経路 1（src/a.c:40）で get_buf() が NULL を返しうるのは、size が 0 のとき（src/a.c:31）。2. 呼び出し元は read_all()（src/io/reader.c:118）だけで、size は sizeof(hdr) の定数。3. よって size が 0 になる経路はなく、NULL は返らない。」
  - 知識を使ったら「プロジェクトの知識：panic_stop() は戻らない」のように書き、コードでも確かめたかを添える。

## チェッカーの見方の要点

チェッカーごとの見方の資料が使えないときの要点です（くわしい資料があれば、そちらを読む）。

- NULL_RETURNS / FORWARD_NULL / REVERSE_INULL：呼び出し元の保証、直前の検証、戻らない関数があれば誤検知。REVERSE_INULL は、確かめが要らないのか、参照の前に確かめるべきかを決める。
- RESOURCE_LEAK：所有権が呼び出し元や構造体に移っていれば誤検知。漏れはエラーの経路に多い。直すなら既存の後始末（`goto cleanup` など）に合わせる。
- OVERRUN / BUFFER_SIZE / STRING_OVERFLOW：添字と大きさを定義元までたどる。終端文字の1バイトに注意。
- UNINIT：到達しない分岐や、出力引数で初期化する関数を Coverity が見落とすことがある。
- DEADCODE / UNREACHABLE：構成（マクロ、ビルドの設定）で決まるなら intentional。MISSING_BREAK は、意図したフォールスルーなら intentional。
- MISRA：本当に違反していれば true_bug、規則の対象外なら false_positive、違反だが設計上必要で安全を説明できれば intentional。Mandatory は逸脱できないので修正。Required は正式な逸脱の手続きが要る。Advisory は比較的柔軟。1つのマクロや型定義が原因の大量の違反は、原因の1か所を直す。
- CERT：攻撃者が入力を制御できる経路かが鍵。入力の出どころをたどる。届かなくても規則の違反が残れば、逸脱コメントで説明する。ERR33-C は、無視して問題ない理由を説明できれば逸脱、できなければ修正。
- ほかのチェッカー：Coverity のチェッカーの説明を読み、この手順で調べる。

## 返す前の確かめ

- [ ] 根拠の場所は、すべて自分で読んだ行か（推測の行がないか）
- [ ] パスはリポジトリの一番上からの相対パスか（Coverity の絶対パスのままでないか）
- [ ] 判定は、経路の条件を確かめた結果と合うか（呼び出し元の決まり）
- [ ] 確信度の理由は、どの基準に当たるかが具体的か
- [ ] 推奨は、判定と「言い切れるか」の結果に合うか（知識の推奨の方針があればそれ）
- [ ] 「たぶん」「ふつうは」が残っていないか
- [ ] コードと、頼まれていないファイルを変えていないか

## 調査の例

警告：CID 20001、NULL_RETURNS、src/reader.c の 42 行（read_header()）。経路は「40 行 fgets は NULL を返しうる」→「★ 42 行 NULL を参照」。

1. チェッカーの見方：NULL_RETURNS は、呼び出し元の保証・直前の検証・戻らない関数を見る。
2. 経路を読む：40 行 `line = fgets(buf, sizeof buf, fp);`、42 行 `len = strlen(line);`。間に NULL の確かめはない。
3. 条件：fgets が NULL を返す（ファイルの終わりか読みの失敗）。
4. 確かめ：read_header() の呼び出し元は main()（src/main.c:30）だけで、空のファイルも渡しうる（src/main.c:25 で開いたファイルをそのまま渡す）。空のファイルで fgets は NULL を返す。
5. 判定：true_bug。確信度：高（経路と呼び出し元をすべてコードで確かめた）。推奨：修正。
6. 最新のコード：src/reader.c の同じ場所に確かめはまだない（直っていない）。ずれ：経路の行とコードが合う（none）。

見立て：「空のファイルで fgets が NULL を返し、strlen で落ちる」
