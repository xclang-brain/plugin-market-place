# MISRA C / C++ の観点

MISRA C:2012 を中心に、Coverity の MISRA の警告（`MISRA C-2012 Rule 10.4`、`MISRA C-2012 Directive 4.7`、`MISRA C++-2008 Rule 5-0-4` などの名前）の観点をまとめています。規則の後の（ ）は分類です。「問題の行」は、警告の経路の main のイベントの行です。逸脱コメントの例の名前と場所は例示です。実際に読んだ場所に置き換えます。

## 考え方

- MISRA の違反は、動作のバグではなく、コーディング規則の違反であることが多い。判定は次のように決める。
  - コードが実際に規則に違反していて、違反する設計上の理由がない → `true_bug`（規則の違反として本物）。推奨は、通常は修正。
  - 違反しているが、設計上必要で、安全であることを説明できる → `intentional`（意図的）。推奨は逸脱で、逸脱コメントは「意図的。」で始める。これを「`true_bug` で逸脱」とはしない（`true_bug` で逸脱にするのは、本物の違反を修正しない事情があるとき、つまり「本物のバグ。」のコメントのとき）。
  - 規則の対象外（Coverity の誤認識、例外の条項に該当する、生成されたコードを対象外と決めている）→ `false_positive`。
- 確認方法は、規則の本文と例外の条項を、問題の行の式・型・マクロの展開結果に当てはめること。型は、マクロと型定義（`typedef`）を定義までたどって決める。
- 修正するときは、警告を解消するために別の規則に違反しない（例：キャストを追加して Rule 10.8 や 11.x に違反する）。修正後の式に、同じ規則をもう一度当てはめる。

## 分類と逸脱の扱い

| 分類 | 扱い | 推奨の目安 |
|---|---|---|
| Mandatory（必須） | 逸脱できない | 実際に違反していれば修正を推奨。Coverity の誤認識なら `false_positive` |
| Required（必要） | 逸脱には正式な手続き（理由・影響・承認の記録）が必要 | 小さく安全に修正できれば修正。設計上必要なら `intentional` で逸脱（手続きが必要であることを `summary` に書く） |
| Advisory（推奨） | 比較的柔軟。プロジェクトが「適用しない」と決めることもある（MISRA Compliance:2020） | プロジェクトの方針に従う。方針がなく、修正すると読みにくくなるなら逸脱 |

- プロジェクトが分類を変更している（Advisory を適用しない、Required を Mandatory に引き上げる）ことがある。プロジェクトの知識（`.coverity-triage/knowledge.md`）に書かれていれば、そちらを優先する。
- MISRA C:2012 の Mandatory の主な規則：9.1、12.5、13.6、17.3、17.4、17.6、19.1、21.13、21.17〜21.20、22.2、22.4〜22.6。

## 原因がマクロや型定義にあるとき

- 1つのマクロや型定義が原因で、同じ規則の警告が何十件も検出されることがある（展開された場所ごとに検出される）。警告の `macro` の項目や、問題の行のマクロを確認し、原因が1つかどうかを確認する。
- 原因が1つなら、その定義の1か所を修正するのが最も効果的である（例：`#define MASK 0x0F` を `0x0FU` にする、マクロの引数を括弧で囲む）。
- 定義を変更すると、そのマクロを使うすべての場所の型や値が変わる。使用箇所をすべて検索し、新しい違反（符号付きの文脈で使っていた場所の Rule 10.x など）や動作の変化がないかを確認する。
- 型定義の元の型を変更すると、外部仕様（構造体のサイズ、関数の引数）が変わることが多い。通常は避け、使用箇所で修正するか、逸脱にする。

## 本質的な型のモデル

Rule 10.x は「本質的な型」（essential type）で考える。C の整数拡張（int への変換）を考慮せず、記述されたとおりの型のカテゴリで比較する。

| 本質的な型のカテゴリ | 例 |
|---|---|
| Boolean | `bool`、比較式（`a < b`）、論理式（`a && b`）の結果 |
| character | `char` |
| signed | `signed char`、`short`、`int`、`int32_t` など |
| unsigned | `unsigned char`、`uint16_t`、`size_t` など |
| enum | 名前のある列挙型（名前のない列挙型の定数は signed） |
| floating | `float`、`double` |

- 整数定数の本質的な型は、その値を表現できる最も小さい型である。`5` は signed（signed char）、`5U` は unsigned（unsigned char）、`200` は signed（short）。
- `u8a + u8b`（どちらも uint8_t）の本質的な型は uint8_t のままである。実際の C では int で計算されるので、狭い型ではオーバーフローする計算を広い型に代入する・キャストする箇所が、Rule 10.6〜10.8 の違反になる。
- 本質的な型は、規則を当てはめるための考え方であり、実際の計算は C の規則（整数拡張と通常の算術型変換）で行われる。int より狭い符号なし型（`uint8_t`、int が 32 ビットなら `uint16_t`）は、計算の前に符号付きの int に変換される。そのため、規則に合わせて定数に `U` を付けると、計算の型が int から unsigned int に変わり、動作が変わることがある（[Rule 10.4](#rule-104) の「`U` を付けて修正するときの注意」）。

## Rule 10.1

- **要求**（Required）：演算子のオペランドに、不適切な本質的な型を使わない。
- **よくある違反**：符号付きの値のビット演算・シフト（`s16 << 2`、`s & 0x0F`）、Boolean の算術演算（`flag + 1`）、Boolean でない値への `!`・`&&`・`||`（`!count`）、符号なしの値への単項の `-`、列挙型の算術演算。
- **修正**：ビット演算は符号なしの型で行う（`(uint16_t)s16 << 2U` とするより、元の変数の型を見直す）。`!count` は `count == 0U` にする。
- **判定**：実際に該当すれば `true_bug`（規則の違反）。修正が小さく安全なら、修正を推奨する。

## Rule 10.3

- **要求**（Required）：式の値を、より狭い本質的な型の変数や、別のカテゴリの変数に代入しない。代入のほか、関数の引数、戻り値、初期化も対象である。
- **よくある違反**：`uint8_t x = u16;`（狭い型への代入）、`int32_t s = u32;`（カテゴリが異なる）、`bool b = 1;`、`return -1;`（戻り値の型が符号なし）。
- **例外**：負でない整数の定数式で、その値を代入先の型で表現できるもの（`uint8_t x = 5;`）は許される。
- **修正**：範囲を確認したうえで、明示的にキャストする（`x = (uint8_t)u16;`）。または、変数や戻り値の型を合わせる（外部仕様の変更になるなら避ける）。
- **判定**：値が切り捨てられる・符号が変わるケースが実際にあるなら、規則の違反に加えて動作のバグでもある（確信度を上げられる根拠を探す）。

## Rule 10.4

- **要求**（Required）：通常の算術型変換が行われる演算子では、両方のオペランドを同じ本質的な型のカテゴリにする。対象の演算子は、二項の `+ - * / % & | ^`、比較の `< > <= >= == !=`、条件演算子 `?:` の第2・第3オペランド、複合代入（`+=` など）である。シフトは対象外（Rule 10.1 で確認する）。
- **よくある違反と修正**：

  | 違反 | 理由 | 修正 |
  |---|---|---|
  | `if (count > 0)`（count は uint16_t） | 符号なしと、符号付きの定数 `0` | `count > 0U` |
  | `s32 + u32` | signed と unsigned | 一方の型に合わせる。キャストはオペランドに付ける（`s32 + (int32_t)u32`。値の範囲を確認する） |
  | `mode == 1`（mode は名前のある列挙型） | enum と signed | 列挙定数と比較する（`mode == MODE_RUN`） |
  | `temp > 0`（temp は float） | floating と signed | `temp > 0.0F` |
  | `flag ? u8 : 0` | unsigned と signed | `flag ? u8 : 0U`（結果の型が変わる。下の注意を参照） |

- **例外**：文字型と、符号付き・符号なしの整数の加算（`'0' + n`、`+=` も）、および文字型から符号付き・符号なしの整数を引く減算（左が文字型の `c - n`、`-=` も）は許される。
- **確認方法**：両方のオペランドの型を、マクロと型定義を定義までたどって決める（マクロの定数に `U` が付いているか、型定義が符号付きか）。
- **誤検知になりやすいパターン**：Coverity が型定義やマクロの展開を誤認識している。両方とも、実際は同じカテゴリである（同じ型定義を経由している）。
- **`U` を付けて修正するときの注意**：修正する前に、相手のオペランドの C での型（整数拡張の後の型）を確認する。`U` を付けると、相手が int のままのときは、計算が unsigned int で行われるようになる。
  - 動作は変わらない（機械的に修正してよい）：相手が符号なし型の単一の変数で、比較演算子（`count > 0U`、`u8 == 5U`）のとき（相手が符号付きの変数のときに `U` を付けると、負の値で動作が変わる）。相手がもともと unsigned int 以上の符号なし型（int が 32 ビットのときの `uint32_t`、`size_t`、`unsigned long`）のとき（定数は以前から符号なしに変換されている）。浮動小数点の相手と比較する定数に `.0F` を付けるとき。
  - 動作が変わることがある（1件ずつ確認する）：条件演算子 `?:` で、もう一方が int より狭い符号なし型のとき。`flag ? u8 : 0` の結果は int だが、`flag ? u8 : 0U` の結果は unsigned int になる（u8 は int に整数拡張され、0U と合わせて unsigned int になる）。`?:` の値をそのまま代入するだけなら同じだが、周囲の式で差が生じる（`(flag ? u8 : 0) - 1 < 0` は flag が 0 のとき真、`0U` にすると偽）。`?:` を使う式の全体を確認する。
  - 動作が変わることがある（1件ずつ確認する）：相手が、int より狭い符号なし型の**演算式**で、値が負になりうるとき（`a - b`、`-a`、`~a`）。例：`uint16_t a = 1, b = 2;` のとき、`(a - b) > 0` は偽（int の -1 と比較する）だが、`(a - b) > 0U` は真（-1 が unsigned int の最大値になる）。`u8 - 1` と `u8 - 1U` も、`u8` が 0 なら -1 と最大値に分かれ、比較・除算・右シフト・広い型への代入で差が生じる。
  - 動作が変わるときは、書いた人の意図に合う形に書き直す（`(a - b) > 0` が「a が b より大きい」の意味なら `a > b`）。意図をコードから判断できなければ、機械的に修正せず、確信度を下げて `summary` に書く。
  - int が 16 ビットの処理系では、`uint16_t` は unsigned int に整数拡張されるので、動作が変わる式が異なる。対象の処理系の int のビット幅を確認する。
- **判定の目安**：実際にカテゴリが異なれば `true_bug`（規則の違反）。上の注意で動作が変わらないと確認できた形は、`U` を付けるような小さく安全な修正を推奨する。動作が変わる形は、意図に合う書き直しを修正コードにする。同じマクロが原因で大量に検出されていれば、マクロの定義を修正する（使用箇所の式ごとに、上の注意を当てはめる）。設計上どうしても混在させる必要があり、値の範囲で安全であることを説明できるなら `intentional`（意図的。推奨は逸脱で、Required なので正式な手続きが必要）。Coverity が型を誤認識しているなら `false_positive`。

## Rule 10.6・10.7・10.8

- **要求**（Required）：
  - 10.6：複合式（`a * b` などの演算の結果）を、より広い本質的な型の変数に代入しない（`uint32_t r = u16a * u16b;`）。
  - 10.7：複合式と、より広い型のオペランドを組み合わせない（`u32 + (u16a * u16b)`）。
  - 10.8：複合式を、別のカテゴリや、より広い型にキャストしない（`(uint32_t)(u16a + u16b)`）。
- **理由**：書いた人は広い型で計算するつもりでも、計算は狭い型（int が 16 ビットの処理系では実際に 16 ビット）で行われ、オーバーフローすることがある。
- **修正**：キャストを、計算の前のオペランドに付ける（`(uint32_t)u16a * u16b`）。
- **判定**：オーバーフローする値の範囲が実際にありうるなら、規則の違反に加えて動作のバグでもある。範囲から決してオーバーフローしないと言えても、規則の違反は残る（修正が小さいので、修正を推奨しやすい）。

## Directive 4

| 規則（分類） | 要求 | 観点 |
|---|---|---|
| Dir 4.1（Required） | 実行時の失敗（オーバーフロー、ゼロ除算、範囲外アクセス）を最小限にする | 内容は標準チェッカーと同じ観点で確認する（OVERRUN、DIVIDE_BY_ZERO など） |
| Dir 4.6（Advisory） | 基本型（`int`）の代わりに、サイズと符号が分かる型定義（`int32_t`）を使う | 外部から見える関数の型を変えるのは、外部仕様の変更になる。内部の変数だけなら修正できる |
| Dir 4.7（Required） | エラーを返す関数の戻り値をチェックする | CHECKED_RETURN と同じ観点 |
| Dir 4.9（Advisory） | 関数形式マクロより関数を使う | 逸脱になりやすい（型に依存しない処理、速度） |
| Dir 4.10（Required） | ヘッダーに多重インクルードの防止（インクルードガード）を付ける | 追加するだけで修正できる |
| Dir 4.12（Required） | 動的なメモリ確保を使わない | 起動時だけの確保などは逸脱。置き換えは大きな変更（最小の変更の範囲を超える） |
| Dir 4.14（Required） | 外部から入力された値を、検証してから使う | TAINTED_SCALAR と同じ観点 |

Directive は、Coverity が近似的に判定するので、誤検知の可能性を丁寧に確認する。

## Rule 2

- 2.1（Required）到達しないコードを置かない。2.2（Required）意味のない処理（dead code。実行されるが結果に影響しない処理）を置かない。2.3〜2.6（Advisory）使用しない型・タグ・マクロ・ラベルの宣言。2.7（Advisory）使用しない引数。
- 2.1 は UNREACHABLE に対応する。2.2 は「実行されても結果が変わらない式」（NO_EFFECT に近い）であり、Coverity の DEADCODE とは意味が少し異なる。
- 2.7 は、コールバックなど、引数の形が決まっている関数に多い。`(void)param;` で使用しないことを示すのが、よくある修正である。周囲にその書き方がなければ逸脱。
- ビルド構成（`#if`）によって使用する・しないが変わるものは `intentional`。

## Rule 8

- 8.2（Required）引数のない関数は `void f(void)` と書く。8.3（Required）宣言と定義で、引数の名前と修飾子を同じにする。8.4（Required）外部リンケージを持つ定義の前に、その宣言（自身のヘッダー）が見えるようにする。8.5（Required）外部宣言は、1つのヘッダーに1回だけ書く。8.6（Required）外部定義は1つだけにする。
- 8.7（Advisory）1つのファイルでしか使わない関数・変数は `static` にする。公開ヘッダーに宣言があるもの、ライブラリとして外部から使うものを `static` にするのは、外部仕様の変更になる。
- 8.9（Advisory）1つの関数でしか使わない変数は、その関数の中で定義する。8.13（Advisory）書き換えないポインタの引数には `const` を付ける（公開関数のシグネチャが変わるので、外部仕様の変更になるかを確認する）。
- 宣言と定義を一致させる修正は、ほとんどの場合、小さく安全である。

## Rule 11

| 規則（分類） | 要求 | 観点 |
|---|---|---|
| 11.1（Required） | 関数へのポインタを、ほかの型と相互に変換しない | 割り込みテーブルなどで必要なら逸脱 |
| 11.3（Required） | 別の型のオブジェクトへのポインタにキャストしない（`(uint32_t *)bytes`） | アライメントとエイリアシングの規則によって、実際に不正な動作になることがある。`memcpy` でコピーする修正がある。char へのポインタへの変換は例外 |
| 11.4（Advisory） | ポインタと整数を相互に変換しない | レジスタのアドレス（`(volatile uint32_t *)0x40021000U`）は逸脱になりやすい（`intentional`） |
| 11.5（Advisory） | `void *` から、オブジェクトへのポインタに変換しない | メモリ確保やコールバックの文脈で必要なら逸脱 |
| 11.6（Required） | `void *` と算術型を相互に変換しない | |
| 11.8（Required） | キャストで `const` / `volatile` を外さない | 呼び出す関数の引数に `const` がないことが原因なら、その関数のシグネチャの変更（外部仕様の変更）になるかを確認する |
| 11.9（Required） | NULL ポインタ定数には `NULL` だけを使う（`p = 0` は違反） | `NULL` に置き換えるだけで修正できる |

## Rule 12

- 12.1（Advisory）演算子の優先順位を括弧で明示する（`a + b << 2` → `(a + b) << 2`）。修正は小さく安全である。
- 12.2（Required）シフト量は、0 から、左オペランドの型のビット幅 - 1 までにする。シフト量の範囲を出所までたどる（BAD_SHIFT と同じ）。
- 12.3（Advisory）カンマ演算子を使わない。12.4（Advisory）定数式で、符号なしのラップアラウンドを起こさない（`0U - 1U`）。12.5（Mandatory）配列として宣言した引数に `sizeof` を使わない（ポインタのサイズになる）。

## Rule 13

- 13.2（Required）評価順序によって結果が変わる式を書かない（`a[i] = i++;`、1つの式で同じ `volatile` を2回読む `REG + REG`）。文を分ける。
- 13.3（Advisory）`++` / `--` を含む式に、ほかの副作用を入れない（`x = a[i++];`）。13.4（Advisory）代入式の結果を使わない（`if ((p = get()) != NULL)`）。どちらも、文を分けて修正する。
- 13.5（Required）`&&` / `||` の右オペランドに、持続する副作用（関数呼び出しで状態を変えるもの）を置かない。右オペランドは評価されないことがあるためである。
- 13.1（Required）初期化子リストに副作用を置かない。13.6（Mandatory）`sizeof` のオペランドに副作用を置かない。

## Rule 14

- 14.1（Required）ループカウンタに浮動小数点型を使わない。14.2（Required）`for` ループを適格な形にする（ループカウンタを本体で書き換えない）。
- 14.3（Required）制御式が不変（常に同じ値）にならないようにする。例外：無限ループ（`for (;;)`、`while (1)`）と、マクロの `do { } while (0)`。
  - ビルド構成のマクロで値が決まる（`if (DEBUG_LEVEL > 2)`）→ `intentional`（逸脱）が多い。
  - 型によって常に同じ値になる（`if (u8 >= 0U)`）→ 記述ミスなら `true_bug`。
- 14.4（Required）`if`・`while` などの制御式は Boolean にする。`if (p)` → `if (p != NULL)`、`if (flags & BIT)` → `if ((flags & BIT) != 0U)`、`while (n--)` → 比較の形に書き直す。修正は小さく安全である。

## Rule 15

- 15.1（Advisory）`goto` を使わない。15.2・15.3（Required）`goto` の飛び先は、同じ関数の中で `goto` より後（下の行）に宣言された、同じブロックか外側のブロックのラベルにする。エラー時の後処理の `goto cleanup` は 15.2・15.3 を満たす。15.1 は、プロジェクトで逸脱していることが多い。
- 15.4（Advisory）ループを終了する `break` / `goto` は1つまでにする。
- 15.5（Advisory）関数の出口は、末尾の1つだけにする。途中の `return` は、既存の書き方に合わせる。プロジェクトで適用しないと決めていることが多く、逸脱になりやすい。修正で出口を増やすときも、周囲の書き方に合わせる。
- 15.6（Required）`if`・`for`・`while` などの本体は `{ }` で囲む。追加するだけで修正できる。
- 15.7（Required）`if … else if` は `else` で終える。何もしないなら、`else { /* 何もしない理由 */ }` を追加する。

## Rule 16

- 16.1（Required）`switch` 文を適格な形にする。16.2（Required）`case` ラベルは、`switch` の最も外側のブロックに置く。
- 16.3（Required）空でない `case` は、無条件の `break` で終える。空の `case` を並べることは許される。意図したフォールスルーも違反なので、修正する（処理を分ける）か、逸脱の手続きを行う。
- 16.4（Required）`default` を置く（`default: break;` と、何もしない理由のコメント）。16.5（Required）`default` は最初か最後に置く。16.6（Required）`case` を2つ以上にする。16.7（Required）`switch` の式を Boolean にしない。

## Rule 17

- 17.1（Required）`<stdarg.h>` を使わない。printf 形式のログ関数は逸脱になりやすい。
- 17.2（Required）関数を再帰呼び出ししない。深さに上限があることを説明できれば逸脱、できなければ修正（ループに書き換える。変更が大きいなら、最小の変更の範囲を超える）。
- 17.3（Mandatory）宣言のない関数を呼び出さない（ヘッダーをインクルードする）。17.4（Mandatory）値を返す関数は、すべての出口で値を返す。
- 17.7（Required）値を返す関数の戻り値を使用する。使用しないなら、`(void)memcpy(...)` のように `(void)` で破棄を明示する。戻り値がエラーを示すなら、破棄せずにチェックする（Dir 4.7、CERT ERR33-C）。
- 17.8（Advisory）関数の引数を書き換えない。ローカル変数にコピーして使う。

## Rule 18

- 18.1（Required）ポインタ演算の結果は、同じ配列の要素を指すようにする（OVERRUN と同じ観点）。18.2・18.3（Required）ポインタの減算・比較は、同じ配列の中だけで行う。
- 18.4（Advisory）ポインタに `+`・`-`・`+=`・`-=` を使わない。添字（`p[i]`）に書き直して修正する。
- 18.5（Advisory）ポインタの入れ子は2段までにする。18.6（Required）自動変数のアドレスを、その変数より寿命の長い場所に格納しない（RETURN_LOCAL と同じ）。18.7（Required）フレキシブル配列メンバを使わない。18.8（Required）可変長配列を使わない。

## Rule 20

- 20.1（Advisory）`#include` の前に、プリプロセッサ指令とコメント以外を置かない。20.4（Required）キーワードと同じ名前のマクロを定義しない。20.5（Advisory）`#undef` を使わない。
- 20.7（Required）マクロの引数を展開する式は、括弧で囲む（`#define SQ(x) ((x) * (x))`）。マクロの定義の1か所を修正すれば、展開された場所の警告がすべて解消される。
- 20.9（Required）`#if` で使う識別子は、定義しておく（未定義の識別子は 0 として扱われ、記述ミスに気づけない）。`defined()` で確認するか、既定値を定義する。
- 20.10（Advisory）`#` と `##` を使わない。

## Rule 21 と 22

| 規則（分類） | 要求 | 観点 |
|---|---|---|
| 21.1・21.2（Required） | 予約済みの識別子（`_` と大文字、`__` で始まる名前）を定義しない | インクルードガードの `__FOO_H` が多い。名前の変更は小さく安全である |
| 21.3（Required） | `malloc` / `free` などを使わない | Dir 4.12 と同じ。起動時だけの確保は逸脱、置き換えは大きな変更 |
| 21.6（Required） | 標準入出力（`printf` など）を使わない | デバッグのビルド構成だけで使うなら逸脱 |
| 21.7（Required） | `atoi`・`atol`・`atof` を使わない | `strtol` などと、エラーのチェックに置き換える |
| 21.8（Required） | `abort`・`exit` など、プログラムを終了させる関数を使わない（バージョンによっては `getenv`・`system` も） | 終了処理の設計を確認する |
| 21.10（Required） | `<time.h>` を使わない | |
| 21.15・21.16（Required） | `memcpy`・`memcmp` などの引数の型を合わせる | |
| 21.17・21.18（Mandatory） | `<string.h>` の関数で範囲外にアクセスしない。サイズの引数を正しくする | OVERRUN・BUFFER_SIZE と同じ観点。逸脱できない |

## そのほかの規則

- 5.x（識別子の重複）：別の場所の識別子と区別できる名前にする（5.1〜5.9）。外部から見える名前の変更は、外部仕様の変更になる。
- 7.1（Required）8進定数を使わない（`010` は 8）。7.2（Required）符号なしの型で表現する整数定数には `U` を付ける。7.3（Required）`l` の接尾辞は大文字の `L` にする。7.4（Required）文字列リテラルは `const char *` に代入する。
- 9.1（Mandatory）値を代入する前の自動変数を読まない（UNINIT と同じ観点）。9.2〜9.5（Required）初期化子の形式。
- 19.1（Mandatory）領域が重なるオブジェクトへの代入をしない。19.2（Advisory）`union` を使わない（通信データの解釈などは逸脱になりやすい）。

## MISRA C++ の補足

- 名前は `MISRA C++-2008 Rule 5-0-4` のような形である（2008 年版の分類は Required・Advisory・Document、2023 年版は Mandatory・Required・Advisory）。分類の扱いは、MISRA C と同じように考える。
- 2008 年版の 5-0-x（暗黙の変換、「基底型」underlying type）は、MISRA C の Rule 10.x の本質的な型と同じ考え方である（5-0-4 は、符号が変わる暗黙の変換）。
- 6-4-x（`switch` の形式。6-4-5 はフォールスルー）は Rule 16.x、0-1-x（到達しない・使用しないコード）は Rule 2.x、15-x（例外）は UNCAUGHT_EXCEPT と同じ観点で確認する。
- C++ では、修正に言語機能（`static_cast`、`constexpr`、`enum class`）を使うことが多い。周囲のコードの書き方と、使用する C++ のバージョンに合わせる。

## 逸脱コメントの例

- 実際に違反しているが設計上必要なもの（`intentional`）は「意図的。」で始め、違反が必要な理由と、安全である理由を、条件を付けずに書く。
  - 「意図的。UART0_DR のレジスタ（0x4000C000、include/regs.h:30）を読み書きするために整数をポインタに変換しており、アドレスは機種の仕様で決まっている。」
  - 「意図的。LOG_LEVEL は製品のビルド構成で 0、デバッグのビルド構成で 3 になり（include/config.h:12）、この条件はビルド構成によって変わる。」
- Coverity の誤認識（`false_positive`）は「誤検知。」で始め、規則の対象にならない理由を書く。
  - 「誤検知。count と比較する LIMIT は 10U（include/limits.h:8）で、両方とも符号なしのため、Rule 10.4 の対象ではない。」
- 逸脱の記録の番号を書くプロジェクトでは、プロジェクトの知識（`.coverity-triage/knowledge.md`）の書き方に従う。
- Mandatory の規則は逸脱できないので、実際に違反していれば、逸脱コメントで済ませない（推奨は修正）。
