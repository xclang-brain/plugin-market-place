# 標準チェッカーの観点

Coverity の標準チェッカー（MISRA・CERT 以外）について、チェッカーごとに、指摘の内容、誤検知になりやすいパターン、確認方法、典型的な修正、逸脱コメントの例、判定の目安をまとめています。逸脱コメントの例の関数名と場所は例示です。実際に読んだ場所に置き換えます。

## 経路の読み方

- 警告の経路のイベントは、Coverity が解析でたどった実行経路です。`cond_true` / `cond_false` は、その分岐を通ったこと（条件が真・偽）を示します。main のイベントの行が、問題の起きる場所（以下「問題の行」）です。
- Coverity が認識できないことが多いもの：戻らない関数、別の関数で実施済みの検証、出力引数による初期化、マクロやビルド設定で無効になるコード、所有権の移動（戻り値で返す、構造体に格納する）、ループ回数の上限。
- 誤検知かどうかは、問題の行に至る条件が、現在のコード（すべての呼び出し元）で成立するかで決めます。関数の中だけで成立することは、本物のバグの理由になりません。

## NULL_RETURNS

- **指摘**：NULL を返すことがある関数の戻り値を、チェックせずに参照している。Coverity は、ほかの場所でその戻り値をチェックしている割合（「checked 5 out of 6 times」など）も判断に使う。経路によく現れるタグは `returned_null`・`var_assigned`・`dereference`。
- **誤検知になりやすいパターン**：
  - その引数（定数のキー、固定のテーブルにある名前）では NULL を返さない。
  - 呼び出し元や直前の処理が、NULL にならないことを保証している（同じ値を別の関数で検証済み）。
  - NULL のときは、戻らない関数（独自の abort、無限ループでリセットを待つ関数）で停止する。
- **確認方法**：関数の実装を読み、どの引数・状態で NULL を返すかを確認する。その条件がこの呼び出しで成立するかを、引数の出所までたどる。
- **典型的な修正**：参照の前に `!= NULL` でチェックし、周囲と同じ方法でエラーを返す（エラーコード、`goto cleanup`）。
- **逸脱コメントの例**：「誤検知。find_param() はテーブルにある名前では NULL を返さず、"uart.baud" は必ずテーブルにある（src/param.c:40）ため、NULL を参照することはない。」
- **判定の目安**：NULL になる条件が現在の呼び出しで成立すれば `true_bug`。成立しなければ `false_positive`。外部のデータ（ファイル、通信、メモリ不足）で決まるなら、それが起こりうるかで決める（malloc の失敗は、組み込み機器でも起こりうるものとして扱う）。

## FORWARD_NULL

- **指摘**：ポインタを NULL と比較した（または NULL を代入した）後、NULL の可能性がある経路でそのポインタを参照している。タグは `var_compare_op`・`assign_zero`・`var_deref_op`・`var_deref_model`（関数に渡し、その中で参照）。
- **誤検知になりやすいパターン**：
  - NULL と比較した分岐で、戻らない関数を呼ぶ（Coverity がそれを認識していない）。
  - 比較は防御的なチェックで、呼び出し元はすべて NULL でない値を渡す。
  - 比較の後、別の変数の条件によって、参照する分岐に入らないことが決まっている（Coverity は変数間の関係を認識できないことがある）。
- **確認方法**：NULL と比較した分岐から参照の行まで、どの分岐を通るかをたどる。呼び出し元が NULL を渡しうるかを、すべての呼び出し元で確認する。
- **典型的な修正**：NULL の分岐で、周囲と同じ形で関数から戻る（エラーコードを返す）。比較が不要なときも、比較を削除するのではなく、参照の前にチェックをそろえる。
- **逸脱コメントの例**：「誤検知。p が NULL のときは panic_stop()（src/panic.c:9）で停止して戻らないため、src/uart.c:52 で NULL を参照することはない。」
- **判定の目安**：NULL のまま参照の行に到達する呼び出し元・分岐があれば `true_bug`。どの呼び出し元からも到達しなければ `false_positive`。

## REVERSE_INULL

- **指摘**：ポインタを参照した後で、NULL かどうかをチェックしている（チェックが遅い、または不要）。タグは `deref_ptr`・`check_after_deref`。
- **誤検知になりやすいパターン**：参照の前に、別の形（呼び出し元、別の変数）で NULL でないことが決まっていて、後のチェックは防御的なもの。
- **確認方法**：参照の行より前に、NULL でないことが保証されているかを、呼び出し元までたどる。保証がなければ、参照の行で先に異常終了する。
- **典型的な修正**：チェックを参照の前に移動する。保証があるなら、不要なチェックを削除する（削除すると MISRA の防御的プログラミングの規則に抵触するプロジェクトでは、前に移動する方を選ぶ）。
- **逸脱コメントの例**：「誤検知。dev は呼び出し元 open_all()（src/dev.c:52）で NULL を除外してから渡すため、src/dev.c:80 のチェックは冗長であり、NULL を参照することはない。」
- **判定の目安**：参照の前に NULL でない保証がなければ `true_bug`（先に参照して異常終了する）。保証があれば `false_positive`（後のチェックが冗長なだけ）。

## RESOURCE_LEAK

- **指摘**：確保したメモリ、開いたファイル、ソケットなどを、解放せずに失っている（変数がスコープを抜ける、上書きされる）。タグは `alloc_fn`・`var_assign`・`leaked_storage`・`leaked_handle`。
- **誤検知になりやすいパターン**：所有権が移動している（戻り値で返す、構造体のメンバやグローバルのテーブルに格納する、登録用の関数に渡す）。独自の確保・解放の関数を Coverity が認識していない。
- **確認方法**：確保した値が、どの経路で解放され、どこに渡されるかをたどる。リークは途中の `return`（エラーの経路）に多い。渡した先の関数が保持するか（後で解放するか）を、その関数の実装で確認する。
- **典型的な修正**：周囲の後処理の書き方に合わせる（関数に `goto cleanup` があればそこへ飛ぶ。なければ、その `return` の前で解放する）。解放の戻り値の扱い（`(void)fclose(fp);` など）も周囲に合わせる。
- **逸脱コメントの例**：「誤検知。buf は session_add()（src/session.c:61）でテーブルに格納され、session_close()（src/session.c:95）で解放されるため、リークすることはない。」
- **判定の目安**：解放も所有権の移動もない経路があれば `true_bug`（1回しか通らない起動時の処理でも、規則の違反としては本物）。所有権が移動していれば `false_positive`。プログラムの終了まで保持する設計（終了時に OS が回収する）なら `intentional`。

## USE_AFTER_FREE

- **指摘**：解放したメモリを、その後で参照したり、関数に渡したりしている。タグは `freed_arg`・`deref_after_free`・`pass_freed_arg`。
- **誤検知になりやすいパターン**：解放と参照が別の分岐にあり、同じ実行では両方を通らない。解放の関数が条件によっては解放しない（参照カウントが残るときなど）のに、Coverity が常に解放すると見なしている。
- **確認方法**：解放の行から参照の行まで、通る分岐の条件をたどる。解放の関数の実装（実際に解放する条件）を読む。
- **典型的な修正**：参照を解放の前に移動する。解放の直後にポインタへ NULL を代入し、後の参照でチェックする（周囲にその書き方があるとき）。
- **逸脱コメントの例**：「誤検知。obj_put()（src/obj.c:30）は参照カウントが 0 のときだけ解放し、ここでは呼び出し元が参照を保持している（src/obj.c:72）ため、解放後に参照することはない。」
- **判定の目安**：解放の後に参照する経路があれば `true_bug`（実行されると異常な動作になることが多いので、確信度が高ければ修正を強く推奨する）。

## DOUBLE_FREE

- **指摘**：同じメモリを2回解放している。タグは `freed_arg`・`double_free`。
- **誤検知になりやすいパターン**：1回目と2回目が別の分岐にある。1回目の後にポインタへ NULL を代入していて、2回目は NULL の解放（何もしない）になる。
- **確認方法**：1回目の解放から2回目までの分岐の条件と、ポインタへの代入をたどる。エラーの経路で、呼び出し元と呼び出された側の両方が解放していないかを確認する。
- **典型的な修正**：解放の責任を一方にまとめる。解放の後に NULL を代入する。
- **逸脱コメントの例**：「誤検知。src/cache.c:44 で解放した後に ptr へ NULL を代入しており、src/cache.c:58 の free() には NULL が渡るだけで、2回解放することはない。」
- **判定の目安**：2回とも実際に解放する経路があれば `true_bug`。

## OVERRUN

- **指摘**：配列やバッファの範囲外を読み書きしている（添字がサイズ以上、コピーの長さがサイズを超える）。タグは `overrun-local`・`overrun-buffer-arg`・`overrun-buffer-val` など。
- **誤検知になりやすいパターン**：添字の値の範囲が、呼び出し元か直前のチェックによって、サイズより小さいと決まっている（Coverity は、ループや別の関数でのチェックを追跡しきれないことがある）。
- **確認方法**：添字・長さの値を、定義（マクロ、型のサイズ）と呼び出し元までたどり、とりうる最大値を求める。終端文字の1バイト（`'\0'`）を含めて足りるかに注意する。サイズのマクロが1つのときは、そのマクロを使うすべての場所で同じ問題が起きていないかも確認する。
- **典型的な修正**：根本原因（サイズのマクロの定義の誤り、終端の1バイトの加算漏れ）を1か所で修正する。根本原因を修正できないときは、使用する場所で範囲をチェックする。
- **逸脱コメントの例**：「誤検知。idx は parse_cmd()（src/cmd.c:20）で 0〜CMD_MAX-1 に制限してから渡すため、cmd_table の範囲（src/cmd.c:8）を超えることはない。」
- **判定の目安**：範囲を超える値が到達する経路があれば `true_bug`。外部から入力される長さ（通信、ファイル）が到達するなら、その長さのチェックがあるかで決める。

## BUFFER_SIZE

- **指摘**：コピーの関数（`memcpy`・`strncpy` など）に渡したサイズが、書き込み先より大きい。または、`strncpy` に渡したサイズが書き込み先と同じで、終端の `'\0'` が書き込まれないことがある（BUFFER_SIZE_WARNING として検出されることもある）。
- **誤検知になりやすいパターン**：書き込みの後で、別の行が必ず終端を書き込んでいる。コピー元の文字列の長さが、サイズより短いと決まっている。
- **確認方法**：書き込み先のサイズ（定義）と、渡したサイズ・コピー元の長さをたどる。コピーの後に終端を書き込む行があるかを確認する。
- **典型的な修正**：サイズを `sizeof(dst) - 1U` にして終端を書き込む。または、周囲で使用している安全なコピーの関数に合わせる。
- **逸脱コメントの例**：「誤検知。src/name.c:31 の strncpy() の直後に、src/name.c:32 で必ず name[NAME_LEN - 1] に終端を書き込むため、終端のない文字列になることはない。」
- **判定の目安**：終端がないまま文字列として使用する経路、またはサイズを超えて書き込む経路があれば `true_bug`。

## STRING_OVERFLOW

- **指摘**：`strcpy`・`strcat`・`sprintf` などで、文字列を固定サイズのバッファに書き込むとき、収まらないことがある。
- **誤検知になりやすいパターン**：コピー元の文字列が定数か、長さをチェック済みの値で、終端まで含めて収まる。
- **確認方法**：コピー元の文字列の最大の長さ（定数の長さ、チェック済みの長さ）と、書き込み先のサイズを比較する。`sprintf` は書式から最大の長さを求める（`%d` は符号を含めて 11 文字など）。
- **典型的な修正**：長さを渡す関数（`snprintf` など）に置き換え、切り詰められたときの扱いを周囲に合わせる。MISRA の Rule 21.6（標準入出力の関数）で使用できないプロジェクトでは、プロジェクトの関数に合わせる。
- **逸脱コメントの例**：「誤検知。ver は "v" と 3 桁までの数（src/ver.c:12 で 999 以下に制限）で、終端を含めて 5 文字に収まり、buf[8]（src/ver.c:20）を超えることはない。」
- **判定の目安**：収まらない長さが到達する経路があれば `true_bug`。

## SIZEOF_MISMATCH

- **指摘**：`sizeof` の使い方が対象と合っていない（`malloc(sizeof(p))` のようにポインタのサイズを取っている、`memset(&s, 0, sizeof(other))` のように別の型のサイズを使っている）。
- **誤検知になりやすいパターン**：実際にポインタのサイズが必要である（ポインタの配列を作る）。同じサイズになるように定義した型どうしである。
- **確認方法**：確保・コピーする対象の型と、`sizeof` の中の型・式を比較する。
- **典型的な修正**：`sizeof(*p)` や `sizeof(s)` のように、対象そのものからサイズを取る。
- **逸脱コメントの例**：「意図的。table はポインタの配列で、要素ごとに sizeof(char *) を確保する設計（src/tbl.c:15）であり、サイズの取り違えではない。」
- **判定の目安**：確保・コピーのサイズが対象より小さくなるなら `true_bug`。意図したサイズなら `intentional`。

## UNINIT

- **指摘**：値を代入する前の変数（または構造体のメンバ）を読んでいる。タグは `var_decl`・`uninit_use`・`uninit_use_in_call`。
- **誤検知になりやすいパターン**：
  - 値を代入しない分岐は、実際には通らない（前の条件で決まっている）。
  - 出力引数に値を書き込む関数（`get_value(&v)`）を Coverity が認識していない。または、失敗のときも書き込むことを認識していない。
- **確認方法**：宣言から使用する行まで、すべての分岐で値が代入されるかを確認する。出力引数の関数の実装で、すべての戻り方で値を書き込むかを確認する。
- **典型的な修正**：宣言で初期化する（`int v = 0;`）。周囲が宣言で初期化しない書き方なら、値を代入しない分岐で代入する。
- **逸脱コメントの例**：「誤検知。read_reg()（src/hal.c:40）はすべての戻り方で *val に値を書き込むため、src/hal.c:88 で未初期化の v を読むことはない。」
- **判定の目安**：値が代入されない分岐を通って読む経路があれば `true_bug`（MISRA C:2012 の Rule 9.1 は Mandatory）。

## NEGATIVE_RETURNS

- **指摘**：負の値（エラーを示す -1 など）を返すことがある関数の戻り値を、チェックせずに、負であってはならない場所（添字、サイズ、`read` の長さ）に使用している。
- **誤検知になりやすいパターン**：この引数では負の値を返さない（固定の値、事前にチェックした値）。
- **確認方法**：関数が負の値を返す条件を実装で確認し、この呼び出しで成立するかをたどる。
- **典型的な修正**：使用する前に `< 0` をチェックし、周囲と同じ方法でエラーを返す。
- **逸脱コメントの例**：「誤検知。find_slot() は空きがないときだけ -1 を返し、呼び出し元 init()（src/slot.c:70）は空きを確認してから呼ぶため、負の添字になることはない。」
- **判定の目安**：負の値が到達する経路があれば `true_bug`。

## INTEGER_OVERFLOW

- **指摘**：整数の演算がオーバーフローし、その値をサイズ・添字・確保する長さなどに使用している（外部から入力された値の演算に多い）。
- **誤検知になりやすいパターン**：値の範囲が事前のチェックで小さく制限されていて、オーバーフローしない。
- **確認方法**：演算に使う値のとりうる範囲を、出所（外部の入力か、内部の定数か）までたどり、最大値で計算する。符号なしのラップアラウンド（`0U - 1U`）も確認する。
- **典型的な修正**：演算の前に上限をチェックする（`if (n > SIZE_MAX / size)`）。または、広い型で計算してから範囲をチェックする。
- **逸脱コメントの例**：「誤検知。count は recv_hdr()（src/net.c:51）で 64 以下に制限されており、count * 16U は 1024 を超えず、オーバーフローすることはない。」
- **判定の目安**：オーバーフローする値が到達し、その値で範囲外にアクセスするなら `true_bug`。

## DIVIDE_BY_ZERO

- **指摘**：0 の可能性がある値で除算している（`/`・`%`）。
- **誤検知になりやすいパターン**：除数が、事前のチェックか定義（0 でない定数、設定値の下限）によって 0 にならない。
- **確認方法**：除数の出所をたどり、0 になりうるかを確認する（設定値、外部からの値、計算の結果）。
- **典型的な修正**：除算の前に 0 をチェックし、周囲と同じ方法でエラーを処理する。
- **逸脱コメントの例**：「誤検知。period は set_period()（src/timer.c:22）で 1 以上に制限してから保存するため、0 で除算することはない。」
- **判定の目安**：0 が到達する経路があれば `true_bug`。

## TAINTED_SCALAR

- **指摘**：信頼できない値（ファイル、通信、`ntohs` などで外部から入力された値）を、範囲をチェックせずに、ループの回数・添字・サイズに使用している。タグは `tainted_data`・`lower_bounds`・`upper_bounds` など。
- **誤検知になりやすいパターン**：値は外部から入力されるが、使用する前に上限と下限の両方をチェックしている（Coverity は、別の関数でのチェックを認識できないことがある）。外部から入力されるように見えて、実際は内部で生成した値である。
- **確認方法**：値の出所（どの入力か）と、使用する場所までのチェックを、上限・下限の両方でたどる。符号付きの値は、負の値も考慮する。
- **典型的な修正**：使用する前に上限と下限をチェックし、範囲外なら周囲と同じ方法でエラーを処理する。
- **逸脱コメントの例**：「誤検知。len は check_frame()（src/frame.c:33）で 1〜FRAME_MAX に制限してから使用するため、範囲外を読むことはない。」
- **判定の目安**：外部の値がチェックなしで到達すれば `true_bug`（攻撃者や破損したデータで起こりうる）。

## DEADCODE

- **指摘**：条件が常に同じ結果になるため、決して実行されないコードがある。タグは `dead_error_condition`・`dead_error_line`。
- **誤検知になりやすいパターン**：マクロやビルド設定（`#if`、構成用のヘッダー）によって、ほかのビルド構成では実行される。防御的なチェックを残している。
- **確認方法**：条件を常に同じ結果にしている値（マクロ、定数、事前のチェック）を定義までたどる。その値がほかのビルド構成で変わるかを、設定ファイルで確認する。
- **典型的な修正**：本当に不要なら削除する（ほかのビルド構成も確認してから）。ビルド構成で変わるなら、残して逸脱にするのが一般的である。
- **逸脱コメントの例**：「意図的。LOG_LEVEL は製品のビルド構成で 0、デバッグのビルド構成で 3 になり（include/config.h:12）、デバッグのビルド構成ではこの処理が実行される。」
- **判定の目安**：ビルド構成によって実行されるなら `intentional`。どのビルド構成でも実行されず、記述ミス（条件の取り違え）なら `true_bug`。防御的なコードなら `intentional`。

## UNREACHABLE

- **指摘**：`return`・`break`・`goto`・無限ループの後など、制御フロー上、決して到達しないコードがある。
- **誤検知になりやすいパターン**：到達しないのは、戻らない関数の後に置いた防御的な `return`（コンパイラの警告を抑止するためのもの）である。
- **確認方法**：到達しない理由（前の `return`、戻らない関数）を確認し、記述ミスによって本来の処理が欠落していないかを確認する。
- **典型的な修正**：不要なコードを削除する。本来の処理が欠落しているなら、制御フローを修正する。
- **逸脱コメントの例**：「意図的。fatal() は戻らないが、コンパイラの警告を抑止するために置いた return（src/main.c:90）で、実行されないことは設計どおりである。」
- **判定の目安**：防御的なコードなら `intentional`。本来の処理に到達しなくなっているなら `true_bug`。

## MISSING_BREAK

- **指摘**：`switch` の `case` の末尾に `break` がなく、次の `case` にフォールスルーする。タグは `unterminated_case`・`fallthrough`。
- **誤検知になりやすいパターン**：フォールスルーが設計どおりで、コメント（`/* fall through */`）や属性がある。続けて行う処理を、意図して次の `case` に任せている。
- **確認方法**：前後の `case` の処理と、コメント・設計文書から、フォールスルーが意図したものかを判断する。
- **典型的な修正**：意図したものでなければ `break` を追加する。意図したものなら、周囲の書き方（`/* fall through */` のコメント、`__attribute__((fallthrough))`、`[[fallthrough]]`）で明示する。MISRA C:2012 の Rule 16.3 を適用するプロジェクトでは、意図したものでも処理を分ける。
- **逸脱コメントの例**：「意図的。case 2 から case 3 へのフォールスルーは、状態 2 の処理に続けて状態 3 の処理を行う設計（src/fsm.c:88 のコメントに記載）であり、break の書き忘れではない。」
- **判定の目安**：意図したものなら `intentional`。次の `case` の処理が誤って実行されるなら `true_bug`。

## CHECKED_RETURN

- **指摘**：戻り値でエラーを返す関数の戻り値をチェックしていない（ほかの場所では、ほとんどでチェックしている）。
- **誤検知になりやすいパターン**：失敗しても問題がない（失敗の後の処理が同じ、ログに出力するだけ）。事前の処理によって、失敗しないことが決まっている。
- **確認方法**：関数が失敗する条件と、失敗したときに後の処理がどうなるかを確認する。
- **典型的な修正**：戻り値をチェックし、周囲と同じ方法でエラーを処理する。無視してよいなら、`(void)` を付けて意図を示す（周囲にその書き方があるとき）。
- **逸脱コメントの例**：「意図的。led_set() の失敗は表示が変わらないだけで、後の処理に影響せず（src/ui.c:40）、戻り値を参照しないのは設計どおりである。」
- **判定の目安**：失敗したまま処理が進んで問題が起きるなら `true_bug`。無害なら `intentional`。

## COPY_PASTE_ERROR

- **指摘**：類似のコードをコピーしたときに、変数を1つ修正し忘れている（`x` の処理の中に `y` が残っている）。タグは `original`・`copy_paste_error`。
- **誤検知になりやすいパターン**：同じ変数を使うのが正しい（両方の処理で同じ値を使う設計）。
- **確認方法**：コピー元のコード（`original`）とコピー先のコードを並べ、どの変数が対応するかを確認する。
- **典型的な修正**：修正し忘れた変数を、対応する変数に置き換える。
- **逸脱コメントの例**：「意図的。送信と受信の両方で同じ timeout を使う設計（src/link.c:14 のコメント）で、コピー時の修正漏れではない。」
- **判定の目安**：コピー時の修正漏れなら `true_bug`。意図したものなら `intentional`。

## NO_EFFECT

- **指摘**：効果のない文や、常に同じ結果になる比較がある（`x == 1;` の記述ミス、符号なしの値を `< 0` と比較、自分自身への代入、配列名を NULL と比較）。
- **誤検知になりやすいパターン**：型がビルド構成で変わり、ほかのビルド構成では意味がある（符号付きになるなど）。
- **確認方法**：式の型と値の範囲を確認し、書いた人の意図（代入のつもり、別の変数のつもり）を前後のコードから読み取る。
- **典型的な修正**：意図した演算子・変数に修正する。不要な比較を削除する。
- **逸脱コメントの例**：「意図的。sensor_t はほかの機種のビルド構成で符号付きになり（include/types.h:20）、そのビルド構成では負の値をチェックするため、比較を残している。」
- **判定の目安**：記述ミスなら `true_bug`。ビルド構成によって意味があるなら `intentional`。

## UNCAUGHT_EXCEPT

- **指摘**（C++）：送出された例外が、どこでも捕捉されずに `main`・スレッドのエントリ関数・`noexcept` の関数・デストラクタの外へ伝播する（`std::terminate` で停止する）。
- **誤検知になりやすいパターン**：その例外は、その引数では送出されない。停止すること（`terminate`）が設計どおりである。
- **確認方法**：例外を送出する関数からエントリ関数まで、捕捉する `try` / `catch` があるかをたどる。送出の条件が成立するかを確認する。
- **典型的な修正**：エントリ関数（`main`、スレッドの関数）で捕捉し、周囲と同じ方法でエラーを処理する。
- **逸脱コメントの例**：「誤検知。std::vector::at() は添字が範囲外のときだけ例外を送出し、ここでは size() 未満に制限している（src/queue.cpp:41）ため、例外が送出されることはない。」
- **判定の目安**：例外が送出されて停止する経路があれば `true_bug`。

## CTOR_DTOR_LEAK

- **指摘**（C++）：コンストラクタで確保したものを、デストラクタで解放していない。
- **誤検知になりやすいパターン**：所有権がほかのオブジェクトに移動する。解放を別のメンバ関数（`close()`）で必ず行う設計である。
- **確認方法**：確保したメンバが、どこで解放されるか（デストラクタ、`close`、所有権の移動）をたどる。
- **典型的な修正**：デストラクタで解放する。外部から見えるクラスの定義（公開メンバ、サイズ）を変える修正（スマートポインタへの置き換え）は、外部仕様の変更になるので避ける。避けられないときは、超えた制約として `fix.summary` に書く。
- **逸脱コメントの例**：「誤検知。buf_ は必ず Pool::release()（src/pool.cpp:77）に返却され、そこで解放されるため、リークすることはない。」
- **判定の目安**：解放されない経路があれば `true_bug`。

## UNINIT_CTOR

- **指摘**（C++）：コンストラクタが、メンバの一部を初期化していない。
- **誤検知になりやすいパターン**：そのメンバは、使用する前に必ず別のメンバ関数（`init()`）で初期化される。
- **確認方法**：初期化されないメンバが、値を代入する前に読まれる経路があるかをたどる。
- **典型的な修正**：メンバ初期化子リスト（`: x_(0)`）か、宣言での初期化で値を設定する（周囲の書き方に合わせる）。
- **逸脱コメントの例**：「誤検知。state_ は使用する前に必ず start()（src/conn.cpp:30）で初期化され、start() の前に読む経路はない。」
- **判定の目安**：値を代入する前に読む経路があれば `true_bug`。

## そのほかのよく検出されるチェッカー

| チェッカー | 指摘の内容 | 確認する点 |
|---|---|---|
| BAD_SHIFT | シフト量が負か、型のビット幅以上 | シフト量の範囲を出所までたどる |
| OVERFLOW_BEFORE_WIDEN | 狭い型で計算してオーバーフローした後に、広い型へ代入している | 計算の前に広い型へ変換する必要があるかを、値の範囲で確認する |
| SIGN_EXTENSION | 符号付きの値が広い型へ変換されるとき、符号拡張される | 負の値が入りうるか。`unsigned char` の値の扱い |
| CONSTANT_EXPRESSION_RESULT | 式が常に同じ値になる（`x & 0` など） | 記述ミスか、ビルド構成で値が変わるマクロか |
| IDENTICAL_BRANCHES | if と else の内容が同じ | コピー時の修正漏れか、ビルド構成で内容が変わるか |
| RETURN_LOCAL | 自動変数のアドレスを返している | 呼び出し元がそのアドレスを使用するか（使用すれば本物） |
| MISSING_RETURN | 値を返す関数に、値を返さずに終了する経路がある | その経路を通るか（MISRA C:2012 の Rule 17.4 は Mandatory） |
| ARRAY_VS_SINGLETON | 配列でない単一の変数を、配列として扱っている | 添字やコピーの長さが 1 を超えるか |
| LOCK / MISSING_LOCK | ロックの取得漏れ・二重取得・解放漏れ。ほかの場所ではロックを取得してアクセスする変数に、ロックなしでアクセスしている | その変数に同時にアクセスするスレッド・割り込みがあるか |
| INFINITE_LOOP | 終了条件が変化しないループ | 割り込みやハードウェアによって変化する値（`volatile` の有無）か |

ここにないチェッカーは、Coverity のチェッカーの説明を読み、同じ方法（警告の経路を仮説として、条件を呼び出し元と定義までたどる）で調査します。
