# 判定・確信度・推奨の詳細な基準

SKILL.md の表だけでは決められないときに読みます。

## 判定

| 状況 | 判定 | 理由と、根拠に書くこと |
|---|---|---|
| 関数の中だけなら経路が成立するが、呼び出し元をすべて確認すると、どれも条件を満たさない | `false_positive` | 現在のコードでは、その経路を通らない。「宣言が値を禁止していない」「将来の呼び出し元」は理由にしない |
| 呼び出し元の1つが、条件を満たす値を渡す | `true_bug` | その呼び出し元を根拠に書く |
| Coverity が戻らない関数（独自の abort、無限ループでリセットを待つ関数）を認識せず、その後ろを経路にしている | `false_positive` | その関数の実装（戻らないこと）を根拠に書く |
| マクロやビルド設定で無効・有効になるコード（DEADCODE など） | `intentional` | 設定の場所（ヘッダーの行、ビルド設定）を根拠に書く。どのビルド構成でも通らないなら `false_positive` |
| 製品のビルド設定で結論が変わる（`assert` と `NDEBUG`、`#if` / `#ifdef` のマクロ）が、その設定がビルド設定のファイルやプロジェクトの知識から分からない | `undetermined` | どの設定なら成立し、どの設定なら成立しないかを書く。設定が分かれば、その設定で判定する |
| 意図したフォールスルー（コメントや設計文書がある） | `intentional` | そのコメントの行を根拠に書く |
| 公開関数で、呼び出し元がリポジトリの外にある | 引数の規約（ヘッダーのコメント、仕様書）があれば、それで決める（確信度 `medium`）。規約がなければ `undetermined`（確信度 `low`） | 外部の呼び出し元は確認できない |
| 実行時の値（外部から入力されるデータ、ハードウェアの値、タイミング）だけで決まる | `undetermined` | コードからは判定できない。どの値なら問題になるかを書く |
| MISRA・CERT の規則に実際に違反していて、違反する設計上の理由がない | `true_bug`（規則の違反として） | 動作のバグでなくても、規則の違反は本物である。設計上必要で、安全であることを説明できる違反は `intentional` |

## 確信度の理由

`summary` に、どの基準に該当するかが読む人に分かるように書きます。

- `high` の例：「警告経路の 3 段階をすべてコードで確認し、呼び出し元 2 か所（src/a.c:40、src/b.c:77）も NULL を除外していた」
- `medium` の例：「呼び出し元 4 か所のうち 3 か所は確認したが、1 か所はコールバックの登録先で、呼び出す側がリポジトリにない」
- `low` の例：「警告の行が `work_dir` のコードと合わず、同じ処理を関数名で探して調査した」「ハードウェアから読む値の範囲が、コードから分からない」
- 不適切な例：「十分に確認した」「おそらく問題ない」（どの基準に該当するかが分からない）

## 推奨

1. プロジェクトの知識（`.coverity-triage/knowledge.md`）に推奨の方針があれば、それに従います（例「MISRA の Advisory の規則は逸脱にする」）。
2. 迷いやすいケース：
   - `false_positive` だが、修正が1行の防御的なチェックで、外部から見える動作も変えない → 修正でもよい（コードの意図が明確になるなら、修正を推奨してよい）。
   - `false_positive` / `intentional` で、問題にならないと言うために条件が必要（「現在の設定では」「呼び出し元が増えなければ」）→ 修正。逸脱コメントには、断定できる範囲の理由だけを短く書く。
   - `undetermined` で、修正すると動作が変わる（タイミング、外部との規約）→ 逸脱（確信度 `low`）。修正しても動作が変わらない防御的なチェックなら、修正。
3. 推奨は判定と矛盾させません。`false_positive` / `intentional` で理由のない修正、`true_bug` で逸脱、にはしません。`true_bug` で逸脱にしてよいのは、最新のコードで修正済みのときと、実行されないことや影響がないことをコードで示せるときだけです。

## 最新のコードとの差

- `work_dir` のコード（取り込み先の最新）と、Coverity が解析したコードは、リビジョンが異なることがあります。行番号がずれるので、関数名とコードの形で同じ場所を探します。
- 最新のコードで、問題の起きる行の問題が解消されている（NULL チェックや後処理が追加された）なら、修正済みです。修正された場所（ファイルと行）を書きます。
- イベントの説明（「fgets は NULL を返しうる」）がその行のコードと合わないときは、何が違うか（「警告の 42 行は、現在は空行。同じ処理は 47 行にある」）を `summary` に書き、確信度を `low` にします。
- `evidence` の行は、`work_dir` のファイルの行で書きます。警告の行（解析されたコードの行）と異なるときは、`note` で区別します。

## summary と evidence の書き方

- `summary` の最初の文は、判定の決め手を 40 文字程度で書きます。
  - 適切な例：「呼び出し元 3 か所すべてで NULL を除外している」「fread が不足したとき fp を閉じずに返す」
  - 不適切な例：「NULL_RETURNS の警告」「調査の結果、誤検知と判断」（決め手がない）
- `evidence` は、経路のどの段階を、どのコードで確認したかを、経路の順に並べます。
  - 例：`src/a.c:31`「size が 0 のときだけ get_buf() は NULL を返す」→ `src/io/reader.c:118`「呼び出し元は read_all() だけで、size は sizeof(hdr) の定数」→ `src/a.c:40`「size が 0 になる経路はなく、NULL は返らない」
- プロジェクトの知識を使用したときは、「プロジェクトの知識：panic_stop() は戻らない」のように書き、コードでも確認したかを添えます。

## 同じ原因の CID をまとめて処置するとき

差し戻しの指摘（`rework.points`）で、同じ原因の CID をまとめるよう依頼されたときは、それぞれの CID の行で、同じ理由（同じ条件、同じ呼び出し元の保証）が成立するかを確認します。修正と逸脱コメントは、すべての CID に当てはまるものを1つ作成します。同じ理由が成立しない CID があれば、その CID と理由を `summary` に書きます。

## 保存の前の確認

- 根拠の場所は、すべて自分で読んだ行か（推測した行がないか）
- パスは、リポジトリの最上位からの相対パスか（Coverity の絶対パスのままではないか）
- 判定は、経路の条件を確認した結果（すべての呼び出し元）と合うか
- 確信度の理由は、どの基準に該当するかが具体的か
- 推奨は、判定と、逸脱コメントを条件なしで書けたかどうかに合うか
- 「おそらく」「通常は」が残っていないか
- `work_dir` の中と `result_file` 以外を変更していないか

## 調査の例

警告：CID 20001、NULL_RETURNS、src/reader.c の 42 行（read_header()）。経路は「40 行：fgets は NULL を返しうる」→「42 行（問題の起きる場所）：NULL を参照」。

1. チェッカーの観点：NULL_RETURNS は、呼び出し元の保証、直前の検証、戻らない関数を確認する。
2. 経路を読む：40 行 `line = fgets(buf, sizeof buf, fp);`、42 行 `len = strlen(line);`。間に NULL チェックはない。
3. 条件：fgets が NULL を返す（ファイルの終端か、読み込みの失敗）。
4. 確認：read_header() の呼び出し元は main()（src/main.c:30）だけで、空のファイルも渡しうる（src/main.c:25 で開いたファイルをそのまま渡す）。空のファイルで fgets は NULL を返す。
5. 最新のコード：`work_dir` の同じ場所に NULL チェックはなく、経路の行とコードは合っている。
6. 判定：`true_bug`。確信度：`high`（経路と呼び出し元をすべてコードで確認した）。推奨：`fix`。

`summary` の最初の文：「空のファイルで fgets が NULL を返し、strlen で異常終了する」
