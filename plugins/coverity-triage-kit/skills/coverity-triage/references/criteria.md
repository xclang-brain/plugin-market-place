# 判定と推奨で迷いやすいケース

SKILL.md の表だけでは決められないときに読みます。

## 判定

| 状況 | 判定 | 根拠に書くこと |
|---|---|---|
| Coverity が戻らない関数（独自の abort、無限ループでリセットを待つ関数）を認識せず、その後ろを経路にしている | `false_positive` | その関数の実装（戻らないこと） |
| マクロやビルド設定で無効・有効になるコードそのものへの警告（DEADCODE など） | `intentional`。どのビルド構成でも通らないなら `false_positive` | 設定の場所（ヘッダーの行、ビルド設定） |
| 意図したフォールスルー（コメントや設計文書がある） | `intentional` | そのコメントの行 |
| 公開関数で、呼び出し元がリポジトリの外にある | 引数の規約（ヘッダーのコメント、仕様書）があれば、それで決める（確信度 `medium`）。規約がなければ `undetermined` | 規約の場所と、外部の呼び出し元は確認できないこと |
| 実行時の値（外部から入力されるデータ、ハードウェアの値、タイミング）だけで決まる | `undetermined` | どの値なら問題になるか |
| MISRA・CERT の規則に実際に違反していて、違反する設計上の理由がない | `true_bug`（動作のバグでなくても、規則の違反は本物である）。設計上必要で、安全であることを説明できる違反は `intentional` | 違反している式と、規則 |

## 推奨

- プロジェクトの知識（`.coverity-triage/knowledge.md`）に推奨の方針があれば、それに従います（例「MISRA の Advisory の規則は逸脱にする」）。
- `false_positive` で、修正が1行の防御的なチェックで、外部から見える動作も変えない：修正でもかまいません（コードの意図が明確になるなら、修正を推奨します）。
- `false_positive` / `intentional` で、問題にならないと言うために条件が必要（「現在の設定では」「呼び出し元が増えなければ」）：修正にします。
- `undetermined` で、修正すると動作が変わる（タイミング、外部との規約）：逸脱にします。修正しても動作が変わらない防御的なチェックなら、修正にします。

## 同じ原因の CID をまとめて処置するとき

`next` の応答に `members` があるときは、受け取った CID と `members` の CID の警告（`<run_dir>/issues.json` の行と、`<run_dir>/cid/<CID>/issue.json` の経路）を読み、それぞれの行で、同じ理由（同じ条件、同じ呼び出し元の保証）が成立するかを確認します。修正と逸脱コメントは、すべての CID に当てはまるものを1つ作成します。同じ理由が成立することを確認できない CID があるときは、その CID と理由を `summary` に書き、確信度を下げます。
