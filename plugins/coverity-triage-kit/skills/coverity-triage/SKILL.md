# CID 1件の処置

Coverity の警告1件について、**修正コード**と**逸脱コメント**（修正しない場合に Coverity に登録する文）の2つを作成し、判定・確信度・根拠を添えて結果フォルダーに保存します。
修正は、スクリプトが用意する作業用コピー（リポジトリの外）に書きます。利用者のリポジトリと Coverity が変わるのは、利用者が結果を確認して OK を出した後です。

## 1. 開始して CID を受け取る

```
uv run --native-tls --quiet "<このスキルのフォルダー>/scripts/triage.py" start --repo "<リポジトリ>"
```

`<リポジトリ>` は、git または svn の作業ツリーの最上位フォルダーです。どのコマンドも JSON を1つ返し、`next` に、次に実行するコマンドの全文が入っています。以降のコマンドは、`next` のものをそのまま実行します。`ok` が `false` のときは、先に `error` と `problems` の内容に対応します。

`start` の応答：

- `wait` が `true` のときは、作業用コピーを準備しています。`next` のコマンド（同じ `start`）をもう一度実行します。
- `fetch` が空でないときは、そこに書かれたツールを `arguments` のとおりに呼び出してから、`next` のコマンドを実行します。`need_fetch` が `true` のときは警告の一覧（`coverity_search_issues`）、それ以外は警告経路（`coverity_get_issue_details`）の取得です。
- 準備が完了すると `message` が返るので、利用者に1回伝えます（例「20 件の警告を処置します」「条件に合う警告は 137 件あります。設定の上限（20 件）まで取得しました」）。警告の取得だけを依頼されたときは、一覧（`<run_dir>/issues.json` の CID、チェッカー、ファイル:行、Impact）を示して終わります。
- 依頼に設定と異なる取得条件（チェッカー、Impact、件数）があるときは、`start` に `--new` を付け、`fetch` の `arguments` にその条件（`checkers`、`impacts`、`limit`）を加えます。

`start` の `next` が、CID を受け取るコマンドです。「CID 20002 を処置して」のように CID を指定されたときは、末尾に `--cid 20002` を付けます。

```
uv run --native-tls --quiet "<このスキルのフォルダー>/scripts/triage.py" next --run "<run_dir>" --cid 20002
```

| 応答の項目 | 内容 |
| --- | --- |
| `issue` | CID、チェッカー、ファイル（作業用コピーでのパス）、行、関数、Impact |
| `issue_file` | 警告経路（`events`。`main` が `true` のイベントが、問題の起きる場所）とチェッカーの説明（`checker_description`）。`fetch` が空でないときは、そのツールを呼び出して取得してから読みます |
| `work_dir` | 作業用コピー（取り込み先の最新のコード）。コードを読むのも、修正を書くのもここです |
| `result_file` | 結果を書くファイル |
| `rework` | 差し戻された CID のときだけ。`points` の指摘に対応します。`patch_applied` が `true` なら、前回の修正が `work_dir` に適用済みで、前回の結果は `result_file` にあります |
| `next` | 保存のコマンド |

`cid` が `null` のときは、処置する CID がありません。`message`（処置済み、一覧にない、など）を伝えます。

## 2. 調査する

警告経路は「このように実行されると問題が起きる」という仮説です。経路の各段階が実際のコードで成立するかを、呼び出し元と定義までたどって確認します。

- 根拠は、実際に読んだコードの場所（リポジトリの最上位からの相対パスと行）で示します。読んでいない場所や推測した行は書きません。
- 「おそらく」「通常は」で判定しません。確認できなかったことは `summary` に書き、確信度を下げます。
- コードと、資料や説明が食い違うときは、コードを優先します。
- `<リポジトリ>/.coverity-triage/knowledge.md` があれば、調査の前に読みます。人が確認して書いたプロジェクトの事実（戻らない関数、呼び出し元が保証する前提など）です。使用した知識は `summary` に「プロジェクトの知識：…」と書き、可能ならコードでも確認します。推奨の方針や逸脱コメントの書き方が書かれていれば、このスキルの基準より優先します。
- 警告経路を取得できないときは、依頼に貼り付けられた警告を使います。それもないときは、警告の行とチェッカーの説明から考えられる経路で調査し、そのことを `summary` に書きます（チャットでは、先に利用者に質問します）。

調査の手順：

1. **チェッカーの観点を読む**：チェッカー名に合う資料の、該当する項目だけを読みます。`MISRA` で始まる名前は [references/misra.md](references/misra.md)、`CERT` と規則の番号（`EXP34-C` など）を含む名前は [references/cert.md](references/cert.md)、そのほか（`NULL_RETURNS`、`RESOURCE_LEAK` など）は [references/standard.md](references/standard.md) です。資料は手がかりで、判定の決め手はコードです。資料にないチェッカーは、`checker_description` を読み、同じ手順で調査します。
2. **警告経路を順に読む**：各イベントの行の前後（目安は 20 行ずつ）を `work_dir` で読み、イベントの説明がその行のコードと合うかも確認します。`issue_file` の中のパスは Coverity のものなので、末尾が一致するファイルを `work_dir` で探します。
3. **経路が成立する条件を挙げる**：分岐の条件、引数の値、戻り値、ループの回数、マクロの値。
4. **条件を1つずつ確認する**：値の出所を、関数名・マクロ名・変数名で検索して、呼び出し元と定義までたどります。
   - 本物のバグと判定する前に、呼び出し元をすべて確認します。条件を満たす呼び出し元が1つでもあれば、経路は成立します。
   - すべての呼び出し元が条件を満たさない（例：どの呼び出し元も NULL を除外してから渡す）なら、経路は成立しません。このとき、「宣言がその値を禁止していない」「将来、呼び出し元が増える可能性がある」を本物のバグの理由にしません。
   - 呼び出し元がリポジトリにない（公開 API、コールバック、割り込み）ときは、そのことを書き、推定として扱います。
5. **最新のコードとの差を確認する**：`work_dir` は、Coverity が解析したコードより新しいことがあります。行がずれていたら、関数名とコードの形で同じ場所を探します。イベントの説明とコードが合わないときは、その内容を `summary` に書き、確信度を `low` にします。

| 判定 | 基準 |
| --- | --- |
| `true_bug`（本物のバグ） | 経路が成立し、現在の呼び出し元のいずれかで実際に問題が起きる |
| `false_positive`（誤検知） | 経路が成立しない（Coverity が認識していない条件がある）。関数の中だけなら成立しても、呼び出し元がすべて条件を満たさないときはこれにする |
| `intentional`（意図的） | 経路は成立するが、設計どおりの動作で問題にならない（意図したフォールスルー、ビルド構成で無効になるコードなど） |
| `undetermined`（判定不能） | 実行時の値や外部の仕様で決まるため、コードからは判定できない |

| 確信度 | 基準 |
| --- | --- |
| `high`（高） | 警告経路をコードで最後まで追跡でき、根拠がすべてコードにある |
| `medium`（中） | 根拠の一部が推定である（呼び出し元がリポジトリにない、マクロの展開を推定した、など） |
| `low`（低） | コードから判定できない前提に依存する。または、解析されたコードと `work_dir` のコードに差がある |

推奨（`recommendation`）：

- `true_bug` は修正（`fix`）。最新のコードで修正済みのときと、実行されないことや影響がないことをコードで示せるときだけ、逸脱にします。
- `false_positive` と `intentional` は、どの状況でも問題にならないことを**条件を付けずに断定できる**ときだけ逸脱（`deviation`）。断定できなければ修正。修正が小さく安全で、コードの意図も明確になるなら、修正でもかまいません。
- `undetermined` は、修正のリスクが小さければ修正、大きければ逸脱。確信度は `low`。
- 断定できるかは、逸脱コメント（「4. 逸脱コメントを書く」）を、「〜の場合に限る」のような条件なしで書けるかで判断します。

判定や推奨に迷うときは [references/criteria.md](references/criteria.md) を読みます。

## 3. 修正を書く

`work_dir` のファイルを、通常の編集で修正します。編集するのは `work_dir` の中と `result_file` だけです。差分は `save` が作成します。

1. **最小の変更**：問題の起きる場所に至る経路を断つのに必要な行だけを変更します。リファクタリング、整形、名前の変更は行いません。原因が1か所（サイズのマクロの定義など）にあるときは、そこを修正し、そのマクロを使うすべての場所で動作と規則への適合が保たれるかを確認します。
2. **外部仕様を保つ**：関数の引数と戻り値の型、公開ヘッダー、グローバル変数の型は変更しません。
3. **新しい MISRA・CERT の違反を作らない**：
   - 暗黙の型変換を増やしません。定数は相手の型に合わせます（符号なしと比較するなら `0U`）。ただし、int より狭い符号なし型（`uint8_t`、`uint16_t`）の演算式（`a - b` など）は int で計算されるため、比較する定数に `U` を付けると動作が変わることがあります。そのときは式を書き直します（`(a - b) > 0` は `a > b`）。
   - 条件は Boolean の式にします（`p != NULL`、`(flags & BIT) != 0U`）。`if`・`for`・`while` の本体は `{ }` で囲み、`else if` を追加したら `else` で終えます。
   - 関数の出口を増やすときは、既存の書き方に従います（出口が末尾の1つだけの関数では、戻り値の変数と `goto` や分岐で末尾に集めます）。途中で返る分岐を追加するときは、それまでに確保した資源（メモリ、開いたファイル）を解放してから返します。
   - 使用しない戻り値は、周囲の書き方（`(void)` を付けるなど）に合わせます。
4. **周囲のコードに合わせる**：インデント（タブか空白か、幅）、命名、括弧の位置、エラー処理（`goto cleanup` の後処理、エラーコードのマクロ、ログ）、コメントの書き方と言語。
5. **文字コードと改行コードを保つ**：ファイルの文字コード（UTF-8、Shift_JIS など）、BOM、改行コード（CRLF / LF）は変更しません。日本語のコメントは、そのファイルの文字コードで表せるときだけ書きます。

この制約の中で修正できないとき（例：エラーを伝えるために、戻り値の型を変更する必要がある）は、制約を超える修正を作成し、`fix.summary` に、超えた制約とその理由、影響を受ける呼び出し元すべて（関数名で検索し、ファイル:行で列挙する）を書きます。

修正コードの扱いが異なるケース：

- **最新のコードで修正済み**：`work_dir` で問題の起きる場所がすでに解消されていれば（形が違っても、経路が断たれていれば修正済みです）、何も変更しません。同じ後処理を追加すると、二重クローズや二重解放になります。判定は解析されたコードに対するもののままにし、`no_fix_reason` に修正済みの場所（ファイル:行）を書き、推奨は `deviation` にして、逸脱コメントにその場所を書きます。
- **誤検知・意図的**：外部から見える動作を変えずに警告を解消できる修正（現在の呼び出し元では通らない防御的なチェック、初期化の明示、`(void)` による明示など）があれば作成し、動作が変わらないことを `fix.summary` に書きます。そのような修正がないときだけ、何も変更せず、`no_fix_reason` に理由を書きます。

書いた後、修正したファイルを読み直し、経路が断たれていること、変更が必要な行だけであること、インデントと改行コードが周囲と同じであることを確認します。

## 4. 逸脱コメントを書く

逸脱コメントは、この警告が**どの状況でも問題にならない**ことを述べる短い文です。Coverity に登録され、後で読む人が「修正しなくてよい理由」として使います。修正を推奨する CID にも書きます。

- 日本語で、改行・箇条書き・書式（`` ` `` や `**`）のない1行。**200 文字以内**。判定区分の後に1〜2文。
- 順序：**判定区分**（「誤検知。」「意図的。」「本物の不具合。」のいずれかで始める）→ **問題にならない理由**（条件を付けずに断定する）→ **根拠の場所**（関数名とファイル:行。例 `open_session()（src/net/session.c:120）`、範囲は `src/reader.c:55〜60`）。実際に読んで確認した場所だけを書きます。
- 判定区分は判定に合わせます：`false_positive` は「誤検知。」、`intentional` は「意図的。」、`true_bug` は「本物の不具合。」。`undetermined` は、コードで確認できた事実に合うものを選びます。

> 誤検知。find_slot() の戻り値は NULL になりうるが、呼び出し元 open_session()（src/net/session.c:120）で NULL を除外してから渡しているため、NULL を参照することはない。

書くのは、問題にならない理由だけです。次の内容は `summary` に書きます。

- 条件、前提、ただし書き：「ただし」「〜の場合に限る」「〜する場合は」「〜に対して」「この判断の前提は」。コードの動作も「場合は」を使わずに書きます（「失敗すると -1 を返す」）
- 推量：「おそらく」「〜と思われる」「〜かもしれない」
- 調査の過程や、調査しきれなかったこと
- 推奨や、読む人への依頼・指示：「修正を推奨」「確認してください」「〜すべき」

断定できないとき：

- 条件を付けないと「問題にならない」と書けないなら、問題になりうるということです。**推奨を修正に**し、逸脱コメントには断定できる事実だけを短く書きます（例「本物の不具合。src/reader.c:42 で fgets の戻り値を確認せずに使用しており、修正しない理由は説明できない。」）。
- 本物の不具合でも、現在は実行されないことや影響がないことをコードで示せるなら、その事実をそのまま書きます（例「本物の不具合。v1 形式の読み込みは現在の製品では無効（include/features.h:31）で、この処理は実行されない。」）。

| 判定区分 | Classification | Action | Severity |
| --- | --- | --- | --- |
| 誤検知 | False Positive | Ignore | Unspecified |
| 意図的 | Intentional | Ignore | Unspecified |
| 本物の不具合 | Bug | Ignore | 警告の Impact に合わせる（High は Major、Medium は Moderate、Low は Minor、不明なら Unspecified） |

ほかの例と、規則に合わない例の修正例は [references/comments.md](references/comments.md) にあります。

## 5. 結果を書いて保存する

`result_file` に、UTF-8 の JSON で書きます。

```json
{
  "cid": 20002,
  "verdict": "false_positive",
  "summary": "呼び出し元 2 か所とも NULL を除外してから渡している。呼び出し元はすべてリポジトリにあり、コードで確認した。",
  "evidence": [
    {"file": "src/net/session.c", "line": 120, "note": "open_session() が find_slot() の戻り値の NULL を除外している"},
    {"file": "src/net/admin.c", "line": 64, "note": "open_admin() も同様に NULL を除外している"}
  ],
  "recommendation": "deviation",
  "confidence": "high",
  "fix": {"summary": "use_slot() の先頭に NULL チェックを追加する。現在の呼び出し元では通らない分岐で、動作は変わらない。"},
  "deviation": {
    "comment": "誤検知。find_slot() の戻り値は NULL になりうるが、呼び出し元 open_session()（src/net/session.c:120）と open_admin()（src/net/admin.c:64）で NULL を除外してから渡しているため、NULL を参照することはない。",
    "classification": "False Positive", "action": "Ignore", "severity": "Unspecified"
  }
}
```

- `summary`：最初の文を、判定の決め手（40 文字程度）にします。人はまずここを読みます。続けて、確信度がその値である理由を、どの基準に該当するかが分かるように書きます。
- `evidence`：経路をどのコードで確認したかを、経路の順に並べます。`file` はリポジトリの最上位からの相対パス、`line` は `work_dir` のファイルでの行です。
- `fix` と `no_fix_reason` は、どちらか一方です。`work_dir` を変更したときは `fix.summary`（修正の内容と、どの条件で何が変わるか）、変更していないときは `no_fix_reason` を書きます。`recommendation` が `fix` のときは、修正が必要です。

書いたら、`next` の保存のコマンド（`… save --run "<run_dir>" --cid 20002 --slot 1`）を実行します。`ok` が `false` のときは、`problems` をすべて修正して、同じコマンドをもう一度実行します。項目の値や逸脱コメントの規則を満たさない結果は保存されません。

## 6. 2つの出力を示す

保存できたら、修正コードと逸脱コメントの**両方**を示します。差分は `patch_file` から読みます。

```
CID 20002（FORWARD_NULL、src/net/slot.c:15）
判定：誤検知（確信度：高 — 呼び出し元 2 か所をすべてコードで確認した）
推奨：逸脱コメントを登録する
根拠：
- src/net/session.c:120 open_session() が find_slot() の戻り値の NULL を除外している
- （根拠を、経路の順にすべて）
修正コード：use_slot() の先頭に NULL チェックを追加する（動作は変わらない）
（差分。修正コードがないときは、その理由）
逸脱コメント：誤検知。find_slot() の戻り値は…（149 文字）
Classification: False Positive／Action: Ignore／Severity: Unspecified
```

「まとめを見せて」と依頼されたときは、次のコマンドを実行し、`table`（全 CID の表）と `summary_file` の場所を示します。`wait` が `true` のときは、もう一度実行します。

```
uv run --native-tls --quiet "<このスキルのフォルダー>/scripts/triage.py" finish --run "<run_dir>"
```

## エージェントが多数の CID を続けて処置するとき

- 質問しません。不足している情報は `summary` に書き、確信度を下げて進めます。
- 保存できたら、出力を示す代わりに、`save` の `next` のコマンドで次の CID を受け取ります。
- `next` が `done: true` を返すまで、「2. 調査する」から「5. 結果を書いて保存する」を繰り返します。

## 結果フォルダーを使用できないとき

警告が依頼に貼り付けられていて、`start` が設定ファイルがないと応答したとき、または `next` がその CID は一覧にないと応答したときは、同じ方法で調査し、「6. 2つの出力を示す」の形でチャットに回答します。ファイルは変更せず、修正コードは差分（unified diff、パスはリポジトリからの相対パス）で示し、逸脱コメントは「4. 逸脱コメントを書く」の規則を自分で確認します。結果を保存していないことを添えます。
