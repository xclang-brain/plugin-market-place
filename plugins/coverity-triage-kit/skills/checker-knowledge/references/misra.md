# MISRA C / C++ の見方

## 考え方

- MISRA の違反は、動きのバグではなく、書き方の決まりの違反であることが多い。判定は次のように決める。
  - コードが本当に規則に違反している → `true_bug`（規則の違反として本物）。直すか、正当な理由で逸脱するかは推奨で決める。
  - 規則の対象外（Coverity の読み違い、例外の条項に当たる、生成したコードで対象外と決めている）→ `false_positive`。
  - 違反しているが、設計上必要で、安全を説明できる → `intentional`。
- 確かめ方は、規則の文と例外の条項を、★ の行の式・型・マクロの展開に当てはめること。型はマクロと型定義（`typedef`）を定義までたどって決める。
- 直すときは、警告を消すために別の規則に違反しない（例：キャストを足して Rule 10.8 や 11.x に当たる）。直した式に、同じ規則を当てはめ直す。

## 分類と逸脱の扱い

| 分類 | 扱い | 推奨の目安 |
|---|---|---|
| Mandatory（必須） | 逸脱できない | 本当に違反していれば修正を推奨。Coverity の読み違いなら `false_positive` |
| Required（必要） | 逸脱には正式な手続き（理由・影響・承認の記録）が要る | 小さく安全に直せれば修正。設計上要るなら逸脱（手続きが要ることを調べた経過に書く） |
| Advisory（推奨） | 比較的柔軟。プロジェクトが「適用しない」と決めることもある（MISRA Compliance:2020） | プロジェクトの決まりに従う。決まりがなく、直すと読みにくくなるなら逸脱 |

- プロジェクトが分類を変えている（Advisory を適用しない、Required を Mandatory に上げる）ことがある。プロジェクトの知識（`.coverity-triage/knowledge.md` の推奨の方針）に書かれていれば、そちらを優先する。
- MISRA C:2012 の Mandatory の主な規則：9.1、12.5、13.6、17.3、17.4、17.6、19.1、21.13、21.17〜21.20、22.2、22.4〜22.6。

## 原因のマクロと型定義

- 1つのマクロや型定義が原因で、同じ規則の警告が何十件も出ることがある（展開した場所ごとに出る）。警告の `macro` の項目や、★ の行のマクロを見て、原因が1つかを確かめる。
- 原因が1つなら、その定義の1か所を直す修正が最も効く（例：`#define MASK 0x0F` を `0x0FU` にする、マクロの引数を括弧で囲む）。
- 定義を変えると、そのマクロを使うすべての場所の型や値が変わる。使う場所をすべて検索し、新しい違反（符号付きの文脈で使っていた場所の Rule 10.x など）や動きの変化がないかを確かめる。
- 型定義の元の型を変えるのは、外から見える仕様（構造体の大きさ、関数の引数）を変えることが多い。ふつうは避け、使う場所で直すか、逸脱にする。

## 本質的な型のモデル

Rule 10.x は「本質的な型」（essential type）で考える。C の整数の格上げ（int への変換）を考えず、書いたままの型の分類で比べる。

| 本質的な型の分類 | 例 |
|---|---|
| Boolean | `bool`、比べる式（`a < b`）、論理の式（`a && b`）の結果 |
| character | `char` |
| signed | `signed char`、`short`、`int`、`int32_t` など |
| unsigned | `unsigned char`、`uint16_t`、`size_t` など |
| enum | 名前のある列挙型（名前のない列挙の定数は signed） |
| floating | `float`、`double` |

- 整数の定数の本質的な型は、その値を表せる最も小さい型。`5` は signed（signed char）、`5U` は unsigned（unsigned char）、`200` は signed（short）。
- `u8a + u8b`（どちらも uint8_t）の本質的な型は uint8_t のまま。実際の C では int で計算するので、狭い型であふれる計算を広い型に入れる・キャストするところで、Rule 10.6〜10.8 に当たる。
- 本質的な型は規則を当てはめるための見方で、実際の計算は C の決まり（整数の格上げと通常の算術変換）で行われる。int より狭い符号なしの型（`uint8_t`、int が 32 ビットなら `uint16_t`）は、計算の前に符号付きの int になる。そのため、規則に合わせて定数に `U` を付けると、計算の型が int から unsigned int に変わり、動きが変わることがある（[Rule 10.4](#rule-104) の「`U` を付けて直すときの注意」）。

## Rule 10.1

- **求めること**（Required）：演算子の被演算子に、ふさわしくない本質的な型を使わない。
- **よくある違反**：符号付きの値のビット演算・シフト（`s16 << 2`、`s & 0x0F`）、Boolean の算術（`flag + 1`）、Boolean でない値の `!`・`&&`・`||`（`!count`）、符号なしの単項の `-`、列挙の算術。
- **直し方**：ビット演算は符号なしの型で行う（`(uint16_t)s16 << 2U` より、元の変数の型を見直す）。`!count` は `count == 0U` にする。
- **判定**：本当に当たれば `true_bug`（規則の違反）。直すのが小さく安全なら修正を推奨。

## Rule 10.3

- **求めること**（Required）：式の値を、より狭い本質的な型や、別の分類の変数に入れない。代入のほか、関数の引数、戻り値、初期化も含む。
- **よくある違反**：`uint8_t x = u16;`（狭くなる）、`int32_t s = u32;`（分類が違う）、`bool b = 1;`、`return -1;`（戻り値の型が符号なし）。
- **例外**：負でない整数の定数の式で、値が入る型で表せるもの（`uint8_t x = 5;`）は許される。
- **直し方**：範囲を確かめたうえで明示的にキャストする（`x = (uint8_t)u16;`）。変数や戻り値の型を合わせる（外から見える仕様に当たるなら避ける）。
- **判定**：値が切れる・符号が変わる場合が本当にあるなら、規則の違反に加えて動きのバグにもなる（確信度を上げる根拠を探す）。

## Rule 10.4

- **求めること**（Required）：通常の算術変換が行われる演算子では、両方の被演算子を同じ本質的な型の分類にする。当たる演算子は、二項の `+ - * / % & | ^`、比べる `< > <= >= == !=`、条件の `?:` の2つ目と3つ目、複合代入（`+=` など）。シフトは当たらない（Rule 10.1 で見る）。
- **よくある違反と直し方**：

  | 違反 | 理由 | 直し方 |
  |---|---|---|
  | `if (count > 0)`（count は uint16_t） | 符号なしと、符号付きの定数 `0` | `count > 0U` |
  | `s32 + u32` | signed と unsigned | 片方の型に合わせる。キャストは被演算子に付ける（`s32 + (int32_t)u32`。値の範囲を確かめる） |
  | `mode == 1`（mode は名前のある列挙型） | enum と signed | 列挙の定数と比べる（`mode == MODE_RUN`） |
  | `temp > 0`（temp は float） | floating と signed | `temp > 0.0F` |
  | `flag ? u8 : 0` | unsigned と signed | `flag ? u8 : 0U` |

- **例外**：文字型と、符号付き・符号なしの整数の足し算（`'0' + n`、`+=` も）と、文字型から符号付き・符号なしの整数を引く引き算（左が文字型の `c - n`、`-=` も）は許される。
- **確かめ方**：両方の被演算子の型を、マクロと型定義を定義までたどって決める（マクロの定数に `U` が付いているか、型定義が符号付きか）。
- **誤検知になりやすい形**：Coverity が型定義やマクロの展開を読み違えている、両方とも実は同じ分類（同じ型定義を通っている）。
- **`U` を付けて直すときの注意**：直す前に、相手の被演算子の C での型（格上げの後の型）を確かめる。`U` を付けると、相手が int のままのときは、計算が unsigned int で行われるようになる。
  - 動きは変わらない（機械的に直してよい）：相手が1つの変数か定数で、比べる演算子（`count > 0U`、`u8 == 5U`）のとき。相手がもともと unsigned int 以上の符号なし（int が 32 ビットのときの `uint32_t`、`size_t`、`unsigned long`）のとき（定数は前から符号なしに変換されている）。浮動小数点の相手と比べる定数に `.0F` を付けるとき。
  - 動きが変わることがある（1件ずつ確かめる）：相手が、int より狭い符号なしの型の**計算の式**で、値が負になりうるとき（`a - b`、`-a`、`~a`）。例：`uint16_t a = 1, b = 2;` のとき、`(a - b) > 0` は偽（int の -1 と比べる）だが、`(a - b) > 0U` は真（-1 が unsigned int の最大の値になる）。`u8 - 1` と `u8 - 1U` も、`u8` が 0 なら -1 と最大の値に分かれ、比べる・割る・右シフト・広い型へ入れるところで差が出る。
  - 動きが変わるときは、書いた人の意図に合う形に書き直す（`(a - b) > 0` が「a が b より大きい」の意味なら `a > b`）。意図がコードから決められなければ、機械的に直さず、確信度を下げて調べた経過に書く。
  - int が 16 ビットの機械では、`uint16_t` は unsigned int に格上げされるので、動きが変わる式が違う。対象の機械の int の幅を確かめる。
- **判定の目安**：本当に分類が違えば `true_bug`（規則の違反）。上の注意で動きが変わらないと確かめられた形は、`U` を付けるような小さく安全な直し方で修正を推奨する。動きが変わる形は、意図に合う書き直しを修正の案にする。同じマクロが原因で大量に出ていれば、マクロの定義を直す（使う場所の式ごとに、上の注意を当てはめる）。設計上どうしても混ぜる必要があり、値の範囲で安全を説明できるなら、逸脱（正式な手続きが要る）。

## Rule 10.6・10.7・10.8

- **求めること**（Required）：
  - 10.6：複合の式（`a * b` などの計算の結果）を、より広い本質的な型の変数に入れない（`uint32_t r = u16a * u16b;`）。
  - 10.7：複合の式と、より広い型の被演算子を組み合わせない（`u32 + (u16a * u16b)`）。
  - 10.8：複合の式を、別の分類か、より広い型にキャストしない（`(uint32_t)(u16a + u16b)`）。
- **なぜ**：書いた人は広い型で計算するつもりでも、計算は狭い型（int が 16 ビットの機械では本当に 16 ビット）で行われ、あふれることがある。
- **直し方**：キャストを計算の前の被演算子に付ける（`(uint32_t)u16a * u16b`）。
- **判定**：あふれる値の範囲が本当にありうれば、規則の違反に加えて動きのバグ。範囲で決してあふれないと言えても、規則の違反は残る（直すのが小さいので修正を推奨しやすい）。

## Directive 4

| 規則（分類） | 求めること | 見方 |
|---|---|---|
| Dir 4.1（Required） | 実行時の失敗（あふれ、0 での割り算、範囲の外）を少なくする | 中身は標準チェッカーと同じ見方（OVERRUN、DIVIDE_BY_ZERO など） |
| Dir 4.6（Advisory） | 基本の型（`int`）の代わりに、大きさと符号の分かる型定義（`int32_t`）を使う | 外から見える関数の型を変えるのは外部の仕様の変更。中の変数だけなら直せる |
| Dir 4.7（Required） | エラーを返す関数の戻り値を確かめる | CHECKED_RETURN と同じ見方 |
| Dir 4.9（Advisory） | 関数のようなマクロより関数を使う | 逸脱になりやすい（型を選ばない処理、速さ） |
| Dir 4.10（Required） | ヘッダに二重の読み込みの防ぎ（include guard）を付ける | 足すだけで直る |
| Dir 4.12（Required） | 動的なメモリの確保を使わない | 起動時だけの確保などは逸脱。置き換えは大きな変更（決まりを超える） |
| Dir 4.14（Required） | 外から来た値を確かめてから使う | TAINTED_SCALAR と同じ見方 |

Directive は Coverity が近い形で判定するので、誤検知の可能性をていねいに確かめる。

## Rule 2

- 2.1（Required）届かないコードを置かない、2.2（Required）意味のない処理（dead code。動くが結果に影響しない処理）を置かない、2.3〜2.6（Advisory）使わない型・タグ・マクロ・ラベルの宣言、2.7（Advisory）使わない引数。
- 2.1 は UNREACHABLE、2.2 は「動いても結果が変わらない式」（NO_EFFECT に近い）で、Coverity の DEADCODE とは意味が少し違う。
- 2.7 は、コールバックなど引数の形が決まっている関数に多い。`(void)param;` で使わないことを示すのがよくある直し方。まわりにその書き方がなければ逸脱。
- 構成（`#if`）で使う・使わないが変わるものは `intentional`。

## Rule 8

- 8.2（Required）引数のない関数は `void f(void)` と書く。8.3（Required）宣言と定義で引数の名前と修飾子を同じにする。8.4（Required）外部に見える定義の前に、その宣言（自分のヘッダ）が見えるようにする。8.5（Required）外部の宣言は1つのヘッダに1回。8.6（Required）外部の定義は1つ。
- 8.7（Advisory）1つのファイルでしか使わない関数・変数は `static` にする。公開のヘッダに宣言があるもの、ライブラリとして外から使うものを `static` にするのは、外から見える仕様の変更。
- 8.9（Advisory）1つの関数でしか使わない変数は、その関数の中で定義する。8.13（Advisory）書き換えないポインタの引数は `const` を付ける（公開の関数の形が変わるので、外部の仕様に当たるかを見る）。
- 宣言と定義を合わせる直し方は、たいてい小さく安全。

## Rule 11

| 規則（分類） | 求めること | 見方 |
|---|---|---|
| 11.1（Required） | 関数へのポインタを、ほかの型と変換しない | 割り込みの表などで必要なら逸脱 |
| 11.3（Required） | 別の型のオブジェクトへのポインタにキャストしない（`(uint32_t *)bytes`） | 整列（alignment）と別名の決まりで本当に壊れることがある。`memcpy` で写す直し方。char のポインタへの変換は例外 |
| 11.4（Advisory） | ポインタと整数を変換しない | レジスタのアドレス（`(volatile uint32_t *)0x40021000U`）は逸脱になりやすい（`intentional`） |
| 11.5（Advisory） | `void *` から、オブジェクトへのポインタに変換しない | メモリの確保やコールバックの文脈で必要なら逸脱 |
| 11.6（Required） | `void *` と算術の型を変換しない | |
| 11.8（Required） | キャストで `const` / `volatile` を外さない | 呼ぶ関数の引数に `const` がないのが原因なら、その関数の形の変更（外部の仕様）に当たるかを見る |
| 11.9（Required） | NULL のポインタの定数は `NULL` だけにする（`p = 0` は違反） | `NULL` に置き換えるだけで直る |

## Rule 12

- 12.1（Advisory）演算子の優先順位を括弧で明示する（`a + b << 2` → `(a + b) << 2`）。直すのは小さく安全。
- 12.2（Required）シフトの量は 0 から、左の型の幅 - 1 まで。量の範囲を出どころまでたどる（BAD_SHIFT と同じ）。
- 12.3（Advisory）カンマ演算子を使わない。12.4（Advisory）定数の式で符号なしの回り込みを起こさない（`0U - 1U`）。12.5（Mandatory）配列の形の引数に `sizeof` を使わない（ポインタの大きさになる）。

## Rule 13

- 13.2（Required）評価の順で結果が変わる式を書かない（`a[i] = i++;`、1つの式で同じ `volatile` を2回読む `REG + REG`）。文を分ける。
- 13.3（Advisory）`++` / `--` のある式に、ほかの副作用を入れない（`x = a[i++];`）。13.4（Advisory）代入の結果を使わない（`if ((p = get()) != NULL)`）。文を分けるのが直し方。
- 13.5（Required）`&&` / `||` の右に、残る副作用（関数の呼び出しで状態を変えるもの）を置かない。右が呼ばれないことがあるため。
- 13.1（Required）初期化の並びに副作用を置かない。13.6（Mandatory）`sizeof` の中に副作用を置かない。

## Rule 14

- 14.1（Required）ループの回数の変数に浮動小数点を使わない。14.2（Required）`for` の形を整える（回数の変数を中で書き換えない）。
- 14.3（Required）条件の式がいつも同じ値にならない。例外：無限ループ（`for (;;)`、`while (1)`）と、マクロの `do { } while (0)`。
  - 構成のマクロで値が決まる（`if (DEBUG_LEVEL > 2)`）→ `intentional`（逸脱）が多い。
  - 型でいつも同じになる（`if (u8 >= 0U)`）→ 書き間違いなら `true_bug`。
- 14.4（Required）`if`・`while` などの条件は Boolean にする。`if (p)` → `if (p != NULL)`、`if (flags & BIT)` → `if ((flags & BIT) != 0U)`、`while (n--)` → 比べる形に書き直す。直すのは小さく安全。

## Rule 15

- 15.1（Advisory）`goto` を使わない。15.2・15.3（Required）`goto` は後ろの、同じか外側の区切りのラベルへ。エラーの後始末の `goto cleanup` は 15.2・15.3 を守り、15.1 はプロジェクトで逸脱していることが多い。
- 15.4（Advisory）ループを抜ける `break` / `goto` は1つまで。
- 15.5（Advisory）関数の出口は終わりの1つにする。途中の `return` は既存の書き方に合わせる。プロジェクトで適用しないと決めていることが多く、逸脱になりやすい。修正で出口を増やすときも、まわりの書き方に合わせる。
- 15.6（Required）`if`・`for`・`while` などの中身は `{ }` で囲む。足すだけで直る。
- 15.7（Required）`if … else if` は `else` で終える。何もしないなら `else { /* 何もしない理由 */ }` を足す。

## Rule 16

- 16.1（Required）`switch` の形を整える。16.2（Required）`case` のラベルは `switch` の一番外の区切りに置く。
- 16.3（Required）空でない `case` は、無条件の `break` で終える。空の `case` を並べるのは許される。意図したフォールスルーも違反なので、直す（処理を分ける）か、逸脱の手続きを取る。
- 16.4（Required）`default` を置く（`default: break;` と、何もしない理由のコメント）。16.5（Required）`default` は最初か最後。16.6（Required）`case` を2つ以上にする。16.7（Required）`switch` の式を Boolean にしない。

## Rule 17

- 17.1（Required）`<stdarg.h>` を使わない。printf の形のログの関数は逸脱になりやすい。
- 17.2（Required）関数を再帰で呼ばない。深さに上限があると説明できれば逸脱、なければ修正（ループにする。変更が大きいなら決まりを超える）。
- 17.3（Mandatory）宣言のない関数を呼ばない（ヘッダを読み込む）。17.4（Mandatory）値を返す関数は、すべての出口で値を返す。
- 17.7（Required）値を返す関数の戻り値を使う。使わないなら `(void)memcpy(...)` のように `(void)` で捨てることを示す。戻り値がエラーなら、捨てずに確かめる（Dir 4.7、CERT ERR33-C）。
- 17.8（Advisory）関数の引数を書き換えない。中の変数に写して使う。

## Rule 18

- 18.1（Required）ポインタの計算の結果は、同じ配列の要素を指す（OVERRUN と同じ見方）。18.2・18.3（Required）ポインタの引き算・比べは同じ配列の中だけ。
- 18.4（Advisory）ポインタに `+`・`-`・`+=`・`-=` を使わない。添字（`p[i]`）に書き直すのが直し方。
- 18.5（Advisory）ポインタの入れ子は2段まで。18.6（Required）自動変数のアドレスを、その変数より長く生きる場所に入れない（RETURN_LOCAL と同じ）。18.7（Required）フレキシブル配列のメンバを使わない。18.8（Required）可変長の配列を使わない。

## Rule 20

- 20.1（Advisory）`#include` の前に、前処理の指示とコメントのほかを置かない。20.4（Required）キーワードと同じ名前のマクロを作らない。20.5（Advisory）`#undef` を使わない。
- 20.7（Required）マクロの引数を展開する式は括弧で囲む（`#define SQ(x) ((x) * (x))`）。マクロの定義の1か所を直せば、展開した場所の警告がすべて消える。
- 20.9（Required）`#if` で使う名前は定義しておく（定義のない名前は 0 として扱われ、書き間違いに気づけない）。`defined()` で確かめるか、既定の値を定義する。
- 20.10（Advisory）`#` と `##` を使わない。

## Rule 21 と 22

| 規則（分類） | 求めること | 見方 |
|---|---|---|
| 21.1・21.2（Required） | 予約された名前（`_` と大文字、`__` で始まる名前）を作らない | include guard の `__FOO_H` が多い。名前を変えるのは小さく安全 |
| 21.3（Required） | `malloc` / `free` などを使わない | Dir 4.12 と同じ。起動時だけの確保は逸脱、置き換えは大きな変更 |
| 21.6（Required） | 標準入出力（`printf` など）を使わない | デバッグの構成だけで使うなら逸脱 |
| 21.7（Required） | `atoi`・`atol`・`atof` を使わない | `strtol` などと、エラーの確かめに置き換える |
| 21.8（Required） | `abort`・`exit` など終わらせる関数を使わない（版によって `getenv`・`system` も） | 終わり方の設計を確かめる |
| 21.10（Required） | `<time.h>` を使わない | |
| 21.15・21.16（Required） | `memcpy`・`memcmp` などの引数の型を合わせる | |
| 21.17・21.18（Mandatory） | `<string.h>` の関数で範囲の外を触らない、大きさの引数を正しくする | OVERRUN・BUFFER_SIZE と同じ見方。逸脱できない |

## そのほかの規則

- 5.x（名前の重なり）：別の場所の名前と区別できる名前にする（5.1〜5.9）。名前を変えるのは、外から見える名前なら外部の仕様の変更。
- 7.1（Required）8進数の定数を使わない（`010` は 8）。7.2（Required）符号なしで表す整数の定数に `U` を付ける。7.3（Required）`l` の接尾辞は大文字の `L`。7.4（Required）文字列の定数は `const char *` に入れる。
- 9.1（Mandatory）値を入れる前の自動変数を読まない（UNINIT と同じ見方）。9.2〜9.5（Required）初期化の並びの形。
- 19.1（Mandatory）重なる場所への代入をしない。19.2（Advisory）`union` を使わない（通信のデータの読み替えなどは逸脱になりやすい）。

## MISRA C++ のヒント

- 名前は `MISRA C++-2008 Rule 5-0-4` のような形（2008 年版は Required・Advisory・Document の分類、2023 年版は Mandatory・Required・Advisory）。分類の扱いは MISRA C と同じに考える。
- 2008 年版の 5-0-x（暗黙の変換、「基礎の型」underlying type）は、MISRA C の Rule 10.x の本質的な型と同じ考え方（5-0-4 は符号を変える暗黙の変換）。
- 6-4-x（`switch` の形。6-4-5 はフォールスルー）は Rule 16.x、0-1-x（届かない・使わないコード）は Rule 2.x、15-x（例外）は UNCAUGHT_EXCEPT と同じ見方。
- C++ では、直し方に言語の機能（`static_cast`、`constexpr`、`enum class`）を使うことが多い。まわりのコードの書き方と、使う C++ の版に合わせる。

## 逸脱コメントのヒント

- 本当に違反しているが設計上必要なもの（`intentional`）は「意図的。」で始め、違反が必要な理由と、安全である理由を、条件を付けずに書く。
  - 「意図的。UART0_DR のレジスタ（0x4000C000、include/regs.h:30）を読み書きするため整数をポインタに変換しており、アドレスは機種の仕様で決まっている。」
  - 「意図的。LOG_LEVEL は製品の構成で 0、デバッグの構成で 3 になり（include/config.h:12）、この条件は構成で変わる。」
- Coverity の読み違い（`false_positive`）は「誤検知。」で始め、規則の対象にならない理由を書く。
  - 「誤検知。count と比べる LIMIT は 10U（include/limits.h:8）で、両方とも符号なしのため、Rule 10.4 の対象ではない。」
- 逸脱の記録の番号を書くプロジェクトでは、プロジェクトの知識の「逸脱コメントの書き方」に従う。
- Mandatory の規則は逸脱できないので、本当に違反していれば逸脱コメントで済ませない（推奨は修正）。
