# 標準チェッカーの見方

Coverity の標準チェッカー（MISRA・CERT のほか）の見方です。項目は、指摘すること・誤検知になりやすい形・確かめ方・直し方の定石・逸脱コメントのヒント・判定の目安の順です。逸脱コメントのヒントの関数名と場所は例なので、実際に読んだ場所に置き換えます。

## 経路の読み方

- 警告経路のイベントは、Coverity がたどった道筋です。`cond_true` / `cond_false` は、その分岐を通ったこと（条件が真・偽）を示します。★（main のイベント）が問題の起きる場所です。
- Coverity がよく見落とすもの：戻らない関数、別の関数ですでにした検証、出力引数での初期化、マクロやビルドの設定で消えるコード、所有権の移動（戻り値や構造体に渡す）、ループの回数の上限。
- 誤検知かどうかは、★ に至る条件が、今のコード（すべての呼び出し元）で成り立つかで決めます。関数の中だけで成り立つことは、本物の理由になりません。

## NULL_RETURNS

- **指摘**：NULL を返すことがある関数の戻り値を、確かめずに参照している。Coverity は、ほかの場所でその戻り値を確かめている割合（「checked 5 out of 6 times」など）からも決める。経路によく出るタグは `returned_null`・`var_assigned`・`dereference`。
- **誤検知になりやすい形**：
  - その引数（定数のキー、固定の表にある名前）では NULL を返さない。
  - 呼び出し元や直前の処理が、NULL にならないことを保証している（同じ値を別の関数で検証済み）。
  - NULL のときは戻らない関数（独自の abort、無限ループでリセットを待つ関数）で止まる。
- **確かめ方**：関数の中身を読み、どの引数・状態で NULL を返すかを確かめる。その条件が、この呼び出しで成り立つかを、引数の出どころまでたどる。
- **直し方の定石**：参照の前に `!= NULL` で確かめ、まわりと同じエラーの返し方（エラーコード、`goto cleanup`）にする。
- **逸脱コメントのヒント**：「誤検知。cfg_get() は表にあるキーでは NULL を返さず、"net.port" は表に必ずある（src/cfg.c:40）ため、NULL を参照することはない。」
- **判定の目安**：NULL になる条件が今の呼び出しで成り立てば `true_bug`。成り立たなければ `false_positive`。外のデータ（ファイル、通信、メモリ不足）で決まるなら、そのことが起こりうるかで決める（malloc の失敗は、組み込みでも起こりうるものとして扱う）。

## FORWARD_NULL

- **指摘**：ポインタを NULL と比べた（または NULL を代入した）後、NULL かもしれない経路でそのポインタを参照している。タグは `var_compare_op`・`assign_zero`・`var_deref_op`・`var_deref_model`（関数に渡して、その中で参照）。
- **誤検知になりやすい形**：
  - NULL を比べた枝で、戻らない関数を呼ぶ（Coverity がそれを知らない）。
  - 比べたのは念のための確かめで、呼び出し元はすべて NULL でない値を渡す。
  - 比べた後、別の変数の条件で、参照する枝に入らないことが決まっている（Coverity は変数どうしの関係を見落とす）。
- **確かめ方**：NULL を比べた枝の後、参照の行まで、どの分岐を通るかをたどる。呼び出し元が NULL を渡しうるかを、すべての呼び出し元で確かめる。
- **直し方の定石**：NULL の枝で、まわりと同じ形で関数を抜ける（エラーコードを返す）。比べ方が要らないなら、比べるのをやめるのではなく、参照の前に確かめをそろえる。
- **逸脱コメントのヒント**：「誤検知。p が NULL のときは fatal()（src/fatal.c:6）で止まり戻らないため、src/settings.c:24 で NULL を参照することはない。」
- **判定の目安**：NULL のまま参照の行に届く呼び出し元・枝があれば `true_bug`。どの呼び出し元からも届かなければ `false_positive`。

## REVERSE_INULL

- **指摘**：ポインタを参照した後で、NULL かを確かめている（確かめが遅い、または要らない）。タグは `deref_ptr`・`check_after_deref`。
- **誤検知になりやすい形**：参照の前に、別の形（呼び出し元、別の変数）で NULL でないことが決まっていて、後の確かめは念のためのもの。
- **確かめ方**：参照の行より前に、NULL でないことが保証されているかを、呼び出し元までたどる。保証がなければ、参照の行で先に落ちる。
- **直し方の定石**：確かめを参照の前に動かす。保証があるなら、要らない確かめを外す（外すと MISRA の防御の決まりに触れるプロジェクトでは、前に動かす方を選ぶ）。
- **逸脱コメントのヒント**：「誤検知。dev は呼び出し元 open_all()（src/dev.c:52）で NULL を除いてから渡すため、src/dev.c:80 の確かめは念のためで、NULL を参照することはない。」
- **判定の目安**：参照の前に NULL でない保証がなければ `true_bug`（先に参照して落ちる）。保証があれば `false_positive`（後の確かめが冗長なだけ）。

## RESOURCE_LEAK

- **指摘**：確保したメモリ・開いたファイル・ソケットなどを、解放せずに失っている（変数がスコープを出る、上書きされる）。タグは `alloc_fn`・`var_assign`・`leaked_storage`・`leaked_handle`。
- **誤検知になりやすい形**：所有権が移っている（戻り値で返す、構造体のメンバや大域の表に入れる、登録の関数に渡す）。独自の確保・解放の関数を Coverity が知らない。
- **確かめ方**：確保した値が、どの経路で解放され、どこに渡されるかをたどる。漏れは途中の `return`（エラーの経路）に多い。渡した先の関数が保持するか（後で解放するか）を、その関数の中身で確かめる。
- **直し方の定石**：まわりの後始末の書き方に合わせる（関数に `goto cleanup` があればそこへ飛ぶ。なければ、その `return` の前で解放する）。解放の戻り値の扱い（`(void)fclose(fp);` など）もまわりに合わせる。
- **逸脱コメントのヒント**：「誤検知。buf は session_add()（src/session.c:61）で表に入り、session_close()（src/session.c:95）で解放されるため、漏れることはない。」
- **判定の目安**：解放も所有権の移動もない経路があれば `true_bug`（一度しか通らない起動時の処理でも、規則の違反としては本物）。所有権が移っていれば `false_positive`。プログラムの終わりまで持ち続ける設計（終了時に OS が回収する）なら `intentional`。

## USE_AFTER_FREE

- **指摘**：解放したメモリを、その後で参照したり、関数に渡したりしている。タグは `freed_arg`・`deref_after_free`・`pass_freed_arg`。
- **誤検知になりやすい形**：解放と参照が別の枝で、同じ実行では両方を通らない。解放の関数が、条件によっては解放しない（参照数が残るときなど）のに、Coverity がいつも解放すると見ている。
- **確かめ方**：解放した行から参照の行まで、通る枝の条件をたどる。解放の関数の中身（いつ本当に解放するか）を読む。
- **直し方の定石**：参照を解放の前に動かす。解放した直後にポインタへ NULL を入れ、後の参照で確かめる（まわりにその書き方があるとき）。
- **逸脱コメントのヒント**：「誤検知。obj_put()（src/obj.c:30）は参照数が 0 のときだけ解放し、ここでは呼び出し元が参照を持つため（src/obj.c:72）、解放後に参照することはない。」
- **判定の目安**：解放した後に参照する経路があれば `true_bug`（動けば壊れることが多いので、確信度が高ければ修正を強く勧める）。

## DOUBLE_FREE

- **指摘**：同じメモリを2回解放している。タグは `freed_arg`・`double_free`。
- **誤検知になりやすい形**：1回目と2回目が別の枝。1回目の後にポインタへ NULL を入れていて、2回目は NULL の解放（何もしない）になる。
- **確かめ方**：1回目の解放から2回目までの枝の条件と、ポインタへの代入をたどる。エラーの経路で、呼び出し元と呼ばれた側の両方が解放していないかを見る。
- **直し方の定石**：解放の責任を一方にまとめる。解放した後に NULL を入れる。
- **逸脱コメントのヒント**：「誤検知。src/cache.c:44 で解放した後に ptr へ NULL を入れており、src/cache.c:58 の free() は NULL を渡すだけで、2回解放することはない。」
- **判定の目安**：2回とも本当に解放する経路があれば `true_bug`。

## OVERRUN

- **指摘**：配列やバッファの範囲の外を読む・書く（添字が大きさ以上、コピーの長さが大きさを超える）。タグは `overrun-local`・`overrun-buffer-arg`・`overrun-buffer-val` など。
- **誤検知になりやすい形**：添字の値の範囲が、呼び出し元か直前の確かめで、大きさより小さいと決まっている（Coverity はループや別の関数の確かめを追いきれないことがある）。
- **確かめ方**：添字・長さの値を、定義元（マクロ、型の大きさ）と呼び出し元までたどり、とりうる最大の値を出す。終端文字の1バイト（`'\0'`）を含めて足りるかに注意する。大きさのマクロが1つのとき、そのマクロを使う場所すべてに同じ問題が出ていないかも見る。
- **直し方の定石**：根の原因（大きさのマクロの定義の誤り、終端の1バイトの足し忘れ）を1か所で直す。根を直せないときは、使う場所で範囲を確かめる。
- **逸脱コメントのヒント**：「誤検知。idx は parse_cmd()（src/cmd.c:20）で 0〜CMD_MAX-1 に限ってから渡すため、cmd_table の範囲（src/cmd.c:8）を超えることはない。」
- **判定の目安**：範囲を超える値が届く経路があれば `true_bug`。外から来る長さ（通信、ファイル）が届くなら、その長さの確かめがあるかで決める。

## BUFFER_SIZE

- **指摘**：コピーの関数（`memcpy`・`strncpy` など）に渡した大きさが、書き込み先より大きい、または `strncpy` で大きさが書き込み先と同じで、終端の `'\0'` が入らないことがある（BUFFER_SIZE_WARNING として出ることもある）。
- **誤検知になりやすい形**：書き込み先の後で、別の行が終端を必ず入れている。元の文字列の長さが、大きさより短いと決まっている。
- **確かめ方**：書き込み先の大きさ（定義）と、渡した大きさ・元の長さをたどる。コピーの後に終端を入れる行があるかを見る。
- **直し方の定石**：大きさを `sizeof(dst) - 1U` にして終端を入れる、まわりで使う安全なコピーの関数に合わせる。
- **逸脱コメントのヒント**：「誤検知。src/name.c:31 の strncpy() の直後に、src/name.c:32 で必ず name[NAME_LEN - 1] に終端を入れるため、終端のない文字列になることはない。」
- **判定の目安**：終端がないまま文字列として使う経路、または大きさを超えて書く経路があれば `true_bug`。

## STRING_OVERFLOW

- **指摘**：`strcpy`・`strcat`・`sprintf` などで、文字列を決まった大きさのバッファに入れるとき、入りきらないことがある。
- **誤検知になりやすい形**：元の文字列が定数か、長さを確かめた値で、終端まで含めて入りきる。
- **確かめ方**：元の文字列の最大の長さ（定数の長さ、確かめた長さ）と、書き込み先の大きさを比べる。`sprintf` は書式から最大の長さを出す（`%d` は符号を含めて 11 文字など）。
- **直し方の定石**：長さを渡す関数（`snprintf` など）に替え、切れたときの扱いをまわりに合わせる。MISRA の Rule 21.6（標準入出力の関数）を使えないプロジェクトでは、プロジェクトの関数に合わせる。
- **逸脱コメントのヒント**：「誤検知。ver は "v" と 3 桁までの数（src/ver.c:12 で 999 以下に限る）で、終端を含め 5 文字に収まり、buf[8]（src/ver.c:20）を超えることはない。」
- **判定の目安**：入りきらない長さが届く経路があれば `true_bug`。

## SIZEOF_MISMATCH

- **指摘**：`sizeof` の使い方が合わない（`malloc(sizeof(p))` のようにポインタの大きさを取っている、`memset(&s, 0, sizeof(other))` のように別の型の大きさを使っている）。
- **誤検知になりやすい形**：本当にポインタの大きさが欲しい（ポインタの配列を作る）。同じ大きさになるよう決めた型どうし。
- **確かめ方**：確保・コピーする対象の型と、`sizeof` の中の型・式を比べる。
- **直し方の定石**：`sizeof(*p)` や `sizeof(s)` のように、対象そのものから大きさを取る。
- **逸脱コメントのヒント**：「意図的。table はポインタの配列で、要素ごとに sizeof(char *) を確保する設計（src/tbl.c:15）であり、大きさの取り違えではない。」
- **判定の目安**：確保・コピーの大きさが対象より小さくなるなら `true_bug`。意図した大きさなら `intentional`。

## UNINIT

- **指摘**：値を入れる前の変数（または構造体のメンバ）を読んでいる。タグは `var_decl`・`uninit_use`・`uninit_use_in_call`。
- **誤検知になりやすい形**：
  - 値を入れない分岐は、実際には通らない（前の条件で決まっている）。
  - 出力引数で値を入れる関数（`get_value(&v)`）を、Coverity が知らないか、失敗のときも入れることを知らない。
- **確かめ方**：宣言から使う行まで、すべての分岐で値が入るかを見る。出力引数の関数の中身で、すべての戻り方で値を入れるかを確かめる。
- **直し方の定石**：宣言で初期化する（`int v = 0;`）。まわりが宣言で初期化しない書き方なら、値を入れない分岐で入れる。
- **逸脱コメントのヒント**：「誤検知。read_reg()（src/hal.c:40）はすべての戻り方で *val に値を入れるため、src/hal.c:88 で値のない v を読むことはない。」
- **判定の目安**：値の入らない分岐を通って読む経路があれば `true_bug`（MISRA C:2012 の Rule 9.1 は Mandatory）。

## NEGATIVE_RETURNS

- **指摘**：負の値（エラーの -1 など）を返すことがある関数の戻り値を、確かめずに、負であってはならない場所（添字、大きさ、`read` の長さ）に使っている。
- **誤検知になりやすい形**：この引数では負を返さない（固定の値、前に確かめた値）。
- **確かめ方**：関数が負を返す条件を中身で確かめ、この呼び出しで成り立つかをたどる。
- **直し方の定石**：使う前に `< 0` を確かめ、まわりのエラーの返し方にする。
- **逸脱コメントのヒント**：「誤検知。find_slot() は空きがないときだけ -1 を返し、呼び出し元 init()（src/slot.c:70）は空きを確かめてから呼ぶため、負の添字になることはない。」
- **判定の目安**：負の値が届く経路があれば `true_bug`。

## INTEGER_OVERFLOW

- **指摘**：整数の計算があふれ、その値を大きさ・添字・確保の長さなどに使っている（外から来た値の計算に多い）。
- **誤検知になりやすい形**：値の範囲が前の確かめで小さく決まっていて、あふれない。
- **確かめ方**：計算に入る値のとりうる範囲を、出どころ（外の入力か、内部の定数か）までたどり、最大の値で計算してみる。符号なしの回り込み（`0U - 1U`）も見る。
- **直し方の定石**：計算の前に上限を確かめる（`if (n > SIZE_MAX / size)`）。広い型で計算してから範囲を確かめる。
- **逸脱コメントのヒント**：「誤検知。count は recv_hdr()（src/net.c:51）で 64 以下に限ってあり、count * 16U は 1024 を超えず、あふれることはない。」
- **判定の目安**：あふれる値が届き、その値で範囲の外を触るなら `true_bug`。

## DIVIDE_BY_ZERO

- **指摘**：0 かもしれない値で割っている（`/`・`%`）。
- **誤検知になりやすい形**：割る数が、前の確かめか定義（0 でない定数、設定の下限）で 0 にならない。
- **確かめ方**：割る数の出どころをたどり、0 になりうるかを確かめる（設定の値、外からの値、計算の結果）。
- **直し方の定石**：割る前に 0 を確かめ、まわりのエラーの扱いにする。
- **逸脱コメントのヒント**：「誤検知。period は set_period()（src/timer.c:22）で 1 以上に限ってから保存するため、0 で割ることはない。」
- **判定の目安**：0 が届く経路があれば `true_bug`。

## TAINTED_SCALAR

- **指摘**：信用できない値（ファイル・通信・`ntohs` などで外から来た値）を、範囲を確かめずに、ループの回数・添字・大きさに使っている。タグは `tainted_data`・`lower_bounds`・`upper_bounds` など。
- **誤検知になりやすい形**：値は外から来るが、使う前に上限と下限の両方を確かめている（Coverity は別の関数の確かめを見落とすことがある）。外から来るように見えて、実は内部で作った値。
- **確かめ方**：値の出どころ（どの入力か）と、使う場所までの確かめを、上限・下限の両方でたどる。符号付きの値は負の値も考える。
- **直し方の定石**：使う前に上限と下限を確かめ、範囲の外ならまわりのエラーの扱いにする。
- **逸脱コメントのヒント**：「誤検知。len は check_frame()（src/frame.c:33）で 1〜FRAME_MAX に限ってから使うため、範囲の外を読むことはない。」
- **判定の目安**：外の値が確かめなしで届けば `true_bug`（攻撃者や壊れたデータで起こりうる）。

## DEADCODE

- **指摘**：条件がいつも同じになるため、決して実行されないコードがある。タグは `dead_error_condition`・`dead_error_line`。
- **誤検知になりやすい形**：マクロやビルドの設定（`#if`、構成のヘッダ）で、ほかの構成では実行される。念のための確かめ（防御のコード）を残している。
- **確かめ方**：条件をいつも同じにしている値（マクロ、定数、前の確かめ）を定義までたどる。その値がほかの構成やビルドで変わるかを、設定のファイルで確かめる。
- **直し方の定石**：本当に要らないなら消す（ほかの構成も確かめてから）。構成で変わるなら、残して逸脱にするのがふつう。
- **逸脱コメントのヒント**：「意図的。LOG_LEVEL は製品の構成で 0、デバッグの構成で 3 になり（include/config.h:12）、デバッグの構成ではこの処理が動く。」
- **判定の目安**：構成で動くなら `intentional`。どの構成でも動かず、書き間違い（条件の取り違え）なら `true_bug`。防御のコードなら `intentional`。

## UNREACHABLE

- **指摘**：`return`・`break`・`goto`・無限ループの後など、流れの上で決して届かないコードがある。
- **誤検知になりやすい形**：届かないのは、戻らない関数の後に置いた念のための `return`（コンパイラの警告を消すため）。
- **確かめ方**：届かない理由（前の `return`、戻らない関数）を確かめ、書き間違いで本来の処理が抜けていないかを見る。
- **直し方の定石**：要らないコードを消す。本来の処理が抜けているなら、流れを直す。
- **逸脱コメントのヒント**：「意図的。fatal() は戻らないが、コンパイラの警告を消すために置いた return（src/main.c:90）で、実行されないことは設計どおりである。」
- **判定の目安**：念のためのコードなら `intentional`。本来の処理が届かなくなっているなら `true_bug`。

## MISSING_BREAK

- **指摘**：`switch` の `case` の終わりに `break` がなく、次の `case` に流れる。タグは `unterminated_case`・`fallthrough`。
- **誤検知になりやすい形**：流れることが設計どおりで、コメント（`/* fall through */`）や属性がある。続けて行う処理を、わざと次の `case` に任せている。
- **確かめ方**：前後の `case` の処理と、コメント・設計の文書で、流れるのが意図かを判断する。
- **直し方の定石**：意図しないなら `break` を足す。意図なら、まわりの書き方（`/* fall through */` のコメント、`__attribute__((fallthrough))`、`[[fallthrough]]`）で明示する。MISRA C:2012 の Rule 16.3 を守るプロジェクトでは、意図でも処理を分ける。
- **逸脱コメントのヒント**：「意図的。case 2 から case 3 へのフォールスルーは、状態 2 の処理のあと状態 3 の処理を続けて行う設計（src/fsm.c:88 のコメントに記載）であり、break の書き忘れではない。」
- **判定の目安**：意図なら `intentional`。次の `case` の処理が誤って動くなら `true_bug`。

## CHECKED_RETURN

- **指摘**：戻り値でエラーを返す関数の戻り値を確かめていない（ほかの場所ではたいてい確かめている）。
- **誤検知になりやすい形**：失敗しても困らない（失敗の後の処理が同じ、ログに書くだけ）。前の処理で失敗しないことが決まっている。
- **確かめ方**：関数が失敗する条件と、失敗したときに後の処理がどうなるかを確かめる。
- **直し方の定石**：戻り値を確かめ、まわりのエラーの扱いにする。無視してよいなら `(void)` を付けて意図を示す（まわりにその書き方があるとき）。
- **逸脱コメントのヒント**：「意図的。led_set() の失敗は表示が変わらないだけで、後の処理に影響せず（src/ui.c:40）、戻り値を見ないのは設計どおりである。」
- **判定の目安**：失敗のまま進んで問題が起きるなら `true_bug`。無害なら `intentional`。

## COPY_PASTE_ERROR

- **指摘**：似たコードを写したときに、変数を1つ直し忘れている（`x` の処理の中に `y` が残っている）。タグは `original`・`copy_paste_error`。
- **誤検知になりやすい形**：同じ変数を使うのが正しい（両方の処理で同じ値を使う設計）。
- **確かめ方**：元のコード（`original`）と写したコードを並べ、どの変数が対応するかを見る。
- **直し方の定石**：直し忘れた変数を、対応する変数にする。
- **逸脱コメントのヒント**：「意図的。送信と受信の両方で同じ timeout を使う設計（src/link.c:14 のコメント）で、写し間違いではない。」
- **判定の目安**：写し間違いなら `true_bug`。意図なら `intentional`。

## NO_EFFECT

- **指摘**：何もしない文や、いつも同じ結果の比べ方がある（`x == 1;` の書き間違い、符号なしを `< 0` と比べる、自分自身への代入、配列の名前を NULL と比べる）。
- **誤検知になりやすい形**：型が構成で変わり、ほかの構成では意味がある（符号付きになるなど）。
- **確かめ方**：式の型と値の範囲を確かめ、書いた人の意図（代入のつもり、別の変数のつもり）を前後から読む。
- **直し方の定石**：意図した演算子・変数に直す。要らない比べ方を消す。
- **逸脱コメントのヒント**：「意図的。sensor_t は他の機種の構成で符号付きになり（include/types.h:20）、その構成では負の値を確かめるため、比べ方を残している。」
- **判定の目安**：書き間違いなら `true_bug`。構成で意味があるなら `intentional`。

## UNCAUGHT_EXCEPT

- **指摘**（C++）：投げた例外が、どこでも受け止められずに `main`・スレッドの入口・`noexcept` の関数・デストラクタの外へ出る（`std::terminate` で止まる）。
- **誤検知になりやすい形**：その例外は、その引数では投げられない。止まること（`terminate`）が設計どおり。
- **確かめ方**：例外を投げる関数から入口まで、受け止める `try` / `catch` があるかをたどる。投げる条件が成り立つかを見る。
- **直し方の定石**：入口（`main`、スレッドの関数）で受け止め、まわりのエラーの扱いにする。
- **逸脱コメントのヒント**：「誤検知。std::vector::at() は添字が範囲の外のときだけ投げ、ここでは size() 未満に限ってある（src/queue.cpp:41）ため、例外が出ることはない。」
- **判定の目安**：例外が出て止まる経路があれば `true_bug`。

## CTOR_DTOR_LEAK

- **指摘**（C++）：コンストラクタで確保したものを、デストラクタで解放していない。
- **誤検知になりやすい形**：所有権がほかのオブジェクトに移る。解放を別のメンバ関数（`close()`）で必ず行う設計。
- **確かめ方**：確保したメンバが、どこで解放されるか（デストラクタ、`close`、所有権の移動）をたどる。
- **直し方の定石**：デストラクタで解放する。外から見えるクラスの形（公開のメンバ、大きさ）を変える直し方（スマートポインタへの置き換え）は、外部の仕様を変えるので避けるか、超えた決まりとして書く。
- **逸脱コメントのヒント**：「誤検知。buf_ は Pool::release()（src/pool.cpp:77）に必ず返され、そこで解放されるため、漏れることはない。」
- **判定の目安**：解放されない経路があれば `true_bug`。

## UNINIT_CTOR

- **指摘**（C++）：コンストラクタが、メンバの一部に値を入れていない。
- **誤検知になりやすい形**：そのメンバは、使う前に必ず別のメンバ関数（`init()`）で値を入れる。
- **確かめ方**：値の入らないメンバが、値を入れる前に読まれる経路があるかをたどる。
- **直し方の定石**：メンバの初期化の並び（`: x_(0)`）か、宣言での初期化で値を入れる（まわりの書き方に合わせる）。
- **逸脱コメントのヒント**：「誤検知。state_ は使う前に必ず start()（src/conn.cpp:30）で値を入れ、start() の前に読む経路はない。」
- **判定の目安**：値を入れる前に読む経路があれば `true_bug`。

## そのほかのよく出るチェッカー

| チェッカー | 指摘すること | 見るところ |
|---|---|---|
| BAD_SHIFT | シフトの量が負か、型の幅以上 | シフトの量の範囲を出どころまでたどる |
| OVERFLOW_BEFORE_WIDEN | 狭い型で計算してあふれた後に、広い型へ入れている | 計算の前に広い型にする必要があるか、値の範囲で確かめる |
| SIGN_EXTENSION | 符号付きの値が広い型へ移るとき、符号が広がる | 負の値が入りうるか。`unsigned char` の値の扱い |
| CONSTANT_EXPRESSION_RESULT | 式がいつも同じ値になる（`x & 0` など） | 書き間違いか、構成で値が変わるマクロか |
| IDENTICAL_BRANCHES | if と else の中身が同じ | 写し間違いか、構成で中身が変わるか |
| RETURN_LOCAL | 自動変数のアドレスを返している | 呼び出し元がそのアドレスを使うか（使えば本物） |
| MISSING_RETURN | 値を返す関数で、値を返さずに終わる経路がある | その経路を通るか（MISRA C:2012 の Rule 17.4 は Mandatory） |
| ARRAY_VS_SINGLETON | 配列でない1つの変数を、配列として扱っている | 添字やコピーの長さが 1 を超えるか |
| LOCK / MISSING_LOCK | 鍵の取り忘れ・二重取り・外し忘れ、ほかの場所では鍵を取って触る変数を鍵なしで触る | その変数を同時に触るスレッド・割り込みがあるか |
| INFINITE_LOOP | 抜ける条件が変わらないループ | 割り込みやハードウェアで変わる値（`volatile` の有無）か |

ここにないチェッカーは、Coverity のチェッカーの説明を読み、ふつうの調べ方（警告経路を仮説として、条件を呼び出し元・定義までたどる）で調べます。
