# 自己診断のコマンドと項目

## 目次

- コマンド
- 項目
- 結果の値
- 結果のフォルダ

## コマンド

どれも `uv run --native-tls --quiet "<このスキルのフォルダ>/scripts/selftest.py" <コマンド> ...` で動かします。結果は JSON を1つ返します（`ok`、記録した項目の `checks[]`）。`<dir>` は `start` が返したフォルダです。

| コマンド | すること | 記録する項目 |
| --- | --- | --- |
| `start [--sections 1,2,3,4] [--repo "<リポジトリ>"] [--client "<使っているもの>"] [--dir "<フォルダ>"]` | 結果のフォルダを作る（既定は ホーム の下の `<このスキルのフォルダの名前>-results/<日時>`）。範囲の外の項目は skip にする。返す：`dir`、`checks[]`（範囲の項目） | 範囲の外 |
| `check-tools --dir "<dir>"` | uv・git・svn の版 | 1-7 |
| `sample --dir "<dir>"` | `assets/sample-target` を `<dir>/sample-target` にコピーし、git のリポジトリにして、push 先（`<dir>/sample-origin.git`）を付ける。前のものは消して作り直す。返す：`repo_root`、`filter`（`all.yaml`）、`output_dir` | 2-1 |
| `check-run --dir "<dir>" --run "<実行フォルダ>"` | 見本の実行フォルダを読み、一覧・作業・結論・グループ・成果物と作業中のファイルを確かめる。結論は `assets/expected.yaml` と比べる | 2-2〜2-6 |
| `check-refused --dir "<dir>" --refused yes\|no [--actual "<返事の要点>"]` | 書き戻しのツールが間違った確認の文字列を断ったか（`--refused`）と、偽の Coverity の書き戻しの記録（`.coverity-triage/fake-issues.yaml.writes.jsonl`）が空か | 2-7 |
| `check-apply --dir "<dir>" --run "<実行フォルダ>"` | 反映の計画（`apply-plan.json`）の逸脱が偽の Coverity に書き戻され、修正のブランチが push 先にあるか | 2-8 |
| `check-config --dir "<dir>"` | 対象のリポジトリの設定（URL、偽の Coverity でないか、結果の置き場所）、条件ファイル（ストリームが1つ）、認証情報の環境変数。返す：`filter_files`（③ の検索に使える条件ファイルの絶対パス） | 3-1 |
| `check-build --dir "<dir>"` | 対象のリポジトリを一時フォルダにコピー（git なら最新のコミット）し、設定の `verify.setup_command`（`{root}` はコピーの根）と `verify.build_command` を `verify.build_dir` で動かす。認証キーは渡さない。コピーは消す。`cov-build`・`cov-analyze`・`cov-commit-defects` があるかも見る | 4-1〜4-3 |
| `record --dir "<dir>" --id <項目> --status <値> --actual "<見たこと>" [--detail "<詳しいこと>"]` | 自分で見たことを記録する。`--stdin` なら標準入力の JSON（`id`、`status`、`actual`、`detail`） | 指定の項目 |
| `report --dir "<dir>"` | `<dir>/report.md` を書く。返す：`report`、`counts`、`failed[]`、`review[]`、`not_recorded[]` | なし |

## 項目

| 項目 | 確かめること | 判定 |
| --- | --- | --- |
| 1-1 | 見本のリポジトリで、接続を確かめるツールが ok を返す | エージェント |
| 1-2 | `/` の一覧に、表のスキルが出る | 利用者に聞く |
| 1-3 | 表の作業役のエージェントが一覧にあり、説明に「作業役」がある | エージェント |
| 1-4 | 表の検証役のエージェントが一覧にあり、説明に「検証役」がある | エージェント |
| 1-5 | 表の統合役のエージェントが一覧にあり、説明に「統合役」がある | エージェント |
| 1-6 | 表の統括エージェントが一覧にある | エージェント |
| 1-7 | uv と git がある | スクリプト |
| 1-8 | Web管理画面を開くツールがある（画面を使わないなら要らない） | エージェント |
| 2-1 | 偽の Coverity の見本のリポジトリを作れる | スクリプト |
| 2-2 | 一括実行が最後まで進み（`run.json` の `finished` が true。止められた `stopped` や、続けられずに止まった `halted` はその理由と一緒に失敗）、一覧（`summary.html`）と承認（`approvals.json`）ができる。`assets/run.schema.json`・`assets/approvals.schema.json`（一括実行の形の写し）があれば、`run.json` と `approvals.json` の形も確かめる | スクリプト |
| 2-3 | すべての作業が終わる（エラーと未処理がない） | スクリプト |
| 2-4 | 推奨が想定（`assets/expected.yaml`）と合う。合わなくても要確認（AI の結論は実行ごとに揺れる） | スクリプト |
| 2-5 | CID 20004〜20006 が1つのグループになる。一部が外れたら要確認 | スクリプト |
| 2-6 | 終わった作業ごとに、結果（`items/<ID>/result.json`）・詳細レポート（`cid/<ID>.html`）・差分（`patches/<ID>-fix.patch`。差分だけがないときは要確認）がそろい、見本の作業中のファイルが変わらない | スクリプト |
| 2-7 | 間違った確認の文字列 `000000000000` では断られ、何も書き込まれない | エージェントとスクリプト |
| 2-8 | 逸脱が偽の Coverity に書き戻され、修正のブランチが push される | スクリプト |
| 3-1 | 対象のリポジトリの設定・条件ファイル・認証情報がそろう（偽の Coverity の設定なら要確認） | スクリプト |
| 3-2 | 接続を確かめるツールが 10 秒以内に ok を返す | エージェント |
| 3-3 | 条件ファイルで1件の検索ができる | エージェント |
| 3-4 | その1件の警告経路を取れる | エージェント |
| 4-1 | 設定のビルドのコマンドが、リポジトリのコピーで通る | スクリプト |
| 4-2 | `cov-build` と `cov-analyze` がある（ビルドでの検証か初回解析を使うとき。使わないなら記録だけ） | スクリプト |
| 4-3 | `cov-commit-defects` がある（初回解析を使うとき。登録は試さない） | スクリプト |

## 結果の値

| 値 | 報告での言葉 | 意味 |
| --- | --- | --- |
| `pass` | 成功 | 確かめたとおり |
| `fail` | 失敗 | 直すことがある（理由は「詳しいこと」） |
| `review` | 要確認 | 人が見て決める |
| `skip` | 未実施 | 範囲の外か、前の項目が失敗して確かめられない |
| `info` | 記録 | 今の設定では要らないものの記録（スクリプトだけが使う） |

## 結果のフォルダ

| ファイル | 中身 |
| --- | --- |
| `selftest.json` | 項目ごとの記録（伏せ字。パスはホームからの `~/…`） |
| `report.md` | 報告（伏せ字） |
| `sample-target/`、`sample-origin.git/`、`coverity-triage-out/` | ② の見本のリポジトリ、その push 先、実行フォルダ |

伏せ字にするもの：認証キー（とその環境変数の値）、ユーザー名、Coverity の URL のホスト名と、ほかの URL のホスト名（`127.0.0.1` と `localhost` を除く）、IP アドレス、メールアドレス、ホームのフォルダ（`~` にする）。
