# 評価基準ごとの確かめ方

`assets/criteria.json` の、`scope` が `item` の20個の基準で、何を見て、どんなときに `ok: false` にするかです。基準の文そのものは `criteria.json` にあります。

## 調べ方（C-01〜C-05）

| 基準 | 見ること | `ok: false` にする例 |
| --- | --- | --- |
| C-01 呼び出し元 | 経路の条件を、すべての呼び出し元で確かめたか | 呼び出し元の1つが条件を満たすのに「成り立たない」としている／呼び出し元を見ずに「宣言が許すから」で本物のバグにしている |
| C-02 判定区分 | 判定が、自分で読んだ経路の成り立ちと合うか | 経路が成り立たないのに true_bug／成り立つのに false_positive |
| C-03 確信度 | 確信度の基準（高：最後まで追えた、中：一部が推定、低：コードで決められない・ずれがある）と理由が合うか | 推定が混じるのに high／理由が「確かめた」だけで、どの基準かが分からない |
| C-04 推奨 | 判定と推奨の組が決まりどおりか（true_bug → 修正、誤検知・意図的 → 言い切れるときだけ逸脱、undetermined → 確信度 低） | 言い切れない逸脱コメントなのに逸脱を推奨／undetermined なのに確信度が low でない |
| C-05 両方の案 | 修正案と逸脱案の両方があるか（最新で直っているときは、修正案にそのことが書いてある） | 修正案か逸脱案のどちらかがない／中身が空 |

## 修正（C-06〜C-08）

差分がないとき（最新で直っている、など）は、`ok: true` にして `detail` にそのことを書きます。

| 基準 | 見ること | `ok: false` にする例 |
| --- | --- | --- |
| C-06 最小 | 警告をなくすのに要る行だけを変えているか | 関係のない整形・名前の変更・まとめての書き直しがある |
| C-07 外部仕様 | 引数・戻り値・公開ヘッダ・グローバル変数の形を変えていないか | 戻り値の意味が変わる／公開の宣言が変わる（`exceeded_constraints` に書いてあれば、理由が妥当かを見る） |
| C-08 新しい違反 | 暗黙の型変換を増やしていないか、出口を増やすなら既存の書き方か | 符号の違う比べ方を足している／周りにない `return` の書き方 |

あわせて、修正が ★ に至る経路を断っているかを見ます。断っていなければ、C-02 か C-06 の `detail` に書き、差し戻します。

## 逸脱コメント（C-09〜C-11）

| 基準 | 見ること | `ok: false` にする例 |
| --- | --- | --- |
| C-09 形 | 日本語、見出しなし、判定区分のあと1〜2文、200文字以内か | 201文字以上／箇条書き／改行 |
| C-10 順と場所 | 判定区分 → 理由 → 場所の順か。場所が実際のコードと合うか | 「誤検知。」で始まらない／書かれた行に、その処理がない |
| C-11 書かないこと | 条件・但し書き・推量・調べた過程・推奨や依頼がないか | 「ただし」「〜の場合に限る」「おそらく」「確認してください」「修正を推奨」 |

## 結果の書き方（C-12〜C-15）

| 基準 | 見ること | `ok: false` にする例 |
| --- | --- | --- |
| C-12 根拠の場所 | evidence の行を開いて、書かれたとおりのコードがあるか。パスはリポジトリからか | その行にそのコードがない（差し戻し）／ファイルがない／絶対パス |
| C-13 形 | 決まった項目だけで、文字列が空でないか。1件の作業（グループでない）では `group_excluded_cids` はなくても空でもよく、`revision_drift.detail` と evidence の `note` は空でよい（どれも ok: true） | 余計な項目／空の summary |
| C-14 見立てと経過 | summary が40文字ほどで決め手を言っているか、rationale が経路を順にたどっているか | summary が「NULL の警告」のように決め手がない／rationale が結論だけ |
| C-15 書く前の確かめ | 修正するフォルダを直したか（差分がある、または最新で直っている）、調べるコードを変えていないか | 差分がないのに already_fixed_on_latest が false |

## グループ・統合とチェッカー（C-20〜C-23、C-28）

| 基準 | 当てはまるとき | 見ること | `ok: false` にする例 |
| --- | --- | --- | --- |
| C-20 統合 | 統合した作業 | 原因が1つで、1か所の修正（か1つの理由）ですべて片付くか。CID は10件まで | 近いだけで原因が違う CID がある（差し戻し） |
| C-21 標準チェッカー | MISRA・CERT でない警告 | NULL：呼び出し元の保証・直前の検証・戻らない関数。RESOURCE_LEAK：所有権が移るか。OVERRUN：添字と終端の1バイト。UNINIT：到達しない分岐と出力引数。DEADCODE・MISSING_BREAK：構成や設計なら意図的 | 戻らない関数を見落として本物のバグにしている |
| C-22 MISRA | MISRA の警告 | 本当の違反か、規則の対象外か、設計上必要か。Mandatory は逸脱できない | Mandatory の規則なのに逸脱を推奨 |
| C-23 CERT | CERT の警告 | 攻撃者が入力を制御できる経路か、入力の出どころをたどったか | 外からの入力が届くのに、届かないとしている |
| C-28 言い切れないとき | いつも | 条件を付けないと言い切れないなら、推奨が修正になっているか。推奨が修正のときの逸脱案が、言える範囲だけを書いた形（「本物の不具合。…（ファイル:行）…、直さない理由は説明できない。」など）なら、それで合っている（C-09〜C-11 も、これだけで ok: false にしない） | 但し書きが要る理由なのに逸脱を推奨 |

当てはまらない基準は、`ok: true`、`detail` を「対象外（MISRA の警告ではない）」のように書きます。

## 差し戻しか、要確認か

- 差し戻し：コードを見ればはっきり誤りと言え、直す点を1つずつ書けるとき。
- 要確認：誤りとは言い切れないが、確信度を下げるべき、または人が見るべき点があるとき（`confidence_cap` を書く）。
- 合格：直すべき点がないとき。言い回しの好みは、合格のまま `detail` に書いてよい。
