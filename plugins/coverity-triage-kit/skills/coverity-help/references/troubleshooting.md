# 困ったとき

まず、点検のスクリプトの `check` で状況を確かめます。`ng` の行の `fix` が直し方です。
部品は役割で呼びます。呼び方は SKILL.md の「使う部品」の表にあります。

## 目次

- Coverity とつながらない
- uv がない・スクリプトが動かない
- Coverity との通信の部品（MCP サーバー）が動かない
- 画面が開かない（Web管理画面）
- 結果と設定の画面
- 設定のエラー
- 実行が止まった・進まない
- 許可の確認が何度も出る
- 反映のエラー

- 文字化け（Windows）
- 長いパス（Windows）

## Coverity とつながらない

まず、Coverity との通信の部品の、接続を確かめるツールで確かめます（`repo_root` にリポジトリの絶対パス）。

| 表示・症状 | 原因と直し方 |
| --- | --- |
| HTTP 401、「認証に失敗しました」 | ユーザー名か認証キーの誤り、または認証キーの期限切れ。Coverity で認証キーを作り直し、準備のスキルの手順で、ターミナルの伏せ字の欄から入れ直す（チャットに書かない） |
| HTTP 403 | ユーザーに「Access Web services」の権限がない、またはストリームを見る権限がない。Coverity の管理者に頼む |
| HTTP 5xx | Coverity のサーバーの問題。しばらく待ってからやり直す。続くときは管理者に連絡する。一括のトリアージは、そこで止まる |
| ユーザー名か認証キーがない | 環境変数 `COV_USER` / `COV_AUTH_KEY`（設定で名前を変えていればその名前）がない。準備のスキルで入れる。Windows で保存した直後は、Copilot CLI を起動し直すと確実 |
| 時間切れ、「接続できません」 | URL の誤りか、社内のネットワークに入っていない。ブラウザーで同じ URL を開けるか確かめる |
| `CERTIFICATE_VERIFY_FAILED`、`UnknownIssuer` など証明書のエラー | 社内の CA 証明書が OS に入っていない。`coverity.ca_file` に CA 証明書のファイルを書く。uv のコマンドから `--native-tls` を外さない |
| プロキシのエラー（407 など）、社外へ出られない | 環境変数 `HTTPS_PROXY` が要るか、社内の担当に確かめる。Coverity が社内なら、`NO_PROXY` にそのホストを足す |
| 「http です」の注意 | `coverity.url` が `http://`。認証キーが暗号化されずに送られる。https が使えるか管理者に確かめる |
| 条件の値が Coverity に知られていない、と出た | その値（チェッカー、分類など）を外して続けている。条件ファイルの綴りを確かめる |
| 警告経路を取るときに、渡したストリームに CID がない、と出た | ストリームは省ける（Coverity との通信の部品が、見えるストリームから CID を探す）。示されたほかのストリームを使うか、ストリームを省いてやり直す。見えるストリームが 100 を超えるときだけ、ストリームを渡すよう求められる |

## uv がない・スクリプトが動かない

| 症状 | 直し方 |
| --- | --- |
| `uv` が見つからない | 準備のスキルの手順で入れる。入れた後、Copilot CLI を起動し直す（PATH を読み直すため） |
| 初めての実行が遅い・ライブラリを取れない | 初回は uv がライブラリを取る。社内のプロキシの設定（`HTTPS_PROXY`）を確かめる |
| `invalid peer certificate` | uv が社内の証明書を信頼していない。コマンドの `--native-tls` を外していないか確かめる |
| スクリプトが `ok: false` を返した | `error` と `problems` に理由がある。同じことを手で代わりにしない。理由を直してから、もう一度動かす |

## Coverity との通信の部品（MCP サーバー）が動かない

症状：Coverity のツールが見つからない、起動に失敗する。

1. `/mcp` で、Coverity との通信の部品の名前が出ていて、つながっているか見る。
2. uv があるか確かめる（上の節）。
3. 初めて使う前に、その部品の README のとおりに Python の環境を用意しておくと、起動の時に何も取りに行かない。
4. Copilot CLI は、MCP サーバーに PATH のほかの環境変数を渡さない。Windows では、サーバーがユーザーの環境変数を直接読む。ほかの OS では、その部品の README のとおりに、認証情報を渡す登録をし直す。

## 画面が開かない（Web管理画面）

チャットで頼んでも画面が開かず、「エクステンションが読み込まれていない」と言われたときは、次の3つのどれかです。

1. 試験的な機能が無効：`copilot --experimental` で起動する（一度付けると設定に残る）。起動しているときは `/settings experimental on`（自動で起動し直し、今の会話は終わる）。
2. 読み込みの確認を断った：Copilot CLI を起動し直し、`Extension "plugin:<プラグインの名前>:<エクステンションの名前>" wants elevated permissions` の確認を許可する（続けて2回出ることがある）。「Yes, and always allow … in this directory」（Git のリポジトリなら `in this repo`）を選ぶと、次からは出ない。
3. `/extensions mode` が Disabled：`/extensions mode` で Load & Augment か Load Only に戻す（Disabled は次のセッションにも残る）。

| ほかの症状 | 直し方 |
| --- | --- |
| 「いまの実行が終わるまで、新しい作業は始められません」 | 実行中。今の画面で様子を見る。変えた作業は、画面で止めてから頼み直す |
| URL が開けない | Copilot CLI を動かしているマシンのブラウザーで開く。Copilot CLI を終えると画面も終わる |
| 画面の更新が止まった | `/clear` をすると止まる。もう一度頼むと、前の実行が途中で切れたことが示される |
| 開始に失敗し、準備の画面に戻った | 画面に理由が出る。設定がないときは、準備のスキルで準備する |

## 結果と設定の画面

| 症状 | 直し方 |
| --- | --- |
| ブラウザーが出てこない | 返った URL をブラウザーに貼って開く |
| 「forbidden」、アドレスで開いてくださいと出る | URL の合言葉（`?t=…`）がないか古い（サーバーが起動し直した）。画面のスキルで開き直し、新しいタブを使う |
| 接続が拒否された | サーバーが止まっている（2時間使わなかった、「サーバを止める」を押した、PC を再起動した）。画面のスキルで開き直す。社内のプロキシで `127.0.0.1` に届かないときは、ブラウザーのプロキシの例外に `127.0.0.1` と `localhost` を足す |
| 承認を選べない | その警告はまだ終わっていない。統合か確かめを使う実行では、一覧ができるまで選べない |
| 「逸脱の内容に直すところがあります」 | Classification / Action / Severity / コメントのどれかが空か、200 文字を超えている。表示された項目を直す |
| 反映した後に承認を変えた | 変えても、反映した内容（Coverity の分類、push したブランチ）は元に戻らない |

## 設定のエラー

| 表示 | 直し方 |
| --- | --- |
| 設定ファイルがない | リポジトリの一番上のフォルダを開いているか確かめる。まだなら準備のスキルで作る |
| YAML の書式が正しくない | 表示された行を直す（字下げはスペース、タブは使わない）。`:` の後にスペースを入れる |
| 条件ファイルが見つからない | 名前の誤り。点検の `check` に、ある条件ファイルが並ぶ |
| 「条件にはストリームを 1 つだけ指定してください」 | 条件ファイルの `streams` を1つにする |
| 「出力先がリポジトリの中です」 | `output_dir` をリポジトリの外にする（既定 `../coverity-triage-out`）。中だと、結果を誤ってコミットするおそれがあるため、始めない |
| `parallel` などの値の範囲 | settings.md の範囲にする（`parallel` 1〜8、`agents.max_rework` 0〜2） |
| 初回解析のビルドのコマンドがない | `verify.initial` か `verify.default` を使うのに `verify.build_command` が空。準備のスキルの「ビルドでの検証」で設定する。その実行だけ使わないなら「解析はしないで」 |

## 実行が止まった・進まない

点検の `run` で、作業ごとの状態を見ます。作業ごとの段と経過の時間は、一括実行のスキルの様子を見るコマンドで見られます。

| 起きたこと | どうなるか・すること |
| --- | --- |
| 「⚠ 停止?」が出た | 10 分（初回解析は 30 分）動きがない。時間がかかっているだけのこともある。続くときは、`parallel` か件数を減らす |
| 作業エージェントがない・起動できない（「その役のエージェントがない」） | その作業は「処理できなかった作業」になる。プラグインを入れ直すか、`/agent` の一覧にそのエージェントがあるか確かめる。汎用のエージェントでは代わりにしない |
| 処理できなかった作業がある | 一覧に理由がある。直して、一括実行のスキルで再開すると、その分だけやり直す |
| 未検証 | 確かめのエージェントが動けなかった。確信度は作業エージェントのまま。詳細レポートを人がいつもより丁寧に見る |
| 初回解析が失敗した | トリアージを始めずに止まる。実行フォルダの `analysis/initial.log` の最後を見る。ビルドのコマンド、`cov-analyze` の引数、登録の権限を確かめ、直して再開する |
| `verify.timeout_minutes` を超えた | ビルドが入力待ちで止まっていないか確かめる。ふだんから長いなら値を大きくする |
| チャットを閉じた・PC を再起動した | 実行は途中のまま残る。一括実行のスキルで再開する |
| 別の版のスクリプトで作った実行だと言われた | 実行フォルダを作ったときと今で、スクリプトの版が違う。その実行は変えない。新しく実行する |
| 一覧に出るが続きからできない実行がある | 別の形で作られた実行フォルダ（元のプラグインの実行など）。見るだけ。続きからも反映もしない |

## 許可の確認が何度も出る

実行フォルダはリポジトリの外にあるので、エージェントがそこに書くたびに、Copilot CLI がパスの許可を求めます。`uv run` と Coverity のツールの初めての呼び出しも許可を求めます。始める前に、usage.md の「許可を前もって与える」の、どちらかを1回します。

- `/add-dir "<output_dir>"` の後、最初の確認で「このセッションでは許可」を選ぶ。
- `copilot --add-dir "<output_dir>" --allow-tool 'shell(uv:*)' --allow-tool write --allow-tool '<登録名>(<読むツール>)' …` で起動し直す（`<登録名>` は Coverity との通信の部品の名前。読むツール（接続の確かめ・警告の検索・警告の詳細・反映の確かめ）ごとに `--allow-tool '<登録名>(<そのツールの名前>)'` を並べます（ツールの名前は、一括実行が示す許可の案内か、Coverity との通信の部品の README にあります）。書き戻すツールは前もって許可しません。反映のときに確認が出ます。）。

## 反映のエラー

| 表示 | 直し方 |
| --- | --- |
| 確認の文字列が反映の内容と合わない | 確かめた後に内容が変わった（画面で承認を変えた など）。もう一度、反映のスキルで確かめから始める |
| 一覧がない | その実行はまだ終わっていない。一括実行のスキルで再開して、最後まで進める |
| push できない | git の認証かリモートの権限。いつもの方法で `git push` できるか確かめる |
| svn の差分を当てられない（競合） | 修正を作った後で同じ箇所が変わった。`patches/` の差分を見て、手で直す |
| 「修正」なのに差分がない | 最新のリビジョンで直っていて、修正案がない。「反映しない」にする |

一部が失敗しても、成功した分は反映済みです。原因を直して、もう一度反映すると、残りだけを行います。

## パスの対応づけ

Coverity の警告のパスと、リポジトリのパスが違うことがあります（解析したマシンのフォルダの名前など）。

- 対応づけの順：そのまま → `coverity.path_strip_prefixes` を外す → リポジトリにある、いちばん長い末尾の一致。
- 結果に「パスを自動で対応づけました」と出たら、合っているか確かめ、`coverity.path_strip_prefixes` に先頭を書くと確実になる。
- 「対応づけられませんでした」と出た警告は、コードを読めないので確信度が下がる。先頭を書くか、リポジトリの一番上のフォルダを開いているか確かめる。

## 文字化け（Windows）

- スクリプトは、PowerShell が読むコンソールの文字コードで結果を書く。手で `PYTHONIOENCODING` を設定していると、その文字コードで書く。文字化けするときは、`PYTHONIOENCODING` を消すか、`[Console]::OutputEncoding` と同じ文字コードにする。
- 設定ファイルとログは UTF-8。メモ帳などで保存するときは UTF-8 を選ぶ（BOM があっても読める）。
- ソースの日本語のコメントは、ファイルの文字コードのまま扱う。文字コードを変えない。

## 長いパス（Windows）

- git は `core.longpaths=true` で動かしている。それでも失敗するときは、Windows の長いパスを有効にする（管理者の設定）。
- 作業用のコピーは `<output_dir>/<実行>/work/w<n>` にできる。`output_dir` を短い場所（例 `C:/cov-out`）にすると、パスが短くなる。パスが 240 文字を超えそうなら、一括実行は止まり、`output_dir` を短くするよう伝える。
