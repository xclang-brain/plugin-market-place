# スキルと作業エージェントの置き換え

機器やつなぎ方が違うときは、スキルか作業エージェントを置き換えます。
- スキルを替えるときは、作業エージェントを変えずに、同じ名前のスキルをプロジェクトに置きます。または、別の名前のスキルを作り、作業エージェントを写して、その中のスキルの名前を書き替えます。
- 統括エージェント・検証エージェント・Web管理画面・ほかのスキルは変えません。

| 違うもの | 置き換えるもの | 例 |
| --- | --- | --- |
| ビルド・転送・ログ取得のやり方 | スキル | FTP でなく scp で送る。シリアルでなく SSH でログを取る |
| 機器の種類（作業の中身ごと違う） | 作業エージェント | Linux の機器でなく、マイコンのボードを扱う |

## しくみ

- 作業エージェントの定義（`.agent.md`）には、スキルについては、名前と役割しか書いてありません。スキルの使い方（コマンドや設定の項目）は、作業エージェントが、初めてそのスキルを使うときに SKILL.md を読んで知ります。
- スキルの SKILL.md には、ほかのスキルやエージェントのことは書いてありません。
- 統括エージェントと Web管理画面は、作業エージェントに、ふつうの文で頼むだけです。機器のことは書いてありません。

そのため、次の「約束」を守れば、置き換えたものも、そのまま組み合わさります。

## スキルを置き換える

### スキルの約束

ビルド・転送・ログ取得のスキルは、次の3つの依頼に応えます。

| 依頼 | 応え方 |
| --- | --- |
| 作業（例：「ビルドして」） | 作業をして、できたかどうか、何が起きたか、ログの場所を伝える。ログ取得なら、機器のコマンドの出力の行も返す |
| 設定ファイルの場所 | 設定ファイルの場所を伝える。なければ作る |
| 設定の確認 | 設定の抜けや誤りを調べて伝える。できれば、機器につながるかも試す |

設定ファイルは、次の形にします。設定のスキルが、この形のファイルなら、どれでも埋められます。

- YAML で、項目は1段だけ（`項目: 値`）にする。値は、文字列、数、true/false、リスト（`["a", "b"]`）のどれか。
- 項目ごとに、すぐ上に `#` で説明を書く。欠かせない項目には「（必須）」と書く。
- 例は `# 例：…`、選べる値は `# 選べる値：a / b / c` と書く。
- パスワードなど見せたくない値の項目は、名前に `password` などを含める（設定のスキルが、値を伏せる）。
- 環境変数で渡す項目は、`<項目>_env` という名前にする（例：`password` と `password_env`）。
- 置き場所は、プロジェクトのフォルダの `.embedded-debug-loop/<スキルの名前>.yaml` をおすすめします。そのフォルダに `.gitignore`（中身は `*`）がなければ作ります（パスワードやログを Git に入れないため）。

スキルの説明（SKILL.md）には、ほかのスキルやエージェントのことを書きません。

### 置き換え方は2つあります

| 方法 | すること | 向いている場面 |
| --- | --- | --- |
| A. 同じ名前で置き換える | プロジェクトに、同じ名前のスキル（例：`.github/skills/cross-compile/`）を置く。作業エージェントは変えない | そのプロジェクトだけ、やり方を替えたい |
| B. 別の名前で置き換える | 別の名前のスキルを作り、作業エージェントを写して、表の名前を替える | 元のスキルも残して、使い分けたい |

#### A. 同じ名前で置き換える

Copilot CLI は、同じ名前のスキルがプロジェクト（`.github/skills/`）や個人のフォルダ（`~/.copilot/skills/`）にあると、そちらを使い、プラグインのスキルは使いません（Copilot CLI 1.0.105 で確かめました）。

1. プロジェクトの `.github/skills/<同じ名前>/` に、新しいスキルを作ります（作り方は、下の B の手順1と同じです）。
2. `/skills list` で、そのスキルが「project」として出て、プラグインのほうが消えたことを確かめます。
3. 前のスキルの設定ファイル（`.embedded-debug-loop/<同じ名前>.yaml`）が残っていれば、消すか名前を変えます。項目が違うので、そのままでは使えません。
4. 作業エージェントに「セットアップしたい」と頼み、新しいスキルの設定を埋めます。

注意：個人のフォルダに、たまたま同じ名前（`deploy`、`setup` など）の別のスキルがあると、プラグインのスキルの代わりにそちらが使われます。作業エージェントの動きがおかしいときは、`/skills list` で確かめてください。

#### B. 別の名前で置き換える（例：転送を FTP から scp に替える）

1. 新しいスキルを作ります。
   - 置き場所：プロジェクトの `.github/skills/deploy-scp/`（自分だけで使うなら `~/.copilot/skills/deploy-scp/`）。
   - `SKILL.md` に、上の3つの依頼への応え方を書きます。今の `deploy` スキルの SKILL.md が手本になります（[GitHub の plugins/embedded-debug-loop/skills/deploy/](https://github.com/xclang-brain/plugin-market-place/tree/main/plugins/embedded-debug-loop/skills/deploy)）。
   - `SKILL.md` の先頭には、`name`（フォルダの名前と同じ）と `description`（何をするか・いつ使うか）を書きます。
   - 設定のひな形（例：`config-template.yaml`）と、作業をするスクリプトを置きます。
2. 作業エージェントを写します。
   - プラグインの `com.github.copilot/agents/device-worker.agent.md`（[GitHub](https://github.com/xclang-brain/plugin-market-place/tree/main/plugins/embedded-debug-loop/com.github.copilot/agents)）を、プロジェクトの `.github/agents/my-device-worker.agent.md` に写します。
   - プラグインのファイルを直接直すと、プラグインを更新したときに消えるためです。
3. 写した作業エージェントの「使うスキル」の表で、「機器への転送」のスキルの名前を `deploy-scp` に替えます。
   - 表には、SKILL.md の `name` をそのまま書きます。`embedded-debug-loop:` のような前置きは付けません。
   - ほかに替えるのは、次の2つです。
     1. 「B-1」の「/agent で device-worker（一覧では「device-worker · plugin」）を選び」を、「/agent で my-device-worker（一覧では「my-device-worker · project」）を選び」に。準備ができていないときに、利用者に正しいエージェントでセットアップしてもらうためです。
     2. 先頭の `description` を、違いが分かる説明に（例：「…転送は scp で行う」を足す）。`/agent` や Web管理画面の一覧で、元の作業エージェントと見分けるためです。
4. 新しいスキルを、それだけで試します（例：`/deploy-scp 設定を確かめて`）。
   - Copilot CLI を起動したままスキルを足したときは、`/skills reload` で読み直します（または、起動し直します）。エージェントは、足すとすぐに `/agent` に出ます。
5. `/agent` で `my-device-worker` を選び、「セットアップしたい」と頼みます。新しいスキルの設定ファイルも、対話で埋められます。
   - スキルどうしは互いを知らないので、同じ値（機器の IP アドレスなど）を、スキルごとに聞かれることがあります。
6. 「ビルドして、機器で動かして、ログを見せて」と頼み、全体がつながるかを確かめます。
7. 3段階目で使うときは、Web管理画面の設定で、作業エージェントに `my-device-worker` を選びます。

## 作業エージェントを置き換える

別の種類の機器に使うときは、その機器向けの作業エージェントを作ります。

### 作業エージェントの約束

統括エージェントは、作業エージェントに、ふつうの文で次の2つを頼みます。

| 依頼 | 応え方 |
| --- | --- |
| 準備の確認（作業はしない） | 1行目に「準備：できている」か「準備：できていない」。続けて、人が確かめたい設定の要約と、足りないもの |
| 試行（1回だけ。合否は判断しない） | 計画どおりに1回作業し、変えたこと・結果・ログの場所（絶対パス）を報告する |

- 統括エージェントから呼ばれたときは、利用者に質問できません。進めなくなったら、起きたことを報告して終えます。
- `/agent` で直接使うときは、質問しながら、自分で判断して繰り返してかまいません。

### 手順

1. `device-worker.agent.md` を写し、名前を替えます（例：`.github/agents/mcu-worker.agent.md`）。
2. その機器に合わせて、次を書き替えます。
   - 名前と役割の説明（ファイルの頭の `description` と、最初の段落）
   - 「使うスキル」の表（機器向けのスキルを先に作ります。作り方は、上の「スキルを置き換える」と同じです）
   - 「A-2」の例（合格の条件の例など）と、「調べ方のこつ」
   - 「ビルド」「転送」「ログ取得」の言葉。ファイルの全体で、その機器の作業の言葉（例：「書き込み」「実行」）に替えます。B-1・B-2 の返す形の行の名前も替えます。
   - 文の中の `device-worker`（B-1 のセットアップの直し方の文にあります）。新しい名前に替えます。
   - 「変えてよいもの」の「このプラグインのファイル」は、「このエージェントのファイル」に直します。
   - 「（一覧では「device-worker · plugin」）」は、プロジェクトに置いたエージェントなら「（一覧では「<新しい名前> · project」）」にします。
   - 書き替えたら、ファイルの中で「機器」「ビルド」「転送」「ログ取得」「クロスコンパイル」を探します。新しい作業に合わない言葉が残っていれば、替えます。
3. 次は、言葉を替えても、形と決まりは残します（上の「作業エージェントの約束」の部分です）。
   - 「2つの使われ方」の見分け方
   - B-1 の返事の1行目（「準備：できている」か「準備：できていない」）と、設定の要約・足りないものの並び
   - B-2 の「1回だけ試す」「合否は判断しない」「進めなくなったら止めて返す」と、変えたこと・結果・ログの場所（絶対パス）を返すこと
   - 「うまくいかなかったとき」の B の行（報告して終える）
4. `/agent` で選び、それだけで使えるかを試します。
5. 3段階目では、統括エージェントへの最初の頼みに「作業エージェントは mcu-worker で」と書くか、Web管理画面の設定で、作業エージェントに新しい名前を選びます。統括エージェントと検証エージェントは、変えずにそのまま使えます。
