# スキルと作業エージェントを置き換える

このプラグインは、ビルドしたプログラムを FTP で機器に送り、シリアル経由でログを取得します。
環境が違うときは、次の表のとおりに置き換えます。

| 環境の違い | 置き換えるもの | 例 |
| --- | --- | --- |
| ビルド・転送・ログ取得の方法 | スキル | FTP ではなく scp で送る |
| 機器の種類 | 作業エージェント（`device-worker`） | Linux の機器ではなく、マイコンのボードを使う |

どちらの場合も、統括エージェント（`orchestrator`）、検証エージェント（`verifier`）、Web管理画面は、そのまま使えます。

## スキルを置き換える

例として、FTP で転送するスキル `deploy` を、scp で送るスキルに置き換えます。

プロジェクトにプラグインと同じ名前のスキルを置くと、Copilot CLI はプロジェクトのスキルを使います。そのため、作業エージェントは変更不要です。

1. プロジェクトに `.github/skills/deploy/` フォルダを作り、新しいスキル（`SKILL.md`、スクリプト、設定ファイルのひな形）を置きます。作り方は、下の「新しいスキルの作り方」を見てください。
2. Copilot CLI で `/skills reload` を実行します。続けて `/skills list` を実行し、`deploy` が「project」の下に表示されることを確認します。
3. 前のスキルの設定ファイル（`.deploy/config.yaml`）があれば、削除するか名前を変えます。項目が違うと、そのままでは使えません。
4. `/deploy 設定を確認して` と入力し、新しいスキルが単体で動くことを確認します。
5. `/agent` で `device-worker` を選び、「セットアップしたい」と頼みます。新しいスキルの設定項目（接続先など）を聞かれるので、答えます。
6. 「ビルドして、機器で動かして、ログを見せて」と頼みます。機器の出力がログに出れば完了です。

注意：個人のフォルダ（`~/.copilot/skills/`）に同じ名前の別のスキルがあると、そちらが使われることがあります。動きがおかしいときは、`/skills list` で確認してください。

### 元のスキルも残したいとき

別の名前（例：`deploy-scp`）でスキルを作り、作業エージェントをコピーして、使うスキルの名前を書き換えます。

1. プロジェクトの `.github/skills/deploy-scp/`（自分だけで使うなら `~/.copilot/skills/deploy-scp/`）に、新しいスキルを作ります。
2. プラグインの `device-worker.agent.md`（[GitHub](https://github.com/xclang-brain/plugin-market-place/tree/main/plugins/embedded-debug-loop/com.github.copilot/agents)）を、プロジェクトの `.github/agents/my-device-worker.agent.md` にコピーします。
3. コピーしたファイルを書き換えます。
   - 先頭の `description`：元のエージェントと見分けられる説明にする（例：「転送は scp で行う」を足す）。Web管理画面で選ぶと、この説明が出ます。
   - 「使うスキル」の表：`deploy` を `deploy-scp` にする。`embedded-debug-loop:` のような前置きは付けない。
   - ファイルの中の `device-worker`：`my-device-worker` にする。「· plugin」は「· project」にする。
4. 上の手順の 2〜6 を、`deploy-scp` と `my-device-worker` で行います。
5. [3段階目](3-orchestrator.md)で使うときは、Web管理画面の設定で、作業エージェントに `my-device-worker` を選びます。

### 新しいスキルの作り方

プラグインの [deploy スキル](../../skills/deploy/) の `SKILL.md` と `README.md` が手本になります。

`SKILL.md` の先頭には、次の2つを書きます。

- `name`：スキルの名前。フォルダの名前と同じにする（同じ名前で置き換えるときは `deploy`）。
- `description`：何をするスキルで、いつ使うか。

作業エージェントは、スキルに次の3つを頼みます。`SKILL.md` に、それぞれの応え方を書きます。

| 依頼 | スキルがすること |
| --- | --- |
| 作業（「機器に送って」など） | 作業をして、成功したか、何が起きたか、ログの場所を返す。ログ取得のスキルは、機器のコマンドの出力も返す |
| 設定ファイルの場所 | 設定ファイルの場所を返す。なければ作る |
| 設定の確認 | 設定の抜けや誤りを返す。できれば、機器に接続できるかも試す |

設定ファイルは、`setup` スキルで入力できるように、次の形の YAML にします。

- 項目は1段だけ（`項目: 値`）にする。値は、文字列・数・true/false・1行のリスト（`["a", "b"]`）のどれか。
- 各項目のすぐ上に、`#` で説明を書く。必須の項目には「（必須）」と書く。
- 例は `# 例：…`、選べる値は `# 選べる値：a / b / c` と書く。質問のときの選択肢になります。
- パスワードなど、画面に出したくない値の項目は、名前に `password`・`secret`・`token` などを含める。`setup` スキルが値を隠します。
- 環境変数で値を渡す項目は、`<項目>_env` という名前にする（例：`password_env`）。

設定ファイルとログの場所も、ほかのスキルとそろえます。

- 設定ファイルは、作業フォルダ（ふつうは、Copilot CLI を起動したフォルダ）の `.<スキル名>/config.yaml` に置く。ログは `.<スキル名>/logs/` に置く。
- スキルは、`.<スキル名>/` に `.gitignore`（中身は `*`）がなければ作る。パスワードやログを Git に入れないためです。

スキルを単体でも使えるように、使い方は `README.md` に書き、テストは `tests/` に置きます。スキルのフォルダの中には、プラグインの名前、ほかのスキル、エージェントのことや、フォルダの外のパスを書きません。

## 作業エージェントを置き換える

例として、マイコンのボード向けの作業エージェント `mcu-worker` を作ります。

1. ボード向けのスキル（書き込み、ログ取得など）を、プラグインのスキルとは別の名前で作ります。作り方は「新しいスキルの作り方」と同じです。
2. プラグインの `device-worker.agent.md` を、プロジェクトの `.github/agents/mcu-worker.agent.md` にコピーします。
3. コピーしたファイルを書き換えます。
   - 先頭の `description` と最初の段落：何をするエージェントか
   - 「使うスキル」の表：1 で作ったスキルの名前
   - ファイルの中の `device-worker`：`mcu-worker`。「device-worker · plugin」は「mcu-worker · project」
   - 「変えてよいもの」の「このプラグインのファイル」：「このエージェントのファイル」
   - 「A-2」（不具合の調査）の例と「調べ方のこつ」：そのボードに合う内容
   - 「ビルド」「転送」「ログ取得」などの言葉：そのボードでの作業の言葉（例：「書き込み」「実行」）。最後に、ファイル全体で「機器」「電源」「ケーブル」などを検索し、合わない言葉が残っていないか確認します。
4. 次の部分は、言葉を変えても、決まりは変えないでください。統括エージェントは、この形で頼み、この形で返事が来ることを前提にしています。
   - 「2つの使われ方」：ほかのエージェントから呼ばれたかを判断する条件。呼ばれたときは、利用者に質問しない。
   - 「B-1」（準備の確認）：返事の1行目に「準備：できている」か「準備：できていない」と書き、続けて設定の要約と、足りないものを書く。
   - 「B-2」（1回の作業）：1回だけ作業し、合否は判断しない。進めなくなったら止めて返す。手順ごとの「できた／できなかった（理由）」、変えたこと、結果、ログの場所（絶対パス）を返す。
   - 「うまくいかなかったとき」の「B では」の行：報告して終える。
5. `/agent` で `mcu-worker` を選び、単体で動くことを確認します。
6. 3段階目で使うときは、Web管理画面の設定で、作業エージェントに `mcu-worker` を選びます。統括エージェントへの最初の依頼に「作業エージェントは mcu-worker で」と書いても選べます。
