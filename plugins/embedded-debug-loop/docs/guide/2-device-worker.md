# 作業エージェントを使う（2段階目）

このプラグインの使い方は3段階あり、段階ごとに AI に任せる範囲が違います（[README の「3つの段階」](../../README.md#3つの段階)）。
この文書では、2段階目として、作業エージェント（`device-worker`）に作業を任せる方法を説明します。
1段階目は [スキルを単体で使う](1-skills.md)、3段階目は [統括エージェントと Web管理画面](3-orchestrator.md) にあります。

作業エージェントは、組み込み機器の作業を受け持つ AI です。
チャットで依頼すると、不具合の原因を調べて、ソースを修正します。
修正したら、スキルでビルド・転送・ログ取得をして、直ったかをログで確認します。
この段階では、Web管理画面やほかのエージェントは使いません。チャットだけで使えます。

依頼できるのは、次の4つです。

- セットアップ
- 不具合の調査と修正
- ビルド・転送・ログ取得を1回だけ実行する
- 設定の確認

## 始め方

1. プロジェクトのフォルダで、Copilot CLI を起動します。
2. `/agent` を実行し、一覧から `device-worker · plugin` を選びます。チャットに「Selected custom agent: device-worker」と表示されます。
3. チャットで依頼します。依頼の例は、下の「依頼できること」にあります。

作業エージェントの正式な名前は、`embedded-debug-loop:device-worker` です。

### 使うときの注意

- 作業の途中で、Copilot CLI がコマンドの実行やファイルの変更の許可を求めます。答えるまで、作業は止まります。
- 確認の画面には、同じ種類の操作を、そのセッションのあいだ許可する選択肢があります。許可の確認を減らしたいときは、それを選びます。
- `/clear` を実行すると、エージェントの選択が既定（Default）に戻ります。続けて使うときは、もう一度 `/agent` で選びます。

## 依頼できること

### セットアップ

セットアップでは、ビルド・転送・ログ取得のスキルが使う設定ファイルに、値を書き込みます。
値は、質問に答えて決めます。

チャットで次のように依頼します。

```text
セットアップしたい
```

1. 作業エージェントが、ビルド・転送・ログ取得のスキルの設定ファイルを用意します。
2. 設定のスキル（`setup`）が、必須の項目のうち値が空のものを、1つずつ質問します。選択肢から選ぶか、値を入力して答えます。
3. 手順 2 で質問されなかった項目が、今の値と一緒に表で表示されます。このままでよいかを聞かれるので、変えたい項目があれば「直す項目を選ぶ」と答えます。
4. 作業エージェントが、3つのスキルで設定を確認し、結果を伝えます。転送とログ取得では、機器に接続できるかも確認します。

手順 2 と 3 は、ビルド・転送・ログ取得の設定ファイルごとに、順に行います。
手順 4 で問題がなければ、セットアップは完了です。
問題があれば、作業エージェントが足りないものを伝え、直すかを聞きます。

次の3つの項目は必須ではないので、手順 2 では質問されません。
ただし、機器でプログラムを動かすには、値が必要です。
3つの項目は、それぞれの設定ファイルの表（手順 3）に出ます。そこで「直す項目を選ぶ」と答えて、値を入力します。

- `sdk_env`（ビルド）：SDK の環境設定ファイルのパス。機器向けにビルドするときに必要です。例：`/opt/poky/4.0/environment-setup-cortexa7t2hf-neon-poky-linux-gnueabi`
- `file_mode`（転送）：送った後にファイルに付ける権限。機器でプログラムを実行するときに必要です。例：755
- `commands`（ログ取得）：機器で実行するコマンド。機器でプログラムを動かしてログを取るときに必要です。例：`["/opt/myapp/my_app"]`

一部だけを直したいときは、「転送の設定だけ直したい」のように依頼します。

### 不具合の調査と修正

症状と期待する結果を書いて依頼すると、作業エージェントが原因を調べて、ソースを直します。

チャットで次のように依頼します。

```text
sensor_app を機器で動かすと、AVG=3 と出ます。正しくは AVG=25 です。原因を調べて直してください。
```

依頼には、次のことも書けます。

- 合格の条件（例：「ログに AVG=25 と出る」）
- 繰り返しの上限（例：「3回まで」）
- 変えてはいけないファイルなど、守ってほしいこと（例：「main.c は変えないで」）

ソースを直してから、ビルド・転送・ログ取得をするまでの1回分を「試行」と呼びます。
作業エージェントは、次の順に進めます。

1. 合格の条件を決めます。依頼に期待する結果（例：「正しくは AVG=25」）があれば、それを合格の条件にして伝えます。なければ質問します。
2. 設定がそろっているかと、機器に接続できるかを確認します。確認の結果（使う機器・ポート・コンパイラー）を伝えます。足りなければ、セットアップをするかを聞きます。
3. 今のソースのまま、ビルド → 転送 → ログ取得をして、症状を確認します。
4. 原因の見当をつけてソースを直し、ビルド → 転送 → ログ取得をします。ログを見て、直ったかを判断します。
5. 直るまで、手順 4 の試行を繰り返します。試行は 5 回までです。依頼に回数を書けば、その回数までになります。
6. 結論（直ったか、原因、変えたところ）、試行ごとの結果の表、ログの場所を報告します。

### ほかの依頼

次のような依頼もできます。

| 依頼の例 | 作業エージェントがすること |
| --- | --- |
| 「ビルドして、機器で動かして、ログを見せて」 | ビルド・転送・ログ取得を1回だけして、結果とログを見せる |
| 「転送の設定を確認して」 | 転送のスキルで、設定と機器への接続を確認する |

## 質問されるとき

作業エージェントは、チャットに質問を出します。選択肢を選ぶか、文を入力して答えます。
主に次のときに質問します。

- 合格の条件が分からないとき
- 設定が足りないとき
- 転送やログ取得が失敗したとき
- デバッグのためにソースに足した出力（printf など）を、作業の終わりに残すか消すかを決めるとき

## 失敗したとき

ビルド・転送・ログ取得が失敗したとき、作業エージェントは次のようにします。

- ビルドが失敗したとき：作業エージェントの変更が原因なら、直してビルドし直します（1回の試行で2回まで）。そうでなければ、止めて伝えます。
- 転送やログ取得が失敗したとき：同じ操作は繰り返しません。起きたことと、確認するとよいこと（電源、ケーブル、設定）を伝えて、どうするかを聞きます。

## 変えるもの・変えないもの

作業エージェントが変えるのは、次の2つです。

- プロジェクトのフォルダの中のソース
- スキルの設定ファイル（セットアップで、あなたが答えた値だけを書き込みます）

プラグインのファイルと、スキルのフォルダの中のファイル（`SKILL.md` やスクリプトなど）は変えません。
変えてはいけないファイルがあれば、依頼に書いてください。

## 統括エージェントから呼ばれたとき

3段階目では、統括エージェント（`orchestrator`）が、この作業エージェントを呼んで作業を依頼します。
このときは質問をせず、依頼されたことだけをします。
依頼されるのは、準備の確認（設定と機器への接続の確認）か、1回の試行です。
結果は、統括エージェントが読む決まった形式で返します。
直ったかどうかは、作業エージェントではなく、検証エージェント（`verifier`）が確認します。
3段階目の使い方は、[統括エージェントと Web管理画面](3-orchestrator.md) を見てください。
