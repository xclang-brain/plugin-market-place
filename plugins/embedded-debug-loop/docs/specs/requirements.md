# embedded-debug-loop 仕様書

この文書は、利用者から見た embedded-debug-loop の振る舞いを決める。
中のしくみは [設計書](../design/design.md) に書く。この仕様の元になる決まりは、[憲章](../constitution.md) にある。

- バージョン：0.3.0

## 1. 目的

embedded-debug-loop を使うと、AI が組み込み機器の C/C++ の不具合を調べて直す。
AI は、ソースの修正 → ビルド → 機器への転送 → 機器のログ取得 を繰り返す。

## 2. 3つの段階

embedded-debug-loop は、3つの段階に分かれる。利用者は、段階ごとに次のように使う。

| 段階 | 部品 | 利用者の使い方 |
| --- | --- | --- |
| 1 | スキル：cross-compile（ビルド）、deploy（機器への転送）、log-capture（機器のログ取得）、setup（設定） | コマンド `/embedded-debug-loop:<スキル>` で呼ぶ。AI が選んで使うこともある |
| 2 | 作業エージェント（`device-worker`） | `/agent` で選び、チャットで依頼する |
| 3 | 統括エージェント（`orchestrator`）、検証エージェント（`verifier`）、Web管理画面 | `/agent` で統括エージェントを選び、チャットで依頼する。伝えられた URL で Web管理画面を開き、「開始」を押す |

- REQ-001：1段階目は、2段階目と3段階目がなくても使える。2段階目は、3段階目がなくても使える。
  - 3段階目だけは、embedded-debug-loop のエクステンション（Web管理画面などを動かす部品）を、Copilot CLI が読み込む必要がある。
  - 1段階目と2段階目は、エクステンションを読み込まない設定（`extensions.mode` を `disabled` にした設定）でも使える。
- REQ-002：機器ごとに違うもの（ビルド・転送・ログ取得の方法と、その設定）は、1段階目と2段階目にだけ置く。3段階目には置かない。
- REQ-003：作業エージェントの定義ファイル（`device-worker.agent.md`）には、スキルについて、名前と役割だけを書く。
  - 定義ファイルの「使うスキル」の表で、スキルの名前を書き換えるだけで、別のスキルを使える。
- REQ-004：4つのスキルは、互いに依存しない。ほかのスキルの名前や中身を前提にしない。1つを置き換えても、ほかのスキルを直す必要はない。
- REQ-005：3段階目では、使う作業エージェントを、Web管理画面の「設定」画面で選ぶ。
  - 利用者がチャットの依頼に作業エージェントの名前を書けば、統括エージェントがその作業エージェントを選ぶ。エクステンションは、選んだ名前をその作業フォルダの設定として保存する。
  - 統括エージェントは、作業エージェントにふつうの文章で依頼する。そのため、作業エージェントを差し替えても、統括エージェントは変えずに使える。

## 3. 1段階目：スキル

### 3.1 共通の決まり

- REQ-101：ビルド・転送・ログ取得のスキルは、次の3つの依頼に応える。

  | 依頼 | スキルがすること |
  | --- | --- |
  | それぞれの作業（ビルド・転送・ログ取得）をする | 作業をして、成功したか、何が起きたか、ログの場所を伝える |
  | 設定ファイルの場所を聞く | 場所を伝える。ファイルがなければ、説明つきのひな形から作る |
  | 設定を確認する | 設定の抜けと誤りを伝える。転送とログ取得のスキルは、機器に接続できるかも試す。ビルドのスキルは、ビルドのコマンドとコンパイラーがあるかを確認する |

- REQ-102：ビルド・転送・ログ取得のスキルは、設定をスキルごとに1つの YAML ファイルに持つ。
  - 置き場所は、作業フォルダの `.<スキルのフォルダの名前>/config.yaml`。
  - 作業フォルダは、ふつうは Copilot CLI を起動したプロジェクトのフォルダ。
  - スキルのフォルダの名前を変えてコピーしたときは、変えた後のフォルダの名前を使う。
- REQ-103：スキルが作る設定ファイルには、各項目のすぐ上に、項目の意味を日本語のコメントで書く。必須の項目には「（必須）」と書く。
- REQ-104：パスワードは、設定ファイルに書くか、環境変数で渡す。
  - スキルは、パスワードを結果にもログにも出さない。
  - パスワードをチャットで入力すると、その値が Copilot CLI の画面と会話の履歴に残る。設定のスキルは、このことを利用者に伝える。そのうえで、環境変数で渡す方法か、利用者が自分でファイルに書く方法を勧める。
- REQ-105：スキルは、失敗したら、何が起きたかと、何を確認すればよいかを伝える。どちらも、利用者が読んで分かる文で書く。
- REQ-106：ビルド・転送・ログ取得のスキルは、作業のログをファイルにして、`.<スキルのフォルダの名前>/logs/` に残す。
- REQ-107：スキルは、機器に接続できないときは、接続をやり直さない。起きたことを伝えて終える。
- REQ-108：どのスキルも、そのフォルダだけで完結する。
  - プラグインをインストールしなくても、スキルのフォルダだけをコピーすれば使える。コピー先は、作業フォルダの `.github/skills/<名前>/` か `~/.copilot/skills/<名前>/`。
  - 呼び方は `/<名前>`。名前は、SKILL.md の `name:` で決まる。
  - 設定とログのフォルダの名前は、スキルのフォルダの名前で決まる。そのため、名前を変えてコピーするときは、フォルダの名前と `name:` を同じ名前に変える。
  - フォルダの中の説明は、プラグインやほかの部品を知らなくても読める。スキルは、その説明のとおりに動く。
  - フォルダの中に、人向けの使い方（`README.md`）とテスト（`tests/`）を持つ。
  - `README.md` には、次のことを書く。
    - 何をするか
    - 必要なもの
    - 置き方
    - 呼び方
    - 設定ファイル（あれば）
    - 結果とログの見方
    - うまくいかないとき
    - テストの動かし方

### 3.2 cross-compile（ビルド）

- REQ-111：ビルドの前に、SDK の環境設定ファイル（例：`environment-setup-…`）を読み込む。そのあと、設定ファイルで指定したコマンド（例：make）でビルドする。
- REQ-112：ビルドの後に、設定ファイルで指定したファイルができたかを確認する。できたファイルの種類とサイズを伝える。
  - ファイルがビルドの前から変わっていなければ、前のビルドのままだと伝える。失敗にはしない。
- REQ-113：ビルドが失敗したときは、エラーの行を抜き出して伝える。

### 3.3 deploy（機器への転送）

- REQ-121：設定ファイルで指定したファイルを、FTP で機器に送る。
  - 送り先は、設定ファイルで指定した機器のフォルダ。そのフォルダがなければ作る。
- REQ-122：送ったファイルに、設定ファイルで指定した権限（例：755）を付ける。
- REQ-123：設定ファイルで、サム値（チェックサム）の種類を crc32 か sum32 にすると、ファイルごとにサム値のファイルを作り、一緒に送る。
- REQ-124：送った後に、機器に届いたファイルのサイズが、PC のファイルと同じかを確認する。
  - 機器の FTP サーバーがサイズの問い合わせに応じないときは、サイズを確認できなかったと伝える。

### 3.4 log-capture（機器のログ取得）

- REQ-131：シリアルポートで機器のコンソールに接続し、必要ならログインする。
- REQ-132：設定ファイルで指定したコマンドを、機器で順に実行する。プロンプトが戻るまでの出力を記録する。
  - 依頼でコマンドを指定すれば、その1回だけ、設定ファイルと違うコマンドを実行できる。
- REQ-133：コマンドを実行せずに、出力を記録するだけのこともできる。記録する時間は、設定ファイルで指定した秒数か、依頼で指定した秒数。
- REQ-134：機器から応答がないときは、ケーブルと電源を確認するよう伝える。

### 3.5 setup（設定）

- REQ-141：設定ファイル（YAML）の項目を、利用者に質問しながら埋める。
  - 依頼でファイルを渡されたときは、そのファイルを埋める。
  - ファイルが渡されなければ、項目の説明のコメントがある YAML を、作業フォルダの中から探す。見つかったファイルを候補として示し、利用者に選んでもらう。
  - 候補がなければ、ファイルの場所を利用者に聞く。
  - 設定のスキルは、自分の設定ファイルもログも持たない。作業フォルダに、新しいファイルやフォルダを作らない。
- REQ-142：質問には、選択肢を示せる質問のツール（ask_user）を使う。
  - 質問では、項目の説明と例を示す。
  - 必須の項目のうち、値が空のものから先に聞く。
- REQ-143：設定のスキルは、ファイルの中の説明だけを頼りに進める。ほかのスキルの名前や中身を前提にしない。
- REQ-144：書き込むときは、説明のコメントの行と、項目の並び順を変えない。
  - 最後に、埋めた結果を一覧で見せる。パスワードはマスクする。

## 4. 2段階目：作業エージェント

- REQ-201：作業エージェントは、利用者が `/agent` で選ぶと、チャットの依頼だけで動く。Web管理画面とほかのエージェントは使わない。
- REQ-202：セットアップを依頼されたら、次の順に進める。
  1. ビルド・転送・ログ取得のスキルで、それぞれの設定ファイルを用意する。
  2. 設定のスキルで、利用者に質問しながら設定ファイルを埋める。
  3. ビルド・転送・ログ取得のスキルで、設定を確認する。
- REQ-203：不具合の調査と修正を依頼されたら、次の順に進める。
  1. 合格の条件を決める。依頼に条件がなければ、利用者に質問する。
  2. 今の症状を確認する。
  3. ソースの修正 → ビルド → 転送 → ログ取得 → 合否の判断 を繰り返す。この1回を試行と呼ぶ。
  4. 直ったら終える。直らなくても、試行が上限の回数（既定 5 回）に達したら終える。
- REQ-204：利用者に質問するときは、必ず ask_user を使う。
- REQ-205：転送やログ取得で機器に接続できないときは、繰り返さない。起きたことを伝え、どうするかを利用者に聞く。
- REQ-206：終わったら、結論、試行ごとの表、ログの場所を報告する。
- REQ-207：ほかのエージェントから作業を依頼されたときは、利用者に質問しない。
  - 依頼されたことだけをする。依頼は、次のどちらか。
    - 準備の確認：ソースを変えず、作業もしない。ビルド・転送・ログ取得のスキルで設定を確認し、作業を始められるかと、足りないものを返す。
    - 1回の試行：依頼された計画どおりに、ソースの修正 → ビルド → 転送 → ログ取得 を1回だけする。
  - 報告の形は、[設計書](../design/design.md)の「3.4 統括エージェントと作業エージェント」に従う。
  - 合否は判断しない。
- REQ-208：作業エージェントが直すのは、プロジェクトのソースだけ。スキルの設定ファイルは、セットアップで利用者が答えた値を書き込むときだけ変える。

## 5. 3段階目：統括エージェントと Web管理画面

### 5.1 実行の流れ

- REQ-301：利用者は、`/agent` で統括エージェントを選び、チャットで依頼する。依頼に合格の条件がなければ、統括エージェントが ask_user で聞く。
- REQ-302：統括エージェントは、Web管理画面を起動し、作業エージェントに準備の確認を依頼する。そのあと、Web管理画面の URL を利用者に伝える。
- REQ-303：利用者が Web管理画面で「開始」を押すと、エクステンションがチャットに開始の知らせを送る。統括エージェントは、この知らせを受けて試行を始める。
  - チャットで別のエージェントが選ばれていたときは、エクステンションが先に統括エージェントに切り替える。
- REQ-304：統括エージェントは、試行ごとに次の順に進める。
  1. 計画を記録する。
  2. 作業エージェントに、1回の試行の作業を依頼する。
  3. 検証エージェントに、合否を確認させる。
  4. 評価を記録する。
  - 記録したものは、Web管理画面に出る。ファイルにも残る（5.3 実行の記録）。
- REQ-305：統括エージェントは、合格の条件をすべて満たすか、試行が上限の回数に達したら終える。
  - 作業エージェントが作業を進められなくなったときは、どうするかを ask_user で利用者に聞く。
- REQ-306：統括エージェントは、ファイルを直さず、コマンドも実行しない。
  - 定義ファイル（`orchestrator.agent.md`）の `tools` で、使えるツールを次のものだけにする：エージェントの呼び出し、読み取り、検索、質問、エクステンションのツール（記録、Web管理画面の起動、Issue の作成）。
  - 「開始」の後に、統括エージェントが次のツールを呼ぶと、エクステンションが拒否する。
    - ファイルを直すツール
    - コマンドを実行するツール
    - スキルを使うツール
- REQ-307：検証エージェントは、作業エージェントの報告に書かれたファイルを読み、合格の条件ごとに合否を判定する。ファイルは直さない。
- REQ-308：統括エージェントは、終えるときに、結論と振り返りを記録する。
  - 振り返りに改善点があれば、Issue にするかを ask_user で聞く。利用者が「する」と答えたら、GitHub に Issue を作る。作る先のリポジトリは、エクステンションの既定の値で決まる。
- REQ-309：統括エージェントは、作業エージェントが作業を報告した試行で、作業を依頼し直さない。もう一度作業を依頼するときは、試行の番号を1つ進め、計画の記録から始める。
  - 同じ試行で作業を依頼し直そうとすると、エクステンションが拒否する。

### 5.2 Web管理画面

Web管理画面には、「設定」「実行のようす」「結果」の3つの画面がある。

- REQ-311：Web管理画面は、Copilot CLI を動かしている PC（127.0.0.1）からだけ開ける。URL には、Web管理画面を起動するたびに作るトークンが入る。
- REQ-312：「設定」画面には、次の項目を置く。機器に固有の項目は置かない。
  - 「頼む作業」「合格の条件」「繰り返しの上限」
  - 作業エージェントと検証エージェントのそれぞれについて、「使うエージェント」「モデル」「考える深さ」。考える深さは、AI が答える前にどれだけ考えるか。
- REQ-313：「設定」画面には、作業エージェントが返した準備の確認の内容を、そのまま見せる。利用者は、機器の設定をここで見られる。
- REQ-314：「開始」を押した後も、「設定」画面で設定を見られる。ただし、変えられない。
- REQ-315：「実行のようす」画面には、次のものを置く。
  - エージェントの構成の図。いま動いているものを目立たせる。
  - 試行ごとの計画・作業の報告・評価
  - 質問や許可を待っているときの知らせ
  - 「止める」ボタン
  - エージェントがしたこと（使ったツールなど）の一覧。「くわしい記録」を開いたときだけ見せる。
- REQ-316：「結果」画面には、結論・試行ごとの表・振り返りを、この順に見せる。前の実行の結果も開ける。
- REQ-317：利用者が「止める」を押すと、エクステンションが統括エージェントのいまの応答を止める。
  - その後、エクステンションはツールの使用を拒否する。ただし、結論と振り返りを記録するツールだけは通す。
- REQ-318：Web管理画面は、幅 390 px の画面でも、横にはみ出さずに見られる。ライトモードとダークモードの両方で読める。

### 5.3 実行の記録

- REQ-321：エクステンションは、実行ごとに、次の3つをファイルに残す。設定、試行ごとの経過（計画・作業の報告・評価）、エージェントの動き。
  - 置き場所は、`<COPILOT_HOME または ~/.copilot>/plugin-data/embedded-debug-loop/`。
  - これらのファイルは、振り返りに使う。
