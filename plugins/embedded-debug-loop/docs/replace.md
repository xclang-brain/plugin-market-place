# 部品を変える（プラグインの設計変更）

このプラグインのスキルを足す・消す・置き換えるときと、作業エージェントを置き換えるときの手順です。プラグインのソース（このリポジトリの `plugins/embedded-debug-loop/`）を直す開発者向けです。
利用者は、新しいバージョンをインストールし直すだけです（名前や設定の項目が変わったスキルは、設定もやり直します）。

部品（スキルと作業エージェント）は、互いの中身を前提にしない作りです。そのため、次のものは直しません。

- 統括エージェント（`orchestrator`）と検証エージェント（`verifier`）
- Web管理画面（既定の作業エージェントの名前を除く）
- 3段階目のガイド（`docs/guide/3-orchestrator.md`）
- プラグインのフォルダ直下の `README.md`

スキルには、設定のスキル（「使うスキル」の表で、役割が「設定」のもの）と、それ以外の作業のスキルがあります。
パスは、ことわりがなければ、プラグインのフォルダからの相対パスです。

## スキルを足す

1. `skills/<名前>/` に、新しいスキルを置きます（[新しいスキルが守ること](#新しいスキルが守ること)）。`SKILL.md` の `name:` は、フォルダの名前と同じにします。
2. 次の2つの「使うスキル」の表に、役割と名前の行を足します。役割と名前は、2つの表で同じにします。
   - 作業エージェントの定義（`com.github.copilot/agents/<作業エージェントの名前>.agent.md`）
   - 同じフォルダの `README.markdown`。名前は、今の行と同じく、そのスキルの README へのリンクにします。
3. 作業エージェントの定義に、そのスキルをいつ使うかを書きます。
   定義には、役割を並べて書いた所がほかにもあります（`description`、セットアップ、準備の確認、試行の報告の形など）。今ある役割の名前で検索して見つけ、新しい役割を足します。
4. `README.markdown` の説明（はじめの文、依頼の例、うまくいかないとき）も、同じように直します。
5. [テストと CI](#テストと-ci) を直します。
6. [仕上げ](#仕上げ)に進みます。

## スキルを消す

1. `skills/<名前>/` を消します。
2. 2つの「使うスキル」の表から、その行を消します。
3. 作業エージェントの定義から、その役割を使う手順と、役割を並べて書いた所の、その役割を消します。
4. `README.markdown` の説明も、同じように直します。
5. [テストと CI](#テストと-ci) を直します。
6. [仕上げ](#仕上げ)に進みます。

## スキルを置き換える

1. 古いスキルを元に新しいスキルを作るときは、先にフォルダをコピーしておきます。
2. [スキルを消す](#スキルを消す)の手順 1〜4 と、[スキルを足す](#スキルを足す)の手順 1〜4 を続けて行います。
   役割が同じなら、作業エージェントの定義と `README.markdown` で直すのは、「使うスキル」の表の名前だけです。
3. [テストと CI](#テストと-ci) を直し、[仕上げ](#仕上げ)に進みます。

## 作業エージェントを置き換える

1. `com.github.copilot/agents/` に、新しい作業エージェントの定義（`<新しい名前>.agent.md`）を置きます（[新しい作業エージェントが守ること](#新しい作業エージェントが守ること)）。元の定義は消します。
   定義の中で、作業エージェントが自分の名前を書く所（準備の確認の返事で、セットアップの頼み方を案内する所）も、新しい名前にします。
2. 同じフォルダの `README.markdown` を、新しい作業エージェントの名前と使い方に書き換えます。「統括エージェントと検証エージェント」の節は残します。
   README は `.md` にしません。`agents/` の `.md` は、エージェントの定義として読み込まれます。
3. 使うスキルが違うときは、上の節の手順で、スキルを足す・消す・置き換えます（テストと仕上げは、まだ行いません）。
4. `com.github.copilot/extensions/embedded-debug-loop/defaults.json` の `worker` を、`embedded-debug-loop:<新しい名前>` にします。これが既定の作業エージェントです。
5. [テストと CI](#テストと-ci) を直し、[仕上げ](#仕上げ)に進みます。

## テストと CI

テストと CI には、今の部品の名前と作りが書いてあります。部品を変えたら、次の所を直します。
古い名前のままでも合格してしまうテストがあります。テストが合格しても、当てはまる所はすべて直します。

| 直すとき | ファイル | 直す所 |
| --- | --- | --- |
| スキルを足す・消す・置き換えたとき | `tests/independence/test_independence.py` | `SKILL_NAMES`（すべてのスキルの名前）と `WORK_SKILLS`（作業のスキルの名前と、そのスクリプトの名前）。足したスキルは、ここに書かないとテストされない |
| 作りの違うスキルにしたとき | 同上 | 今のスキルの作りを前提にした所。`template_keys()`（設定のひな形のファイルの名前。合わないと、項目の名前の確認が黙って空になる）、`test_no_skill_internals` の禁止の言葉、`test_each_work_skill_runs_alone`（設定の確認と、設定ファイルの用意のコマンド、設定ファイルの名前）、`test_replaced_worker_and_skills_need_no_upper_change` の `renames`（例に使うスキルの名前）。設定のスキルを置き換えたときは、その名前・スクリプト・コマンドを使う所（`SkillReplacement` など）も |
| スキルに名前を付けるとき | 同上 | `test_worker_readme_knows_only_names_and_roles` は、作業エージェントの README を `SPECIFIC_WORDS`（転送・ログ取得の具体の言葉）で調べる。スキルの名前にその言葉が入っていると、不合格になる |
| 作業エージェントを置き換えたとき | 同上 | 作業エージェントの定義のファイル名と、名前。定義の決まった書き方（「## 使うスキル」の見出し、依頼の書き出し、準備の確認の返事の1行目、セットアップの節）を調べるテストも |
| スキルか作業エージェントの名前が変わったとき | `tests/extension/independence.test.mjs` | `FORBIDDEN`（Web管理画面に書いてはいけない言葉）。消した名前を消し、足した名前を足す |
| テストに要るパッケージが変わったとき | リポジトリ直下の `.github/workflows/` にある、このプラグインの CI の定義 | スキルのジョブと独立性のジョブの `pip install` の行（2か所）、その下でバージョンを表示する行、その上のコメント |
| 設定のスキルを置き換えたとき | 同上 | 設定のスキルを Windows の PowerShell で動かすジョブ |

`tests/run.py` と、CI でスキルのテストを動かすジョブは、`skills/` の下からスキルを探すので、直しません。

## 仕上げ

1. 古い名前を、リポジトリ全体で検索します（まだ `git add` していない新しいファイルも）。名前を変えずに作りを替えたときは、古いスクリプトとひな形のファイルの名前でも検索します。

   ```text
   git grep -n --untracked "<古い名前>" -- ':/'
   ```

2. 仕様書（`docs/specs/requirements.md`）と設計書（`docs/design/design.md`）の、次の所を直します。
   - スキルの一覧と数、役割の一覧
   - 足した・消したスキルの節
   - 構成図
   - スキルのフォルダの中身（スクリプトとひな形のファイルの名前、同梱するほかの人のコード）
   - Windows への対応の表と、テストの表の、そのスキルの行
   - 作業のスキルの共通の作り（設定ファイルの形式、コマンドの名前）
   - 作業エージェントの名前
3. 役割を足したり消したりしたときは、プラグインの説明も直します。次の3か所にあります。
   - `plugin.json`
   - リポジトリ直下の `.github/plugin/marketplace.json`
   - リポジトリ直下の `README.md`

   憲章（`docs/constitution.md`）の第1条にも、役割が書いてあります。直すときは、憲章の版と変更履歴（付録）も更新します。
4. この手順書の「テストと CI」と「守ること」の節も、変えた部品とテストに合わせます。
5. バージョンを上げます。次の5か所にあります。
   - `plugin.json`
   - 仕様書の先頭
   - 設計書の先頭
   - リポジトリ直下の `.github/plugin/marketplace.json`
   - リポジトリ直下の `README.md` の表
6. スキルのテストに要るパッケージ（CI の `pip install` の行と同じもの）と、Node.js を入れます。プラグインのフォルダで次を実行します。

   ```text
   # Windows（PowerShell）
   py -3 tests\run.py
   # Linux（bash）
   python3 tests/run.py
   ```

   不合格がないことを確認します。「うち N 件は飛ばしました」と出たら、`-v` で、飛ばした理由がこの PC にない道具だけかを確認します。パッケージが足りないと、そのテストも飛ばされます。
7. push してプルリクエストを作り、GitHub Actions のテスト（Windows と Linux）が合格することを確認します。
8. マージしたら、開発者自身の Copilot CLI でプラグインをアンインストールし、インストールし直します。新しい部品で動くことを確認します。

   ```text
   /plugin uninstall embedded-debug-loop
   /plugin install embedded-debug-loop@plugin-market-place
   ```

## 新しいスキルが守ること

| 約束 | 内容 |
| --- | --- |
| 頼まれること | 作業エージェントの[「使うスキル」の表](../com.github.copilot/agents/README.markdown#使うスキル)にある役割の作業と、設定の確認 |
| 返すもの | 作業では、成否・起きたこと・ログの場所。設定の確認では、抜けや誤り（できれば、実際に使えるかも試す） |
| 設定の確認 | 作業フォルダに何も作らない。設定ファイルがなければ、作らずに「ない」と返し、作り方を伝える |
| 設定 | 要るなら、スキルのフォルダの `README.md` に、設定ファイルの場所・作り方・項目の意味を書く。形式（YAML・INI・JSON など）と項目の名前は自由。ただし、今の仕様書とテストは、作業のスキルが YAML の設定ファイルと、設定の確認・設定ファイルの用意のコマンドを持つことを前提にしている。違う作りにするなら、そこも直す |
| 設定の書き方 | 設定のスキル（「使うスキル」の表の「設定」）が読める形で書く。書き方は、そのスキルの README にある |
| データの置き場所 | 設定とログは、作業フォルダの `.<スキルのフォルダの名前>/` にだけ置く。フォルダの名前を変えてコピーしたら、その名前になる（ログの名前と、経過の表示の頭も） |
| README | スキルのフォルダの `README.md` に、何をするか、必要なもの、置き方（`.github/skills/<名前>/` と `~/.copilot/skills/<名前>/`、`/skills reload`）、呼び方、設定、結果とログ、うまくいかないとき、テストの実行のしかたを書く |
| テスト | `tests/test_*.py` に置く。スキルのフォルダだけをほかの場所にコピーしても、そのフォルダで `python -m unittest discover -s tests` で合格する |
| スクリプト | Python 3.8 以上の標準ライブラリだけで動く。ほかのものが要るなら `scripts/vendor/` に同梱し、ライセンスの文書も置く。標準出力は、Windows ではコンソールの文字コードで書く |
| コマンド | `SKILL.md` のコマンドは、Windows の PowerShell で動く書き方を必ず示す（ヒアドキュメント・`source`・`$(…)` は、PowerShell では動かない）。Python は、Windows では `py -3`（なければ `python`）、ほかは `python3` で呼ぶ |
| 独立 | 要るファイルは、スキルのフォルダに置く。プラグイン・ほかのスキル・エージェントの名前と、フォルダの外を指すパスを書かない（コメントとエラーメッセージも）。`SKILL.md` の `description` に、スラッシュコマンドの名前を書かない |

設定のスキルを置き換えるときは、新しいスキルが次のことをできるようにします。

- 渡されたスキルの名前から、そのスキルの README と設定ファイルを見つける。プラグインの中では、ほかのスキルは同じ `skills/` の下にある。
- ほかのスキルの設定のひな形を、今のコメントの書き方のまま読む。書き方を変えるなら、ほかのスキルのひな形も直す。

## 新しい作業エージェントが守ること

統括エージェントとの約束は、次のとおりです。

| 場面 | 約束 |
| --- | --- |
| ほかのエージェントから呼ばれたとき | 利用者に質問せず、頼まれたことだけをする。呼ばれたと判断するのは、質問のツール `ask_user` が使えないとき、または依頼が「これは準備の確認です」か「あなたは作業役です」で始まるとき |
| 準備の確認 | 作業はしない。1行目に「準備：できている」か「準備：できていない」と書き、続けて設定の要約と、足りないもの（直し方つき）を書く |
| 試行 | 1回だけ作業し、合否は判断しない。進めなくなったら止める。変えたこと、手順ごとの「できた／できなかった（理由）」、ログの要点、ログの場所（絶対パス）、気づいたことを返す |

- 依頼の書き出し（「これは準備の確認です」「あなたは作業役です」）と、返事の1行目（「準備：…」）は、この文字のまま使います。ほかの言い回しは変えてかまいません。
- 使うスキルは、「## 使うスキル」の節の表（`| 役割 | スキル |`）に名前だけを書きます。スキルの中身は書きません。
- 定義には、統括エージェント・検証エージェント・Web管理画面のことを書きません。
- 試行の報告の行（ビルド・転送など）は、作業に合わせて変えてかまいません。統括エージェントは、行の名前を読みません。
- 定義の `description` は、Web管理画面で作業エージェントを選ぶときに表示されます。何をする作業エージェントかが分かるように書きます。
