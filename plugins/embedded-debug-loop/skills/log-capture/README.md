# log-capture：シリアルコンソールの記録

PC から機器のシリアルコンソールに接続し、機器のシェルでコマンドを実行して、出力を記録するスキルです。
GitHub Copilot CLI で使います。動かすのに必要なファイルは、すべてこのフォルダにあります。

使い始めるときは、次のとおりに進めます。

1. このフォルダを、作業フォルダの `.github/skills/log-capture/` にコピーします（下の「インストールする」）。
   作業フォルダは、ふつうは Copilot CLI を起動したフォルダです。
2. Copilot CLI で `/log-capture 設定ファイルはどこ？` と入力します。設定ファイルができ、その場所が表示されます。
3. 設定ファイルの `port` に、シリアルポートの名前（例：`/dev/ttyUSB0`）を書きます。
   ほかの項目（`baud`・`login_user`・`login_password` など）も、機器に合わせて書き換えます。
   実行するコマンドが決まっているなら、`commands` にも書きます（下の「設定ファイル」）。
4. `/log-capture 設定を確認して` と入力します。
   「… で機器につながり、… でログインできました」のように表示されれば、接続とログインの設定は完了です。
   ログインが要らない機器では、「… シェルのプロンプトを確かめました」と表示されます。
5. `/log-capture 機器で /opt/myapp/my_app を動かして、出力を見せて` のように依頼します（下の「使い方」）。
   コマンドの出力、機器での終了コード（コマンドの終わり方を表す数）、ログファイルの場所が表示されます。

## できること

- 機器がログインを求めたら、設定のユーザー名とパスワードでログインします。
- 設定したコマンドを、機器のシェルで順に実行します。
- コマンドごとに、出力と、機器での終了コードを返します。
- 機器から届いた文字を、ログファイルに保存します（下の「ログ」）。
- コマンドを実行せず、指定した秒数だけ出力を記録することもできます。

## 必要なもの

- Linux の PC。
- Python 3.8 以上。標準ライブラリだけで動きます（pyserial などは不要）。
- GitHub Copilot CLI。
- 機器と PC を接続するシリアルケーブル（USB シリアル変換器など）。
  PC での名前は、`/dev/ttyUSB0` や `/dev/ttyACM0` などです。
- シリアルポートを開く権限。
  権限がないときは、今のユーザーを、シリアルポートのグループ（多くの Linux では `dialout`）に追加します。
  `sudo usermod -aG dialout $USER` を実行し、PC にログインし直してください。
- 機器のシリアルコンソールで使えるシェル（sh や bash）。
  終了コードの取得に、シェルの `$?` を使います。

## インストールする

1. このフォルダを、次のどちらかにコピーします。
   - 作業フォルダの `.github/skills/log-capture/`：その作業フォルダだけで使う
   - `~/.copilot/skills/log-capture/`：どの作業フォルダでも使う

   作業フォルダにコピーするときは、作業フォルダで次のように実行します。
   `log-capture` の部分は、このフォルダのパスに置き換えます。

   ```
   mkdir -p .github/skills
   cp -r log-capture .github/skills/log-capture
   ```

2. Copilot CLI を起動したままコピーしたときは、Copilot CLI で `/skills reload` を実行します。
3. Copilot CLI で `/skills list` を実行します。一覧に `log-capture` があれば、インストールは完了です。

### 別の名前でコピーする

フォルダを別の名前でコピーしたときは、`SKILL.md` の先頭の `name:` も、同じ名前に書き換えます。
Copilot CLI は、`name:` に書いた名前でスキルを呼び出します。

設定とログを置くフォルダも、`.log-capture/` から `.<新しい名前>/` に変わります（下の「設定ファイル」）。

## 使い方

Copilot CLI で、`/log-capture` の後に依頼の内容を書きます。
依頼できることと、その例は次のとおりです。

| 依頼できること | 例 |
| --- | --- |
| コマンドを実行して、出力を記録する | `/log-capture 機器で /opt/myapp/my_app を動かして、出力を見せて` |
| コマンドは実行せず、出力を記録する | `/log-capture 機器の出力を 30 秒記録して` |
| 設定ファイルの場所を表示する（なければ作る） | `/log-capture 設定ファイルはどこ？` |
| 設定を確認する（機器に接続できるか、ログインできるか） | `/log-capture 設定を確認して` |

- 依頼の文にコマンドを書かなければ、設定ファイルの `commands` を実行します。
  依頼の文にコマンドを書くと、今回だけ、`commands` の代わりにそのコマンドを実行します。
- 設定の確認では、機器のシェルでコマンドを実行しません。
- プラグインに入れて配られているときは、`/<プラグインの名前>:<スキル名>` でも呼べます。

### スクリプトを直接実行する

Copilot CLI を使わずに、スクリプトを直接実行することもできます。
作業フォルダで、次のように実行します。

```
python3 .github/skills/log-capture/scripts/capture.py run
python3 .github/skills/log-capture/scripts/capture.py run --command "/opt/myapp/my_app"
python3 .github/skills/log-capture/scripts/capture.py run --listen-only 30
python3 .github/skills/log-capture/scripts/capture.py config-path
python3 .github/skills/log-capture/scripts/capture.py check
```

`~/.copilot/skills/` に置いたときや、別の名前でコピーしたときは、パスをその場所に変えます。

| サブコマンド | すること |
| --- | --- |
| `run` | コマンドを実行して、出力を記録する |
| `config-path` | 設定ファイルの場所を表示する（なければ作る） |
| `check` | 設定を確認する（機器に接続できるか、ログインできるか） |

| オプション | 意味 |
| --- | --- |
| `--command "コマンド"` | 設定の `commands` の代わりに、このコマンドを実行する。複数指定できる |
| `--listen-only 秒数` | コマンドを実行せず、その秒数だけ出力を記録する |
| `--workdir フォルダ` | 作業フォルダを変える（ふつうは今のフォルダ） |
| `--config ファイル` | 別の場所の設定ファイルを使う |

## 設定ファイル

設定は、作業フォルダの `.log-capture/config.yaml` に書きます。
ファイルは、直接書き換えてかまいません。
各項目の意味は、ファイルの中でも、その項目のすぐ上のコメントに書いてあります。

### 置き場所

- 作業フォルダは、ふつうは Copilot CLI を起動したフォルダです。
- 別の名前でコピーしたときは、`.<新しい名前>/config.yaml` です。
- 設定は、作業フォルダごとに別です。
  別のフォルダ（サブフォルダを含む）で使うと、そこに新しい設定ファイルができます。
  Copilot CLI は、いつも同じフォルダで起動してください。
  スクリプトを直接実行するときは、`--workdir` で作業フォルダを指定することもできます。

### スクリプトが自動で行うこと

- 設定ファイルがなければ、このフォルダの `config-template.yaml`（ひな形）をコピーして作ります。
- 設定とログを置くフォルダに `.gitignore`（中身は `*`）がなければ、それも作ります。
  これで、設定やログは git の管理対象から外れます。
- スキルを新しいバージョンに更新し、ひな形の項目が増えたときは、足りない項目をファイルの最後に追加します。
  追加した項目の値は、ひな形と同じです。すでにある内容は変えません。

### 項目

| 項目 | 意味 | 例 |
| --- | --- | --- |
| `port` | 機器に接続するシリアルポート（必須） | `"/dev/ttyUSB0"` |
| `baud` | シリアルの速さ（ボーレート）。機器と同じ値にする | `115200` |
| `login_user` | ログインするユーザー名。機器がログインを求めないときだけ空にする（空ならログインしない） | `"root"` |
| `login_password` | ログインのパスワード。機器のユーザーにパスワードがないときや、環境変数で渡すときは空にする | `""` |
| `login_password_env` | パスワードを設定した環境変数の名前 | `"DEVICE_PASSWORD"` |
| `prompt` | シェルのプロンプトの終わりに一致する正規表現。空なら `[#$] $`（「# 」か「$ 」で終わるプロンプトに一致する） | `"[#$] $"` |
| `commands` | 機器のシェルで、並べた順に実行するコマンド | `["/opt/myapp/my_app"]` |
| `command_timeout_seconds` | 1つのコマンドを待つ最長の秒数。過ぎたら Ctrl-C を送って止める | `30` |
| `listen_seconds` | コマンドの後に、さらに出力を記録する秒数。0 なら記録しない | `10` |
| `logout` | 終わったら `exit` を送ってログアウトするか。このスキルがログインしたときだけ送る（接続したときに、すでにシェルのプロンプトが出ていたら送らない） | `true` |

- `commands` が空なら、コマンドを実行せず、`listen_seconds` の秒数だけ記録します。
  そのときは、`listen_seconds` を 1 以上にします。
- 1行に「項目: 値」の形で書きます。文字列は `"…"` で囲みます。
  `\` を使う正規表現は、`'…'`（シングルクォート）で囲みます。

### パスワードを環境変数で渡す

パスワードをファイルに書きたくないときは、環境変数で渡します。

1. 設定ファイルに、環境変数の名前を書きます。

   ```
   login_password: ""
   login_password_env: "DEVICE_PASSWORD"
   ```

2. Copilot CLI を起動する前に、その環境変数にパスワードを設定します。

   ```
   export DEVICE_PASSWORD='機器のパスワード'
   copilot
   ```

- 環境変数があれば、`login_password` ではなく、環境変数の値を使います。
- `login_password_env` に書いた環境変数がなく、`login_password` も空のときは、設定の問題として止まります。機器には接続しません。
  ただし、`login_user` が空（ログインしない設定）なら、止まりません。
- パスワードは、結果にもログにも出しません。
  設定の確認の結果に各項目の値を表示するときも、パスワードは「＊＊＊」と表示します。

## 結果とログ

### 結果

Copilot CLI が、次の内容を文章で伝えます。

- 何が起きたか。失敗したときは、考えられる原因と、確認すること。
- コマンドごとの出力。長いときは、最後の 60 行だけを表示します。すべての出力は、ログファイルにあります。
- 機器での終了コード。0 なら、コマンドは正常に終わっています。
  0 以外なら、機器でコマンドがうまく動いていない可能性があります。
- 時間内に終わらず、Ctrl-C で止めたコマンド。止めるまでの出力は残ります。
- 実行しなかったコマンド（途中で止まったとき）。
- ログファイルの場所。

### スクリプトの出力

スクリプトを直接実行したときは、標準出力に JSON を1つ出します。
主な項目は次のとおりです。

| 項目 | 意味 |
| --- | --- |
| `ok` | 成功したか |
| `message` | 何が起きたかを表す文 |
| `commands` | コマンドごとの結果（下の表） |
| `listen` | コマンドの後や、記録だけのときに記録した出力 |
| `not_run` | 実行しなかったコマンド |
| `problems` | 設定の問題（直すところ） |
| `summary` | 設定の内容（check のとき。パスワードはマスクする） |
| `config` | 設定ファイルの場所 |
| `log` | ログファイルの場所 |
| `added` | 設定ファイルに追加した項目 |
| `created` | 設定ファイルを、今回ひな形から作ったか |
| `missing` | 値がまだ書かれていない必須の項目（config-path のとき） |

`commands` の中の、コマンドごとの項目は次のとおりです。

| 項目 | 意味 |
| --- | --- |
| `command` | コマンド |
| `output` | 出力 |
| `exit_code` | 機器での終了コード。分からなければ null |
| `timed_out` | 時間切れで止めたか |
| `truncated` | 出力を最後の 60 行に切ったか |

config-path が出すのは、`config`・`created`・`missing`・`added` です。
設定ファイルに項目を追加したときは、`message` も出します。
設定に問題があるときは、`problems` も出します。

スクリプト自身の終了コードは、次のとおりです。

| 終了コード | 意味 |
| --- | --- |
| 0 | 成功。config-path は、設定に問題があっても 0 |
| 1 | run の失敗（機器に接続できない、ログインできない、時間切れで止めた、など） |
| 2 | 設定の問題。check は、機器に接続できないときも含め、問題があれば 2 |

### ログ

- 場所は、作業フォルダの `.log-capture/logs/` です。
- 名前は `log-capture-年月日-時分秒.log` です（例：`log-capture-20261105-143000.log`）。
  同じ秒に2つできたときは、`log-capture-20261105-143000-2.log` のように `-2` などが付きます。
  別の名前でコピーしたときは、フォルダが `.<新しい名前>/logs/` に、ファイル名の先頭が新しい名前になります。
- 先頭の数行（`#` で始まる行）には、開始時刻、シリアルポート、実行するコマンド（run のとき）などが書かれます。
- その後に、機器から届いた文字がそのまま入ります。色の制御文字も残ります。
- 各コマンドの出力の後には、「（終了コード：0）」のような行が入ります。
  終了コードを調べるため、スキルは各コマンドの後に短いコマンドを送ります。
  そのコマンドと応答の行はログに残さず、この行に置き換えます。
  読み取れなかったときは、「（終了コード：読めませんでした）」です。
- 最後に、結果の文が入ります。

## うまくいかないとき

結果に出た文や起きたことを左の列で探し、右の列を確認します。

| 結果に出た文・起きたこと | 確認すること |
| --- | --- |
| Copilot CLI で `/log-capture` が使えない | フォルダの置き場所。フォルダの名前と `SKILL.md` の `name:` が同じか。確認したら、`/skills reload` を実行する |
| シリアルポート … が見つかりません | ケーブルが接続されているか。`port` が正しいか。文の最後に、PC で見つかったシリアルポート（`/dev/ttyUSB*`・`/dev/ttyACM*` など）の名前が出ていれば、その中から正しいものを `port` に書く |
| シリアルポート … を開く権限がありません | 今のユーザーを `dialout` グループに追加し、PC にログインし直す |
| シリアルポート … は、ほかのプログラムが使っています | minicom や screen などの端末ソフトを閉じる |
| … はシリアルポートではありません | `port` が正しいか |
| シリアルポート … から応答がありません | ケーブルが接続されているか。機器の電源が入っているか |
| 文字は届きますが、ログインの求めも、シェルのプロンプトも出ません | `baud` が機器と同じか。`prompt` が機器のプロンプトに一致するか。機器で前のプログラムが動いたままでないか |
| ログインできませんでした | `login_user` とパスワード（`login_password` または環境変数）が正しいか |
| 機器がログインを求めていますが、設定の login_user … が空です | `login_user` に、ログインするユーザー名を書く |
| ログインの後、シェルのプロンプトが出ません | `prompt` が機器のプロンプトに一致するか |
| 環境変数 … がありません | Copilot CLI を起動する前に、その環境変数にパスワードを設定したか |
| … 秒で終わらなかったため、Ctrl-C で止めました | 長く動くプログラムなら、`command_timeout_seconds` を、出力を記録したい秒数まで増やす |
| Ctrl-C を送ってもプロンプトが戻りませんでした | 機器のコンソールでプログラムを止めるか、機器の電源を入れ直す |
| やりとりが、途中で切れました | USB ケーブルが抜けていないか |
| 設定ファイルの … 行目が読めません | その行の書き方。文字列を `"…"` で囲んでいるか |
| 実行するコマンド（commands）が空で、記録する秒数（listen_seconds）も 0 です | `commands` を書くか、`listen_seconds` を 1 以上にする |
| baud（シリアルの速さ）の … は使えません | 9600、38400、57600、115200 などの、決まった速さを書く |
| 終了コードが「読めませんでした」になる | 機器のシェルで `$?` が使えるか（fish などでは使えません） |

## テストを実行する

スキルが正しく動くかを、機器なしでテストできます。
このフォルダで、次のコマンドを実行します。

```
python3 -m unittest discover -s tests
```

最後に `OK` と表示されれば、成功です。

- 機器のシリアルコンソールは、PC の中の疑似端末（pty）でエミュレートします。
- Linux で実行します。すべて終わるまで、2 分ほどかかります。
- テストを実行すると、`tests/__pycache__` が残ります。不要なら削除してかまいません。
  残したくないときは、`python3 -B -m unittest discover -s tests` で実行します。
