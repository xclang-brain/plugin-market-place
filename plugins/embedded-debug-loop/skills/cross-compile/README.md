# cross-compile（クロスコンパイル）

機器で動かすプログラムを、PC でビルドするスキルです。
GitHub Copilot CLI で使います。

## 何をするスキルか

- SDK の環境設定ファイルを読み込んでから、`make` などのビルドのコマンドを実行します。
  - SDK：機器向けのコンパイラーなどをまとめたもの。例：Yocto の SDK。
- ビルドの後に、できるはずのファイルが本当にできたか（作り直されたか）を確かめます。
- できたファイルの大きさと種類（例：ARM 用）を報告します。
- ビルドの出力は、すべてログのファイルに残します。
- するのはビルドだけです。できたファイルを機器に送ったり、動かしたりはしません。

## 必要なもの

- OS：Linux。
- Python 3.8 以上（標準のライブラリだけで動きます）。
- bash。
- ビルドの道具：`make` など、ビルドのコマンドで使うもの。
- 機器向けにビルドするとき：機器の SDK を PC に入れておくこと。
  - SDK を読み込まないと、PC のコンパイラーで PC 用のプログラムができます。
- `file` コマンド（無くても動きます。あると、ファイルの種類をくわしく報告します）。
- 機器をつなぐ必要はありません。

## 置き方

このフォルダを、まるごと次のどちらかに写します。

| 置き場所 | 使える範囲 |
| --- | --- |
| `<作業フォルダ>/.github/skills/cross-compile/` | その作業フォルダだけ |
| `~/.copilot/skills/cross-compile/` | どの作業フォルダでも |

- 作業フォルダとは、ビルドしたいプロジェクトのフォルダです。
- Copilot CLI を起動したまま写したときは、`/skills reload` を入力します。
- フォルダの名前を変えて写すときは、`SKILL.md` の `name:` も同じ名前に変えます。
  Copilot CLI は、スキルを `name:` の名前で呼ぶためです。
  このとき、設定とログのフォルダは `.<新しい名前>/` に、ログのファイルの名前の頭も新しい名前になります。

## 呼び方

Copilot CLI のチャットで、`/cross-compile` に続けて頼みます。

| 頼むこと | 例 |
| --- | --- |
| ビルド | `/cross-compile ビルドして` |
| 設定ファイルの場所（無ければ作る） | `/cross-compile 設定ファイルはどこ？` |
| 設定の確認（ビルドはしない） | `/cross-compile 設定を確かめて` |

- `/cross-compile` を付けずに「ビルドして」と頼んでも、Copilot がこのスキルを選ぶことがあります。
- プラグインに入れて配られているときは、`/<プラグインの名前>:<スキル名>` でも呼べます。

### スクリプトを直接動かすとき

作業フォルダで、次のように動かします（`.github/skills/` に置いたときの例）。

```bash
python3 .github/skills/cross-compile/scripts/build.py run          # ビルド（run は省ける）
python3 .github/skills/cross-compile/scripts/build.py config-path  # 設定ファイルの場所
python3 .github/skills/cross-compile/scripts/build.py check        # 設定の確認
```

- `--workdir <フォルダ>`：作業フォルダを変えます（ふつうは今のフォルダ）。
- `--config <ファイル>`：ほかの場所の設定ファイルを使います。

## 設定ファイル

### 置き場所

`<作業フォルダ>/.cross-compile/config.yaml`

- 作業フォルダは、コマンドを動かした今のフォルダです（ふつうは Copilot CLI を動かしているフォルダ）。
  上のフォルダは探しません。別のフォルダ（サブフォルダも）で動かすと、そこに新しい設定ファイルができます。
  作業フォルダは `--workdir` で変えられます。

次のことは、スクリプトが自動でします。

- 初めて使うとき、スキルのフォルダ（この README があるフォルダ）の `config-template.yaml` を写して、設定ファイルを作ります。
- `.cross-compile/` に `.gitignore`（中身は `*`）を作ります。設定とログを git に入れないためです。
  すでに `.gitignore` があれば、そのままにします。
- スキルを新しくして、ひな形に項目が増えたときは、足りない項目を設定ファイルの最後に足します。
  説明のコメントも一緒に足します。ほかの所は変えません。

設定ファイルは、自分で書き換えてかまいません。
各項目の意味は、項目のすぐ上のコメントに書いてあります。

### 項目

| 項目 | 意味 | 例（既定） |
| --- | --- | --- |
| `source_dir` | ビルドするフォルダ。作業フォルダからの相対パスか、絶対パス。空や `"."` なら作業フォルダ | `"firmware/app"`（既定 `"."`） |
| `sdk_env` | ビルドの前に読み込む、SDK の環境設定ファイル。機器向けにビルドするなら必ず書く。空なら読み込まない | `"/opt/poky/4.0/environment-setup-cortexa7t2hf-neon-poky-linux-gnueabi"`（既定 `""`） |
| `build_command` | ビルドのコマンド。ビルドするフォルダの中で実行する。空なら `make` | `"make -j4 all"`（既定 `"make"`） |
| `clean_command` | ビルドの前に実行する、片付けのコマンド。空なら片付けない | `"make clean"`（既定 `""`） |
| `outputs` | ビルドでできるファイル（必須）。ビルドするフォルダからの相対パス | `["my_app"]`、`["build/my_app"]`（既定 `[]`） |
| `timeout_seconds` | ビルドを待つ最長の秒数。過ぎたらビルドを止める | `600`（既定） |

- `clean_command` が空だと、ソースが変わっていないファイルは作り直されません。
  前のビルドでできたファイルが、そのまま残ります。
  毎回作り直すなら、`make clean` などを書きます。

### 書き方

- 1行に1つ、`名前: 値` の形で書きます。
- 文字は `"` で囲みます。例：`build_command: "make -j4"`
- リストは `["a", "b"]` と書くか、次の行から `  - a` の形で書きます。
- `#` で始まる行は、説明（コメント）です。
- 入れ子や、`|` で始まる複数行の文字は使えません。
- 文字コードは UTF-8 です。

### パスワードと環境変数

- このスキルの設定には、パスワードはありません。
- 環境変数 `CC` が設定されていると、Makefile の `$(CC)` は、そのコンパイラーになります（Makefile の中で `CC` を決めていないとき）。
  SDK の環境設定ファイルも、ふつう `CC` を設定します。

## 結果とログの見方

### 結果

- スクリプトは、結果を JSON で1つだけ、標準出力に出します。
- 途中のようすは、標準エラー出力に出します。
- Copilot は、この JSON を読んで、ふつうの言葉で伝えます。

ビルド（`run`）の主な項目：

| 項目 | 中身 |
| --- | --- |
| `ok` | うまくいったら `true` |
| `message` | 何が起きたかの文。失敗したときは、考えられる原因と、確かめること |
| `notes` | 注意。例：SDK を読み込まなかったので、PC 用のプログラムになった |
| `log` | ログのファイルの場所 |
| `outputs` | できたファイルごとの、場所（`path`）、大きさ（`size`、バイト）、時刻（`mtime`）、種類（`file_type`・`arch`）、作り直されたか（`updated`） |
| `stale_outputs` | ビルドは成功したが、作り直されなかったファイル（前のビルドのまま） |
| `compiler`・`compiler_path` | 使ったコンパイラーと、その場所 |
| `error_lines`・`warning_lines` | エラーの行と警告の行（それぞれ最大 20 行） |
| `tail` | 失敗したときの、出力の最後の 30 行 |
| `failed_step` | 失敗した段階。`sdk_env`（SDK の読み込み）、`cd`（フォルダに移る）、`clean`（片付け）、`build`（ビルド）、`outputs`（できたファイルの確認） |
| `timed_out` | 時間切れで止めたら `true` |
| `problems` | 設定や PC の準備の問題（1つずつの文） |
| `added` | 設定ファイルに足した項目 |

- `config-path` は、設定ファイルの場所（`config`）、作ったか（`created`）を出します。
  まだ空の必須の項目（`missing`）と、機器向けにビルドするときに書く項目のうち、まだ空のもの（`empty_recommended`）も出します。
- `check` は、問題（`problems`）と、設定の要点（`summary`）を出します。
  `summary` には、使うコンパイラー（`compiler`・`compiler_path`）も入ります。
- 終了コード：`run` は 0＝成功、1＝ビルドの失敗、2＝設定の問題。
  `check` は 0＝問題なし、2＝問題あり。`config-path` は、ふつう 0。

### ログ

- 置き場所：`<作業フォルダ>/.cross-compile/logs/cross-compile-<年月日>-<時分秒>.log`
  - 例：`cross-compile-20261105-093000.log`
  - 同じ秒に2回動かすと、2つ目には `-2` が付きます。
- ビルドを始めるたびに、1つできます。`config-path` と `check` は作りません。
- 中身は、上から次の順です。
  1. 設定の値（ビルドするフォルダ、SDK、コマンド、できるファイルなど）
  2. 「==== ビルドの出力（ここから） ====」から「==== ビルドの出力（ここまで） ====」まで：ビルドの出力のすべて。`==> ` で始まる行は、段階の区切り（SDK の読み込み、片付け、ビルド）です。
  3. 終了コード、使ったコンパイラー、できたファイル、結果の文
- スクリプトの中で思わぬエラーが起きたときも、くわしい中身をログに残します。

## うまくいかないとき

| 言われたこと | すること |
| --- | --- |
| outputs（ビルドでできるファイル）が空です | `outputs` に、ビルドでできるファイルの名前を書きます |
| SDK を読み込みません（PC 用のプログラムになる） | 機器向けにビルドするなら、`sdk_env` を書きます |
| sdk_env（SDK の環境設定ファイル）の … がありません／ファイルではありません | SDK を入れた場所と、ファイルの名前を確かめます |
| … の読み込みが失敗しました／途中で終わってしまいます | SDK が正しく入っているかを確かめます。SDK が出したメッセージも見ます |
| … の読み込みが、… 秒たっても終わりません | SDK の環境設定ファイルが、入力を待っていないかを確かめます |
| source_dir（ビルドするフォルダ）の … がありません／フォルダではありません／移れません | `source_dir` を確かめます（作業フォルダからの相対パスか、絶対パス） |
| … が見つかりません（ビルドのコマンドやコンパイラー） | その道具を PC に入れます。SDK の中の道具なら、`sdk_env` を確かめます |
| PC に bash が見つかりません | bash を入れます |
| ビルドが失敗しました | エラーの行とログを見て、ソースや Makefile を直します |
| 片付けのコマンド（…）が失敗しました | `clean_command` を確かめます |
| ビルドは終わりましたが、… ができていません | `outputs` の名前（ビルドするフォルダからの相対パス）と、ビルドのコマンドを確かめます |
| … は作り直されず、前のビルドのままです | ソースが変わっていません。毎回作り直すなら、`clean_command` に `make clean` などを書きます |
| … 秒たっても終わらないため、止めました | ビルドが入力を待っていないかを確かめます。長くかかるなら `timeout_seconds` を大きくします |
| 実行できないファイルがあります | そのファイルに実行の権限を付けます（例：`chmod +x build.sh`） |
| 設定ファイル … の N 行目が読めません | その行の書き方を直します（「書き方」を見てください） |
| 設定ファイル … が UTF-8 で書かれていません | UTF-8 で保存し直します |
| … で書いてください（文字、リスト、1 以上の数など） | その項目の値を、言われた形に書き直します（「書き方」を見てください） |
| … の書き方が正しくありません（引用符が閉じていません） | コマンドの中の `"` や `'` を閉じます |
| 設定ファイル … を作れません／… が読めません／ログのフォルダ … に書き込めません | 作業フォルダと設定ファイルに、読み書きの権限があるかを確かめます |
| 設定ファイルの場所 … は、フォルダです | その場所にあるフォルダの名前を変えるか、`--config` でファイルを指定します |
| 設定のひな形 … がありません | このフォルダを、まるごと写し直します |
| 作業フォルダ … がありません | `--workdir` に書いたフォルダを確かめます |
| 「…」は使えません／… の後ろに、パスを書いてください | スクリプトを直接動かすときの書き方を確かめます（「スクリプトを直接動かすとき」を見てください） |
| スクリプトの中で思わぬエラーが起きました | ログを見ます |
| `/cross-compile` が出てこない | 置き場所を確かめて、`/skills reload` を入力します。フォルダの名前と `SKILL.md` の `name:` が同じかも確かめます |

## 試験の動かし方

このフォルダで、次のコマンドを動かします。

```bash
python3 -m unittest discover -s tests -v
```

- 一時フォルダに小さな C のプロジェクトを作り、実際にビルドして確かめます。
- `make`・`gcc`・`bash` が無いと、それを使う試験（ビルドや、設定の確認）は飛ばします（skipped と出ます）。
- ARM 向けの試験は、`/opt/poky/4.0/environment-setup-cortexa7t2hf-neon-poky-linux-gnueabi` があって、その中のコンパイラーが使えるときだけ動きます。
- 動かすと、このフォルダの `scripts/` と `tests/` に `__pycache__` ができます。消してかまいません。
  残したくないときは、`python3 -B -m unittest discover -s tests -v` とします。
