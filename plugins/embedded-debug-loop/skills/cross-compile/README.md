# cross-compile：クロスコンパイルのスキル

機器（組み込み機器などのターゲット）で動かすプログラムを、PC でビルドするスキルです。
GitHub Copilot CLI で使います。

使い始めるときは、次のとおりに進めます。

1. このフォルダを、作業フォルダ（ビルドしたいプロジェクトのフォルダ）の `.github/skills/cross-compile/` にコピーします。ほかのコピー先は「インストールする」を見てください。
2. 作業フォルダで Copilot CLI を起動します。すでに作業フォルダで起動しているときは、`/skills reload` を実行します。
3. `/cross-compile 設定ファイルはどこ？` と入力します。設定ファイルができ、その場所が表示されます。
4. 設定ファイルに、次の項目を書きます。
   - `source_dir`：ビルドするフォルダ。Makefile が作業フォルダの直下にないときに書きます。例：`source_dir: "firmware/app"`
   - `outputs`：ビルドでできるファイル（必須）。ビルドするフォルダからの相対パスで書きます。例：`outputs: ["my_app"]`
   - `sdk_env`：SDK の環境設定ファイルのパス。機器向けにビルドするときに書きます。
5. `/cross-compile ビルドして` と入力します。できたファイルのサイズと種類が表示されれば成功です。

## できること

- SDK の環境設定ファイルを読み込んでから、`make` などのビルドコマンドを実行します。
  - SDK は、機器向けのコンパイラーなどをまとめたものです。例：Yocto の SDK。
- ビルドの後、`outputs` に書いたファイルがあるか、今回のビルドで作り直されたかを確認します。
- できたファイルのサイズと種類（例：ARM 用）を報告します。
- ビルドの出力は、すべてログファイルに保存します。

このスキルは、ビルドだけを行います。できたファイルを機器に送ったり、機器で実行したりはしません。

## 必要なもの

- OS：Linux
- Python 3.8 以上（標準ライブラリだけで動きます）
- bash
- ビルドコマンドで使うツール（`make` など）
- 機器の SDK（機器向けにビルドするとき）。PC にインストールしておきます。
  - SDK を読み込まないと、PC のコンパイラーで PC 用のプログラムができます。
- `file` コマンド（任意）。あると、ファイルの種類をくわしく報告します。

機器と接続する必要はありません。

## インストールする

このフォルダをまるごと、次のどちらかにコピーします。

| コピー先 | 使える範囲 |
| --- | --- |
| `<作業フォルダ>/.github/skills/cross-compile/` | その作業フォルダだけ |
| `~/.copilot/skills/cross-compile/` | すべての作業フォルダ |

Copilot CLI を起動したままコピーしたときは、`/skills reload` を実行します。

### フォルダの名前を変えるとき

フォルダの名前を変えてコピーするときは、`SKILL.md` の `name:` も同じ名前に変えます。
Copilot CLI は、`name:` に書いた名前でスキルを呼び出します。`/<新しい名前>` と入力して使います。

フォルダの名前を変えると、次の2つも新しい名前になります。

- 設定とログのフォルダ：`.<新しい名前>/`
- ログファイル名の先頭：`<新しい名前>-<年月日>-<時分秒>.log`

## 使い方

Copilot CLI のチャットで、`/cross-compile` に続けて依頼を入力します。

| 依頼 | 例 |
| --- | --- |
| ビルド | `/cross-compile ビルドして` |
| 設定ファイルの場所（なければ作る） | `/cross-compile 設定ファイルはどこ？` |
| 設定の確認（ビルドはしない） | `/cross-compile 設定を確かめて` |

- `/cross-compile` を付けずに「ビルドして」と入力しても、Copilot がこのスキルを使うことがあります。
- プラグインに入れて配られているときは、`/<プラグインの名前>:<スキル名>` でも呼べます。

### スクリプトを直接実行する

作業フォルダで、次のように実行します。
例のパスは、`.github/skills/` にインストールしたときのものです。
`~/.copilot/skills/` にインストールしたときは、パスの `.github/skills/` を `~/.copilot/skills/` に置き換えます。

```bash
python3 .github/skills/cross-compile/scripts/build.py run          # ビルド（run は省略できる）
python3 .github/skills/cross-compile/scripts/build.py config-path  # 設定ファイルの場所
python3 .github/skills/cross-compile/scripts/build.py check        # 設定の確認
```

オプションは次の2つです。

- `--workdir <フォルダ>`：作業フォルダを指定します。指定しないときは、カレントディレクトリを使います。
- `--config <ファイル>`：別の場所の設定ファイルを使います。

## 設定ファイル

設定ファイルは `<作業フォルダ>/.cross-compile/config.yaml` です。
初めて使うときに、スクリプトが自動で作ります。

### 作業フォルダの決まり方

スクリプトは、実行したときのカレントディレクトリを作業フォルダとして使います。
Copilot CLI から使うときは、ふつうは Copilot CLI のカレントディレクトリが作業フォルダになります。

- 親フォルダの設定ファイルは探しません。別のフォルダ（サブフォルダを含む）で実行すると、そこに新しい設定ファイルができます。
- 作業フォルダは、`--workdir` で変えられます。

### スクリプトが自動ですること

- 初めて使うとき、ひな形をコピーして設定ファイルを作ります。ひな形は、このフォルダ（この README があるフォルダ）の `config-template.yaml` です。
- 設定とログが Git にコミットされないように、`.cross-compile/` に `.gitignore`（中身は `*`）を作ります。
  - すでに `.gitignore` があれば、変更しません。
- スキルを新しいバージョンに更新して、ひな形に項目が増えたときは、足りない項目を設定ファイルの最後に追加します。
  - 説明のコメントも一緒に追加します。ほかの部分は変更しません。

設定ファイルは、直接編集してかまいません。
各項目の意味は、項目のすぐ上のコメントに書いてあります。

### 項目

項目は次の6つです。パスワードの項目はありません。

| 項目 | 意味 | 例 | 既定値 |
| --- | --- | --- | --- |
| `source_dir` | ビルドするフォルダ。作業フォルダからの相対パスか、絶対パス。空か `"."` なら作業フォルダ | `"firmware/app"` | `"."` |
| `sdk_env` | ビルドの前に読み込む、SDK の環境設定ファイル。機器向けにビルドするときは必ず書く。空なら読み込まない | `"/opt/poky/4.0/environment-setup-cortexa7t2hf-neon-poky-linux-gnueabi"` | `""` |
| `build_command` | ビルドコマンド。ビルドするフォルダの中で実行する。空なら `make` | `"make -j4 all"` | `"make"` |
| `clean_command` | ビルドの前に実行するクリーンコマンド。空ならクリーンしない | `"make clean"` | `""` |
| `outputs` | ビルドでできるファイル（必須）。ビルドするフォルダからの相対パス | `["my_app"]`、`["build/my_app"]` | `[]` |
| `timeout_seconds` | ビルドのタイムアウト（秒）。超えたらビルドを中断する | ― | `600` |

毎回作り直すときは、`clean_command` に `make clean` などを書きます。
空のままだと、ソースが変わっていないファイルは作り直されません。前のビルドでできたファイルが、そのまま残ります。

### 設定ファイルの書き方

- 1行に1項目を、`名前: 値` の形で書きます。
- 文字列は `"` で囲みます。例：`build_command: "make -j4"`
- リストは `["a", "b"]` と書きます。次の行から `  - a` の形で書くこともできます。
- `#` で始まる行は、コメントです。
- ネスト（入れ子）は使えません。
- `|` で始まる複数行の文字列は使えません。
- 文字コードは UTF-8 です。

### 環境変数 `CC`

- Makefile の中で `CC` を設定していなければ、Makefile の `$(CC)` は環境変数 `CC` のコンパイラーになります。
- SDK の環境設定ファイルも、ふつうは `CC` を設定します。

## 結果とログ

### 結果

スクリプトは、結果を1つの JSON で標準出力に出します。
途中経過は、標準エラー出力に出します。
Copilot は、この JSON を読んで、ふつうの言葉で伝えます。

ビルド（`run`）の結果の主な項目は、次のとおりです。

| 項目 | 内容 |
| --- | --- |
| `ok` | 成功したら `true` |
| `message` | 何が起きたかの説明。失敗したときは、考えられる原因と、確認すること |
| `notes` | 注意。例：SDK を読み込まなかったので、PC 用のプログラムになった |
| `log` | ログファイルの場所 |
| `outputs` | できたファイルごとの情報。場所（`path`）、サイズ（`size`、バイト）、更新時刻（`mtime`）、種類（`file_type`・`arch`）、作り直されたか（`updated`） |
| `stale_outputs` | ビルドは成功したが、作り直されなかったファイル（前のビルドのまま） |
| `compiler`・`compiler_path` | 使ったコンパイラーと、その場所 |
| `error_lines`・`warning_lines` | エラーの行と警告の行（それぞれ最大 20 行） |
| `tail` | 失敗したときの、出力の最後の 30 行 |
| `failed_step` | 失敗した段階。`sdk_env`（SDK の読み込み）、`cd`（フォルダへの移動）、`clean`（クリーン）、`build`（ビルド）、`outputs`（できたファイルの確認） |
| `timed_out` | タイムアウトで中断したら `true` |
| `problems` | 設定や PC の準備の問題のリスト。1件を1つの文で書く |
| `added` | 設定ファイルに追加した項目 |

`config-path` と `check` の結果には、主に次の項目があります。

| コマンド | 項目 | 内容 |
| --- | --- | --- |
| `config-path` | `config` | 設定ファイルの場所 |
| `config-path` | `created` | 設定ファイルを作ったか |
| `config-path` | `missing` | 値が空の必須項目 |
| `config-path` | `empty_recommended` | 機器向けにビルドするときに書く項目のうち、値が空のもの |
| `check` | `problems` | 見つかった問題 |
| `check` | `summary` | 設定の要点。使うコンパイラー（`compiler`・`compiler_path`）も入る |

終了コードは、次のとおりです。

| コマンド | 終了コード |
| --- | --- |
| `run` | 0＝成功、1＝ビルドの失敗、2＝設定の問題 |
| `check` | 0＝問題なし、2＝問題あり |
| `config-path` | 0＝設定ファイルの場所を返せた、2＝設定の問題（設定ファイルを作れないなど） |

### ログ

ビルドを始めるたびに、ログファイルを1つ作ります。
`config-path` と `check` では作りません。

- 場所：`<作業フォルダ>/.cross-compile/logs/cross-compile-<年月日>-<時分秒>.log`
  - 例：`cross-compile-20261105-093000.log`
  - 同じ秒に2回実行すると、2つ目のファイル名には `-2` が付きます。
- 内容は、上から次の順です。
  1. 設定の値（ビルドするフォルダ、SDK、コマンド、できるファイルなど）
  2. ビルドの出力のすべて
     - 「==== ビルドの出力（ここから） ====」と「==== ビルドの出力（ここまで） ====」の間にあります。
     - `==> ` で始まる行は、段階（SDK の読み込み、クリーン、ビルド）の区切りです。
  3. 終了コード、使ったコンパイラー、できたファイル、結果の説明
- スクリプトで予期しないエラーが起きたときも、その詳細をログに残します。

## うまくいかないとき

表示されるメッセージと、その対処です。
メッセージの中の … には、ファイルの場所や名前などが入ります。

| メッセージ・症状 | 対処 |
| --- | --- |
| outputs（ビルドでできるファイル）が空です | `outputs` に、ビルドでできるファイルを書きます（ビルドするフォルダからの相対パス） |
| SDK を読み込みません（PC 用のプログラムになる） | 機器向けにビルドするときは、`sdk_env` を書きます |
| sdk_env（SDK の環境設定ファイル）の … がありません／ファイルではありません | SDK をインストールした場所と、ファイル名を確認します |
| … の読み込みが失敗しました／途中で終わってしまいます | SDK が正しくインストールされているかを確認します。SDK が出したメッセージも確認します |
| … の読み込みが、… 秒たっても終わりません | SDK の環境設定ファイルが、入力を待っていないかを確認します |
| source_dir（ビルドするフォルダ）の … がありません／フォルダではありません／移れません | `source_dir` を確認します（作業フォルダからの相対パスか、絶対パス） |
| … が見つかりません（ビルドコマンドやコンパイラー） | そのツールを PC にインストールします。SDK の中のツールなら、`sdk_env` を確認します |
| PC に bash が見つかりません | bash をインストールします |
| ビルドが失敗しました | エラーの行とログを見て、ソースや Makefile を直します |
| 片付けのコマンド（…）が失敗しました | `clean_command` を確認します |
| ビルドは終わりましたが、… ができていません | `outputs` に書いたパス（ビルドするフォルダからの相対パス）と、ビルドコマンドを確認します |
| … は作り直されず、前のビルドのままです | ソースが変わっていないと考えられます。毎回作り直すときは、`clean_command` に `make clean` などを書きます |
| … 秒たっても終わらないため、止めました | ビルドが入力を待っていないかを確認します。時間がかかるビルドなら、`timeout_seconds` を大きくします |
| 実行できないファイルがあります | そのファイルに実行権限を付けます（例：`chmod +x build.sh`） |
| 設定ファイル … の N 行目が読めません | その行の書き方を直します（「設定ファイルの書き方」を参照） |
| 設定ファイル … が UTF-8 で書かれていません | UTF-8 で保存し直します |
| … で書いてください（文字、リスト、1 以上の数など） | その項目の値を、指定された形で書き直します（「設定ファイルの書き方」を参照） |
| … の書き方が正しくありません（引用符が閉じていません） | コマンドの中の `"` や `'` を閉じます |
| 設定ファイル … を作れません／… が読めません／ログのフォルダ … に書き込めません | 作業フォルダと設定ファイルに、読み書きの権限があるかを確認します |
| 設定ファイルの場所 … は、フォルダです | そのフォルダの名前を変えるか、`--config` で設定ファイルを指定します |
| 設定のひな形 … がありません | このフォルダを、まるごとコピーし直します |
| 作業フォルダ … がありません | `--workdir` に指定したフォルダを確認します |
| 「…」は使えません／… の後ろに、パスを書いてください | スクリプトに渡したコマンド（`run`・`config-path`・`check`）と、`--workdir`・`--config` の後ろのパスを確認します（「スクリプトを直接実行する」を参照） |
| スクリプトの中で思わぬエラーが起きました | ログを確認します |
| `/cross-compile` が、コマンドの候補に出てこない | インストール先を確認して、`/skills reload` を実行します。フォルダの名前と `SKILL.md` の `name:` が同じかも確認します |

## テストを実行する

このフォルダで、次のコマンドを実行します。

```bash
python3 -m unittest discover -s tests -v
```

- テストは、一時フォルダに小さな C のプロジェクトを作り、実際にビルドして確認します。
- `make`・`gcc`・`bash` がないと、それを使うテスト（ビルドや設定の確認）はスキップします。`skipped` と表示されます。
- ARM 向けのテストは、次の2つがそろうときだけ実行します。
  - `/opt/poky/4.0/environment-setup-cortexa7t2hf-neon-poky-linux-gnueabi` がある
  - そのファイルを読み込んだ後、SDK のコンパイラー（環境変数 `CC`）が使える
- 実行すると、このフォルダの `scripts/` と `tests/` に `__pycache__` ができます。削除してかまいません。作らないときは、`python3 -B -m unittest discover -s tests -v` を実行します。
