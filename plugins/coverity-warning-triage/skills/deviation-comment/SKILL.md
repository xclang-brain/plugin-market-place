# 逸脱コメントの書き方

逸脱コメントは、**この警告がどんな状況でも問題にならないこと**を述べる文章です。Coverity に登録され、あとから読む人が「直さなくてよい理由」として使います。

指示ファイルがないとき（チャットで直接頼まれたとき）は、下の「指示ファイルがないとき」の節も読みます。

## 書き方

- **日本語**で、**見出しを付けない 1〜2 文**で書く。**200 字以内**（スクリプトが確かめます。下の「確かめ」）。（K-42）
- 次をこの順に入れる。（K-43）
  1. **判定区分**（必須）：「誤検知。」「意図的。」など、文の先頭に置く。
  2. **問題にならない理由**（必須）：なぜ問題にならないのかを、条件を付けずに言い切る。
  3. **コードの根拠の場所**：理由を裏づける関数名とファイル・行（例 `read_all()（src/io/reader.c:120）`）。

## 例

> 誤検知。get_buf() の戻り値は NULL になりうるが、呼び出し元 read_all()（src/io/reader.c:120）で NULL を除いてから渡しているため、NULL を参照することはない。

> 意図的。case 2 から case 3 へのフォールスルーは、状態 2 の処理のあと状態 3 の処理を続けて行う設計（src/fsm.c:88 のコメントに記載）であり、break の書き忘れではない。

## 書かないこと

逸脱コメントには、問題にならない理由だけを書きます。次は書きません（必要なら結果ファイルの `verdict.rationale` か `confidence_reason` に書く）。（K-44）

- 条件や但し書き：「ただし〜の場合に限る」「〜を確認した場合は」「〜に対して」
- 調べた過程や、調べきれなかったこと：解析リビジョンが分からない、警告の説明とコードが合わない、再解析が必要 など
- 推奨や、人への依頼：「修正を推奨」「確認してください」

## 言い切れないとき

条件を付けないと「問題にならない」と書けないなら、それは問題になりうるということです。その場合は**推奨を修正**にします（`recommendation` を `fix`）。逸脱案は形として作り、言える範囲の理由だけを短く書きます。（K-97）

- 本物のバグ（`true_bug`）でも、今は動作に影響しない理由がコードで示せるなら、それを書く（例「本物の不具合。ただし、この機能は今の製品では無効（config.h:12）で、この処理は実行されない。」）。示せなければ、推奨は修正にする。（K-98）

## 注意

- プロジェクトの知識（`knowledge.md`）に「逸脱コメントの書き方」があれば、それに従う。
- 根拠の場所は、調べて実際に読んだ場所だけを書く。確かめていない場所を推測で書かない。（K-46）

## 確かめ

ターミナルが使えるときは、書いた逸脱コメントを、このスキルのスクリプトで確かめます。

```
uv run --native-tls "<このスキルのフォルダ>/scripts/check_comment.py" --comment "<逸脱コメント>"
```

- `<このスキルのフォルダ>` は、この SKILL.md があるフォルダの絶対パスです。uv がなければ、Python（`python3`、Windows は `python`）で同じように動かします。
- 確かめるのは、200 字以内か、判定区分（「誤検知。」「意図的。」「本物の不具合。」）で始まるか、書かないことのうち条件や但し書き、推奨や人への依頼の言い方がないか、です。
- 結果は JSON で 1 つ出ます。`ok`（合格なら true。終了コードは 0、不合格なら 1）、`length`（字数）、`problems`（直すところ）。
- `ok` が false なら、`problems` のとおりに直して、もう一度確かめます。

ターミナルが使えないときは、字数を自分で数えて確かめます（結果ファイルに書いたときは、結果ファイルを受け取るスクリプトも字数を確かめます）。

## Classification / Action / Severity の選び方

逸脱案（`deviation`）の目安です。値は Coverity Connect に設定されている選択肢の名前で書きます。（K-47）

| 判定 | Classification | Action | Severity |
|---|---|---|---|
| 誤検知 | False Positive | Ignore | Unspecified |
| 意図的 | Intentional | Ignore | Unspecified |
| 本物のバグだが直さない | Bug | Ignore | 影響に応じて Major / Moderate / Minor |

修正案（`fix`）の目安：Classification は `Bug`、Action は `Fix Required`、Severity は影響に応じて選ぶ。

社内で使っている選択肢が違うときは、この表を社内の値に書き換えてください。

## 指示ファイルがないとき（チャットで直接頼まれたとき）

人がチャットで、警告を示して「この警告の逸脱コメントを書いて」と頼んだときの進め方です。書き方・確かめ・選び方は、上と同じです。

- 警告の情報は、頼んだ人が示したもの（CID、チェッカー、ファイルと行、警告経路、真偽の見立て）を使う。
  - 警告経路が示されていなくて、MCP サーバー coverity-triage の `get_issues` が使えれば、ツールの説明のとおりに `output_dir` を渡さずに呼び、警告経路を取る。
  - 判定区分と根拠の場所が示されていなければ、スキル `triage-investigation` があれば、その手順で調べて決める。なければ、頼んだ人に聞く。
  - ほかに足りないもの（警告経路、CID、ファイルと行、ストリーム名など）も、頼んだ人に聞く。推測で補わない。
- プロジェクトの知識は、`<リポジトリ>/.coverity-triage/knowledge.md` があれば読む（上の「注意」）。
- 結果ファイルは書かない。Coverity にも書き込まない。
- チャットで返すもの：逸脱コメントの文、Classification・Action・Severity、判定区分と根拠の場所（ファイルと行）。言い切れないときは、そのことと、推奨は修正になることも伝える（上の「言い切れないとき」）。
