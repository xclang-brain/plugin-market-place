# embedded-debug-kit 仕様書

- 版：0.1.0
- 上位の文書：[憲章](../constitution.md) 1.0.0

## 1. 目的

組み込み機器で動く C/C++ プログラムの不具合を、AI が実機で試しながら直す。
ソースの修正 → クロスビルド → 機器への転送 → 機器での実行とログの取得 を繰り返す。

対象の機器は、FTP サーバーと、シリアルでつながるシェルを持つものとする。
Claude Code と GitHub Copilot CLI の両方で動く。

## 2. 共通

| 段階 | 部品 | 使い方 |
| --- | --- | --- |
| 1 | スキル（ビルド、転送、機器での実行とログの取得、設定） | 1つの作業だけを頼む |
| 2 | 作業エージェント | 不具合の調査と修正を任せる |
| 3 | 統括エージェントと検証エージェント | 作業と合否の判定を別のエージェントに分けて、計画・作業・評価を繰り返す |
| 4 | Web管理画面 | 3段階目の設定・進み具合・結果を、ブラウザーで見る |

- REQ-001：どの段階も、上の段階なしで使える。
- REQ-002：上の段階は、下の段階を名前だけで使う。下の段階の部品を替えても、上の段階は直さずに済む。
- REQ-003：機器ごとに違うもの（作業の方法と設定）は、1段階目と2段階目にだけ置く。
- REQ-004：Claude Code と GitHub Copilot CLI の両方で動く。スキルは、両方で同じものを使う。
- REQ-005：利用者の PC は Windows。Linux でも動く。
- REQ-006：各部品の使い方は、その部品の文書にだけ書く。上の段階の文書に、下の段階の中身を書かない。
- REQ-007：人が読む文書と、エージェントとスキルの定義は、独自の用語を避け、簡潔で自然な日本語で書く。してはいけないことは、最後に1か所にまとめる。

## 3. 1段階目：スキル

- REQ-101：設定を持つスキルは、次の3つの頼みに応える。
  - 作業をする。
  - 設定を確かめる。ファイルは作らない。
  - 設定ファイルを、説明つきのひな形から作る。
- REQ-102：設定ファイルとログは、作業フォルダの `.<スキルの名前>/` に置く。そのフォルダの中身は Git に入れない。
- REQ-103：設定ファイルの各項目のすぐ上に、意味を日本語のコメントで書く。必須の項目には「（必須）」と書く。
- REQ-104：パスワードは、設定ファイルか環境変数で渡す。結果にもログにも出さない。
- REQ-105：失敗したら、起きたことと確かめることを、平易な文で伝える。
- REQ-106：機器に接続できないときは、やり直さずに終える。
- REQ-107：転送が途中で失敗しても、機器に途中までのファイルを残さない。
- REQ-108：各スキルは、そのフォルダだけで完結する。フォルダをコピーするだけで、ほかのスキルやプラグインなしで使える。
- REQ-109：スクリプトは、Python 3.8 以上の標準ライブラリだけで動く。要るものは、スキルのフォルダに同梱する。
- REQ-110：スクリプトは、PowerShell と bash のどちらから動かしても、結果の文字が化けない。結果は、決まった形の JSON 1つで返す。
- REQ-111：設定のスキルは、指定されたスキルの SKILL.md と設定ファイルのコメントを読み、利用者に質問しながら設定を埋める。特定のスキルを前提にしない。

## 4. 2段階目：作業エージェント

- REQ-201：チャットの頼みだけで動く。Web管理画面とほかのエージェントは使わない。
- REQ-202：作業エージェントの定義は、使うスキルの名前だけを持つ。スキルが何をするかは、スキルの説明（description）に任せる。
- REQ-203：不具合を直すときは、次のように進める。
  1. 合格の条件を決める。頼みになければ、利用者に聞く。
  2. 今の症状を、機器で確かめる。
  3. 修正 → ビルド → 転送 → 機器での実行とログの取得 → 合否の判断 を、合格するか上限（既定 5 回）に達するまで繰り返す。1回を試行と呼ぶ。
- REQ-204：効かなかった変更は、戻してから次の試行に進む。デバッグ用の出力を足したときは、終わりに残すかを聞き、消したら確かめ直す。
- REQ-205：機器と通信できないときは、同じ操作を繰り返さず、起きたことを伝えてどうするかを聞く。
- REQ-206：終わったら、結論（直ったか、原因、変えたファイル）、試行ごとの結果、ログの場所を報告する。
- REQ-207：ほかのエージェントから頼まれたときは、頼みの文に書かれた手順と返事の形に従う。
- REQ-208：直すのは、作業フォルダのソースだけ。スキルの設定ファイルは、頼まれたときだけ変える。

## 5. 3段階目：統括エージェントと検証エージェント

- REQ-301：統括エージェントは、頼みから「頼む作業」と「合格の条件」を決める。条件がなければ、利用者に聞く。
- REQ-302：試行ごとに、計画 → 作業（作業エージェント）→ 評価（検証エージェント）の順に進める。すべての条件に合格するか、上限（既定 5 回）に達したら終える。
- REQ-303：統括エージェントは、ファイルを直さず、コマンドも動かさない。使えるツールで、これを守らせる。
- REQ-304：作業エージェントへの頼みは、ふつうの文で目的を伝える。機器やスキルのことは書かない。
- REQ-305：作業エージェントは、頼みに名前があればそれを使い、なければ既定の作業エージェントを使う。
- REQ-306：検証エージェントは、報告に書かれたファイルを自分で読み、条件ごとに「合格」「不合格」「判断できない」を返す。成果物は直さない。見かけだけ条件を満たす変更は、合格にしない。
- REQ-307：合否は、検証エージェントの返事のとおりに扱う。統括エージェントは、自分で合否を決めない。
- REQ-308：終わったら、結論（成功・失敗・人の判断が必要）、条件ごとの最後の評価、試行ごとの要約、変えたファイルを、チャットで報告する。
- REQ-309：終わったら、このプラグイン自身の改善点を振り返る。改善点があれば、Issue にするかを聞く。Issue は、題と本文を入れた作成ページの URL を示し、利用者が開いて作る。
- REQ-310：Web管理画面なしで動く。設定と結果は、チャットでやり取りする。

## 6. 4段階目：Web管理画面

- REQ-401：Web管理画面は、スキルで起動と停止をする。127.0.0.1 だけで待ち受け、起動ごとに変わる鍵を付けた URL で開く。
- REQ-402：設定：頼む作業、合格の条件、試行の上限、作業エージェントの名前を入れると、統括エージェントに送る頼みの文ができる。利用者は、その文をチャットに送って始める。
- REQ-403：監視：動いているエージェント、試行ごとの作業の頼みと報告、検証エージェントの返事、使われたツールを見られる。
- REQ-404：停止：「止める」を押すと、エージェントのツールの呼び出しを断り、作業を終えるよう伝える。次の頼みを送ると、元に戻る。
- REQ-405：結果：統括エージェントの最後の報告と、条件ごとの最後の評価を見られる。条件ごとの評価は、検証エージェントの返事から読む。前の実行の結果も開ける。
- REQ-406：記録は、作業フォルダの `.debug-dashboard/` に置き、Git に入れない。画面を起動していない作業フォルダでは、何も記録しない。
- REQ-407：統括・検証・作業エージェントは、Web管理画面のことを知らない。記録と停止は、CLI のフックで行う。
