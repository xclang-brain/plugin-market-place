# embedded-debug-kit 仕様書

- バージョン：0.1.0
- 上位の文書：[憲章](../constitution.md) 1.0.0

## 1. 目的

組み込み機器で動く C/C++ プログラムの不具合を、AI が実機で試しながら直す。
ソースを直し、クロスビルドし、機器に送り、機器で動かしてログを取る。これを繰り返す。

対象は、FTP サーバーと、シリアルでつながるシェルの両方を持つ機器とする。

## 2. 用語

| 用語 | 意味 |
| --- | --- |
| 作業フォルダ | CLI を起動したフォルダ。直すソースがある |
| 依頼文 | 利用者やエージェントが、エージェントに送る依頼の文 |
| 試行 | 修正 → ビルド → 転送 → 機器での実行とログの取得 → 合否の判断 の1回 |
| 報告 | 作業エージェントと統括エージェントが返す、作業の結果の文 |
| 判定 | 検証エージェントが返す、合格の条件ごとの合否 |
| フェーズ | 試行の中の区切り。計画・作業・評価の3つ |
| セッション | CLI を起動してから終えるまでの、1つの会話 |
| フラグ | あるかないかで状態を表すファイル。記録中フラグと停止フラグがある |

フェーズの計画・作業・評価は、憲章の Plan・Do・Study にあたる。

## 3. 4つの段階と共通の要件

| 段階 | 部品 | 使い方 |
| --- | --- | --- |
| 1 | スキル（ビルド、転送、機器での実行とログの取得、設定） | 1つの作業だけを依頼する |
| 2 | 作業エージェント | 不具合の調査と修正を任せる |
| 3 | 統括エージェントと検証エージェント | 作業と合否の判定を別のエージェントに分け、計画・作業・評価を繰り返す |
| 4 | Web管理画面 | 3段階目の設定・進み具合・結果を、ブラウザーで見る |

- REQ-001：どの段階も、上の段階なしで使える。
- REQ-002：上の段階は、下の段階を名前だけで使う。下の段階の部品を替えても、上の段階は直さずに済む。ただし、統括エージェントの定義は、使う作業エージェントの名前を持つ。作業エージェントを替えるときは、その名前を直す。
- REQ-003：機器ごとに違うもの（作業の方法と設定）は、1段階目と2段階目にだけ置く。
- REQ-004：Claude Code と GitHub Copilot CLI の両方で動く。スキルは、両方で同じものを使う。
- REQ-005：利用者の PC は Windows。Linux でも動く。
- REQ-006：各部品の使い方は、その部品の使い方の文書にだけ書く（置き場所は設計書の2章）。上の段階の文書に、下の段階の中身を書かない。
- REQ-007：エージェントとスキルの定義と、使い方の文書は、独自の用語を避け、簡潔で自然な日本語で書く。してはいけないことは、各ファイルの最後の「してはいけないこと」の節にまとめる。
- REQ-008：エージェントとスキルの名前は、ほかのプラグインとぶつかりにくい、役割の分かる名前にする。

## 4. 1段階目：スキル

- REQ-101：設定を持つスキルは、次の3つの依頼に応える。
  - 作業をする。
  - 設定を確かめる。このとき、作業フォルダに何も作らない。
  - 設定ファイルを、説明つきのひな形から作る。
- REQ-102：設定ファイルとログは、作業フォルダの `.<スキルの名前>/` に置く。このフォルダに何かを書く前に、中身を Git に入れないための `.gitignore` を置く。
- REQ-103：設定ファイルの各項目のすぐ上に、意味を日本語のコメントで書く。必須の項目には「（必須）」、パスワードの項目には「（秘密）」と書く。値の例は「例：」、選べる値は「選べる値：」で始まる行に書く。
- REQ-104：パスワードは、設定ファイルか環境変数で渡す。チャットでは聞かない。結果にもログにも出さない。
- REQ-105：失敗したら、起きたことと確かめることを、平易な文で伝える。
- REQ-106：機器に接続できないときは、やり直さずに終える。
- REQ-107：転送が途中で失敗したら、機器に残った途中までのファイルを消す。接続が切れたなどで消せないときは、ファイルが残っているかもしれないと伝える。送り先は、設定したフォルダの中だけにする。
- REQ-108：1段階目の各スキルは、そのフォルダだけで完結する。フォルダをコピーするだけで、ほかのスキルやプラグインなしで使える。
- REQ-109：スクリプトは、Python 3.8 以上の標準ライブラリだけで動く。ほかに必要なものは、スキルのフォルダに同梱する。
- REQ-110：スクリプトは、PowerShell と bash のどちらから動かしても、結果の文字が化けない。結果は、決まった形の JSON 1つで返す。
- REQ-111：設定用のスキルは、スキルの名前を受け取り、そのスキルの設定ファイルのコメントを読んで、利用者に質問しながら値を埋める。ほかのスキルの SKILL.md やフォルダは読まない。「（秘密）」の項目は値を聞かず、環境変数の名前を聞くか、利用者が自分で書くよう伝える。

## 5. 2段階目：作業エージェント

- REQ-201：チャットの依頼だけで動く。Web管理画面とほかのエージェントは使わない。
- REQ-202：作業エージェントの定義は、使うスキルの名前だけを持つ。スキルが何をするかは、スキルの説明（description）に任せる。
- REQ-203：利用者から直接依頼されて不具合を直すときは、次のように進める。
  1. 合格の条件を決める。依頼になければ、利用者に聞く。
  2. 今の症状を、機器で確かめる。
  3. 試行を、合格するか上限（既定は5回）に達するまで繰り返す。
- REQ-204：効かなかった変更は、戻してから次の試行に進む。デバッグ用の出力を足したときは、終わりに残すかを利用者に聞く。消したら、もう一度ビルドして機器で確かめる。
- REQ-205：機器と通信できないときは、同じ操作を繰り返さず、起きたことを伝えてどうするかを聞く。
- REQ-206：終わったら、結論（直ったか、原因、変えたファイル）、試行ごとの結果、ログの場所を報告する。
- REQ-207：ほかのエージェントから依頼されたときは、依頼文に書かれた手順と報告の形に従う。合否は決めず、利用者には質問しない。聞きたいことや足りないものは、報告に書いて返す。
- REQ-208：直すのは、作業フォルダのソースだけ。スキルの設定ファイルは、依頼されたときだけ変える。
- REQ-209：機器の中身を変える操作（フラッシュやブートローダーへの書き込み、ファイルの一括削除、パスワードの変更など）は、する前に利用者に確かめる。確かめられないときはしない。

## 6. 3段階目：統括エージェントと検証エージェント

- REQ-301：統括エージェントは、利用者の依頼から、作業エージェントに任せる作業と合格の条件を決める。依頼に条件がなければ、依頼に書かれた正しい結果から作る。どちらもなければ、利用者に聞く。条件には C1 から順に番号を振る。
- REQ-302：試行ごとに、計画 → 作業（作業エージェント）→ 評価（検証エージェント）の順に進める。統括エージェントは、検証エージェントの判定を次の計画に生かす。すべての条件に合格するか、上限（既定は5回）に達したら終える。
- REQ-303：統括エージェントは、ファイルを直さず、コマンドも動かさない。統括エージェントの定義で使えるツールを絞り、これを守らせる。依頼できる相手も、作業エージェントと検証エージェントに絞る。
- REQ-304：作業エージェントへの依頼文は、ふつうの文で目的を伝える。機器やスキルのことは書かない。
- REQ-305：作業エージェントが、聞きたいことや足りないものを報告に書いたときは、統括エージェントが利用者に聞き、答えを次の依頼文に入れる。進められないときは、「人の判断が必要」として終える。
- REQ-306：検証エージェントは、報告に書かれたファイルを自分で読み、条件ごとに「合格」「不合格」「判断できない」のどれかで判定する。成果物は直さない。見かけだけ条件を満たす変更は、合格にしない。
- REQ-307：合否は、検証エージェントの判定のとおりに扱う。統括エージェントは、自分で合否を決めない。
- REQ-308：終わったら、結論（成功・失敗・人の判断が必要）、条件ごとの最後の判定、試行ごとの計画・報告の要約・判定、変えたファイルを、チャットで報告する。
- REQ-309：終わったら、実行を振り返り、このプラグイン自身の改善点を探す。改善点があれば、Issue にするかを利用者に聞く。Issue にするときは、まずタイトルと本文をチャットに出して利用者に確かめる。次に、タイトルと本文を入れた作成ページの URL を示す。利用者がその URL を開いて Issue を作る。本文には、作業フォルダのソース、ログ、設定の値、機器のアドレス、利用者の名前を入れない。
- REQ-310：Web管理画面なしで動く。設定と結果は、チャットでやり取りする。
- REQ-311：3段階目の実行の記録は、CLI が残す会話の記録と、各スキルのログとする。振り返り（REQ-309）は、この記録と REQ-308 の報告をもとにする。

## 7. 4段階目：Web管理画面

- REQ-401：Web管理画面は、debug-dashboard スキルと、それを呼ぶ CLI のフックの設定を合わせた1つの部品とする。プラグインとしてインストールしたときに動く。スキルは、利用者が呼んだときだけ動く。
- REQ-402：画面は、スキルで起動と終了をする。127.0.0.1 だけで待ち受け、起動ごとに変わるトークンを付けた URL で開く。
- REQ-403：設定：直したいこと、合格の条件、試行の上限を入力すると、統括エージェントに送る依頼文ができる。利用者は、それをチャットに送って始める。
- REQ-404：進み具合：今のフェーズを見られる。作業エージェントと検証エージェントへの依頼文と、その報告・判定を、届いた順にそのまま見られる。使われたツールも、新しい順にそのまま見られる。今のフェーズは、動いているエージェントの名前で決める。
- REQ-405：停止：「実行を止める」を押すと、そのセッションのツールの呼び出しを断り、エージェントに作業を終えるよう伝える。止めた状態は、そのセッションで次の依頼を送ると解除される。
- REQ-406：結果：統括エージェントの最後の報告と、検証エージェントの最後の判定を、そのまま見られる。前のセッションも開ける。
- REQ-407：記録は、作業フォルダの `.debug-dashboard/` に置き、Git に入れない。Copilot CLI では、作業フォルダが Git のリポジトリの中にあれば、リポジトリのいちばん上のフォルダに置く。画面を起動していないフォルダでは、何も記録しない。決まった形で書かれたパスワード（`名前=値`、URL の `利用者:パスワード@` など）は、`***` に替えて記録する。
- REQ-408：画面を使っていないときと、Python が見つからないときも、フックは1〜3段階目の動きを変えない。ツールの呼び出しを断るのは、「実行を止める」が押されたときだけにする。
- REQ-409：統括・検証・作業エージェントは、Web管理画面のことを知らない。画面も、エージェントの依頼文や報告の中身を読まない。
