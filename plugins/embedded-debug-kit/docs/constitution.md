# embedded-debug-kit 憲章

- 版：1.0.0
- 由来：embedded-debug-loop 憲章 1.2.0 を引き継いだもの。条の番号は同じにしてある。欠番（第4条と、第3章の第11条〜第18条）は、embedded-debug-kit に関わらないので載せていない。

## 第1章 総則

### 第1条 目的

本憲章は、embedded-debug-kit（組み込み機器の C/C++ の不具合を、ビルド・機器への転送・機器のログ取得を繰り返して調べ、直すプラグイン）が守る最上位ルールである。

### 第2条 構成

第2章は共通条項、第4章は embedded-debug-kit の条項である。どちらも embedded-debug-kit が守る。

### 第3条 用語

| 用語 | 定義 |
| --- | --- |
| 統括エージェント | 作業全体の指揮とタスク分担を行う |
| 作業エージェント | 割り当てられた作業を実行する |
| 検証エージェント | 作業成果物を検証する |
| Web管理画面 | ローカルWebサーバーが提供する、設定・監視・確認のためのブラウザ画面 |
| PDSサイクル | Plan（計画）– Do（実行）– Study（評価・学習）の反復 |

## 第2章 共通条項

### 第5条 準拠仕様

1. Agent Plugins 1.0.0、Claude Code の公式プラグイン仕様、GitHub Copilot CLI の公式プラグイン仕様に従う。
2. 仕様どうしが両立しない場合は Agent Plugins 1.0.0 を優先する。
3. 技術的な判断は、その時点の最新の公式の情報（公式の仕様、公式ドキュメント、更新履歴、最新の版での実測）にもとづいて行う。古い版や古いモデルの情報を使うときは、版と時点を書き、最新の情報で確かめ直す。

### 第6条 リポジトリの構成

1. リポジトリは、次の4種類の成果物を基本とする。

   | 成果物 | 内容 |
   | --- | --- |
   | 憲章 | プロジェクトが必ず守る最上位ルール |
   | 仕様書 | 実現する機能や振る舞いの要件 |
   | 設計書 | 仕様を実現するための構造・方式 |
   | 実装資産 | プログラムのソースコードとテストコードに加え、`SKILL.md` などのエージェント用定義ファイルを含む |

2. 優先順位は 憲章 ＞ 仕様書 ＞ 設計書 ＞ 実装資産 とし、下位は上位に矛盾しない。
3. 仕様書の要件は、設計書・実装資産・テストまで追跡できるようにする。

### 第7条 開発の進め方

ユーザーと対話しながら、憲章 → 仕様書 → 設計書 → 実装資産 の順に開発・保守する。

### 第8条 SWEBOK

[SWEBOK](https://www.computer.org/education/bodies-of-knowledge/software-engineering) の知識体系・考え方を踏まえて開発する。一律の手順とはせず、対象に適した実践方法を選ぶ。

### 第9条 分かりやすさ

1. 人間に伝える内容と人間が読む成果物は、分かりやすさを何より重視し、簡潔に、伝わる用語で書く。
2. 人間の指摘は、文言をそのまま残さず、目的に沿って直す。

### 第10条 KISS

1. 必要なものだけを、できるだけ単純に作る（KISS：Keep It Simple, Stupid）。
2. リポジトリを肥大化させない。

## 第4章 embedded-debug-kit の条項

### 第19条 マルチエージェント構成

1. 統括エージェント1体、作業エージェント1体以上、検証エージェント1体で構成する。
2. 作業エージェントは自らの成果物を判定しない。検証エージェントは成果物を修正せず、指摘を統括エージェントに返す。
3. 作業エージェントは、統括エージェントと検証エージェントなしに、単体でも使えるようにしてよい。単体で使うときは、第2項と第20条から第24条にかかわらず、Web管理画面を使わずに、作業エージェントが自分で計画を立て、結果を見て次の試行を決め、作業を終えてよい。

### 第20条 Web管理画面

1. ローカルWebサーバーを起動し、Web管理画面で各種設定を行えるようにする。
2. 既定ではローカルホストからの接続だけを受け付ける。

### 第21条 監視

Web管理画面で、各エージェントの状態・担当タスク・PDS のフェーズを監視でき、実行を停止できるようにする。

### 第22条 結果確認

Web管理画面で、各エージェントの実行結果と検証結果を確認できるようにする。

### 第23条 PDSサイクル

PDS サイクルで成果物と作業の進め方を改善する。

- Plan：統括エージェントが実施内容と評価基準を決める。
- Do：作業エージェントが計画に沿って試行する。
- Study：検証エージェントが結果を分析し、統括エージェントが次の試行に反映する。

### 第24条 自己改善

1. 実行中にログを残し、実行後にログを振り返って課題を洗い出す。
2. 自身の改善につながる課題を見つけたら、自身の GitHub リポジトリに Issue を起票する。
3. 起票は毎回ユーザーの承認を得てから行う。

### 第25条 部品の独立性

1. 部品（スキル、スクリプトなど）は、疎結合で、モジュール強度が高くなるように作る。
2. 部品は、単体でも動くことが望ましい。
3. 組み込み機器に固有のことは、すべて作業エージェントとそのスキルが受け持つ。統括エージェント・検証エージェント・Web管理画面は、機器に固有のことを持たず、作業エージェントとは自然な文の頼みだけでやり取りする。作業エージェントを替えれば、別の機器でも動くようにする。
4. 作業エージェントは、使うスキルの名前と役割だけを知り、スキルの中身に頼らない。スキルどうしは、互いを知らず、頼り合わない。

### 第26条 4つの段階

1. 利用者が AI に任せる範囲に応じて、次の4つの段階で使えるようにする。
   - 1段階目：スキル。1つの作業だけを頼む。
   - 2段階目：作業エージェント。不具合の調査と修正を任せる。
   - 3段階目：統括エージェントと検証エージェント（マルチエージェント）。作業と合否の判定を別のエージェントに分け、計画・作業・評価を繰り返す。
   - 4段階目：Web管理画面。3段階目の設定・進み具合・結果を、ブラウザーで見る。
2. どの段階も、上の段階なしで使える。
3. 上の段階は、下の段階を名前だけで使い、その中身に頼らない。
4. 第20条から第22条は、4段階目に当てはまる。3段階目では、設定と結果をチャットでやり取りする。
